## 2026-08-26 — Task 状态节点、机械判定与等待/自动续派

### 原始思路

调度 Agent 与开发 Agent 之间，不应只依赖“发 Task → Agent 工作 → 聊天返回结果”的一次性交互，而应存在一个类似 **Task Record / State Node（任务记录节点 / 状态节点）** 的中间层。

可能的基本链路：

```text
Orchestrator
→ 创建 Task
→ Task 进入可运行状态
→ Agent 领取 / 开始执行
→ Agent 完成并把 Result 落库
→ 系统执行机械判定
→ 若满足 Task completion contract，则自动标记 Task OK / DONE
→ 更新 Task 状态
→ 触发后续依赖 Task / Waiting Task
```

### 机械判定层

Agent 完成后，系统不一定需要每次都等待 Orchestrator 人工读取全文才能知道“任务是否形式上完成”。

可以存在一个机械判定层，只负责检查明确、可机器验证的 completion 条件，例如：

- Result 文件是否存在；
- Task ID 是否一致；
- required commit / remote commit 是否存在；
- required files / outputs 是否存在；
- declared validation 是否完成；
- Result schema 是否完整；
- Task 是否仍基于有效 Coordination Revision；
- 是否存在明确 blocker / escalation / failed validation；
- 是否满足 Task 定义的 machine-checkable completion contract。

机械判定通过后，可以把 Task 从例如：

```text
RUNNING
→ RESULT_DELIVERED
→ MECHANICALLY_COMPLETE
```

或类似状态推进。

但“机械完成”是否等于“最终接受 / ACCEPTED”，需要后续单独设计。高风险任务仍可能需要 Reviewer / Orchestrator / Lead Design Authority 作语义裁决。

### 等待任务 / Dependency Waiting

该状态节点可以进一步支持 **Waiting Task（等待任务）**。

Task 可以声明：

```text
WAITING_FOR:
- Task A mechanically complete
- Task B accepted
- exact artifact / commit exists
- Finding closed
```

系统能够判断依赖 Task：

- 是否尚未开始；
- 是否正在运行；
- 是否已经交付 Result；
- 是否机械完成；
- 是否失败；
- 是否最终接受。

这样等待任务不需要依赖聊天上下文判断“前一个 Agent 做完没有”。

### Agent 等待队列 / 自动续派

Agent 也可以拥有自己的 Waiting Queue / Ready Queue。

例如：

```text
Claude Session A
当前：Task-100 RUNNING
等待：Task-104 WAITING_FOR Task-100
```

当 Task-100 满足指定完成条件后：

```text
Task-100 DONE
→ Task-104 dependency satisfied
→ Task-104 READY
→ 系统自动把 Task-104 发给 / 唤醒原 Agent 会话
```

因此 Agent 可以：

- 判断自己当前是否正在执行 Task；
- 注册一个或多个等待 Task；
- 空闲后自动领取下一项 Ready Task；
- 在依赖完成时自动恢复执行；
- 减少用户手工复制 Task、查看谁完成、再手动续派的工作。

### 潜在延伸

这个方向以后可以继续讨论：

1. Task 状态机应如何设计；
2. “机械完成”与“语义接受 / Review PASS”如何分层；
3. Waiting Task 的依赖表达方式；
4. Event-driven（事件驱动）还是 polling（轮询）；
5. 如何识别一个 Agent / Session 是否仍在运行；
6. 同一个 Agent 的 2–3 个并行 Session 如何分别维护 queue；
7. Task 完成后如何自动选择下一 Task；
8. Agent 失联 / 会话关闭 / quota exhausted 时如何重新分配；
9. 自动续派如何避免同时向多个 Session 重复发送同一 Task；
10. 完成 Task 的长期归档、压缩、历史索引方式后续单独设计。

### 当前判断

这是一个值得保留的方向：

> Repository file handoff 可以进一步演进为 Repository-backed Task State Machine + Dependency Queue + Agent Scheduling Layer。

它可能成为未来“自动化多 Agent 开发调度器”的核心基础之一。
