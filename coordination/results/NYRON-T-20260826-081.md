## Determination

Existing accepted Runtime and Accounting read boundaries are sufficient to reject fabricated or unrelated reservation identity without adding a cross-owner contract. The correction can remain local to BudgetReservation admission and can preserve Accounting as the sole writer of budget state.

The implementation must consume Runtime-owned truth through the existing repository/query surfaces. It must not query Runtime tables directly from Accounting merely because the SQLite schema makes that convenient.

## Existing Accepted Surfaces

1. `ActivationRepository.resolve(activation_ref) -> Activation | None` in `src/nyron_kernel/execution/activation.py` resolves the immutable Runtime Activation. The returned value includes `activation_ref`, `execution_ref`, `graph_revision_ref`, `module_instance_revision_ref`, and `static_accounting_scope_ref`.
2. `RuntimeAuthorityResolver.resolve_current(run_ref) -> AttemptAuthority | None` and `RuntimeAuthorityResolver.resolve_current_with(connection, run_ref)` in `src/nyron_kernel/execution/authority.py` are the accepted read-only Runtime query boundary. They return the canonical current authority tuple: `execution_ref`, `activation_ref`, `run_ref`, `attempt_seq`, `fencing_token`, and `fencing_generation`. The query itself requires an admitted WorkflowExecution, matching Activation/Run execution identity, an open Run, and a current `CREATED` or `ACTIVE` RunAttempt.
3. `AccountingScopeResolver.resolve(accounting_scope_ref, graph_revision_ref, definition_anchor_ref)` in `src/nyron_kernel/accounting/scope_resolver.py` is the accepted Accounting-owned resolver. It proves the exact leaf binding, complete root-to-leaf ancestry, common GraphRevision affiliation, and ancestry-hash consistency.

`RunRepository.resolve(run_ref)` is also a public Runtime repository read, but `RuntimeAuthorityResolver` is the narrower and stronger surface for reservation admission because it explicitly exposes current-attempt truth and validates the admitted Activation/Run/Attempt join without exposing Runtime tables.

## Fail-Closed Validation Sequence

The following sequence is implementation-local and requires no new contract:

1. Validate the request value shape as already required.
2. Resolve `request.activation_ref` with `ActivationRepository.resolve`. Reject if absent. This proves the exact immutable Activation rather than trusting caller identity.
3. Compare `request.graph_revision_ref` with `activation.graph_revision_ref`; reject any mismatch.
4. Compare `request.accounting_scope_ref` with `activation.static_accounting_scope_ref`; reject any mismatch.
5. Compare `request.definition_anchor_ref` with `activation.module_instance_revision_ref`; reject any mismatch. For the Module-execution path in Task 074, this is the immutable definition anchor already used by `ExecutionAdmissionGate`, which calls `AccountingScopeResolver.resolve(instance.static_accounting_scope_ref, graph.graph_revision_ref, instance.module_instance_revision_ref)`.
6. Resolve current Runtime authority using `RuntimeAuthorityResolver.resolve_current_with` on the connection/snapshot used for admission, or the equivalent accepted `resolve_current` boundary where the accepted synchronous single-writer discipline makes the snapshot indivisible. Reject if no current authority exists.
7. Compare the returned authority's `activation_ref` to the resolved Activation, `run_ref` to the request, `execution_ref` to `activation.execution_ref`, and `attempt_seq` to the request. Reject any mismatch. Because the Runtime resolver derives `attempt_seq`, fencing token and generation from the canonical current pointer and exact RunAttempt row, the request does not need to carry or reconstruct a fencing token. `(run_ref, attempt_seq)` identifies the Attempt; the resolver proves that this Attempt currently holds Runtime authority.
8. Call `AccountingScopeResolver.resolve` with the canonical values from the resolved Activation: `activation.static_accounting_scope_ref`, `activation.graph_revision_ref`, and `activation.module_instance_revision_ref`. Do not use unmatched caller values as authority. Reject any resolution or ancestry failure.
9. Only after steps 1–8 may Accounting evaluate policies, change exposure counters, or insert a `RESERVED`/`DENIED` reservation. Existing-request replay must also pass the Runtime/static-binding checks before returning the canonical reservation; otherwise a row created through the former defect could bypass the correction.

The current Runtime authority check must be part of the indivisible reservation-admission snapshot. `resolve_current_with(connection, run_ref)` already exists specifically for a caller-supplied connection and is used as a read-only query boundary; using it does not authorize Accounting to mutate Runtime state. Under the standing accepted synchronous SQLite single-writer model, it can be invoked while Accounting owns the reservation transaction without creating a second writer or a cross-owner write transaction. Any future multi-connection/process writer model would require separate revalidation under the existing concurrency interlock.

## Required Questions

1. **Activation exists and resolves exactly:** YES — `ActivationRepository.resolve` returns the immutable canonical Activation or `None`.
2. **GraphRevision equality:** YES — compare the request to `Activation.graph_revision_ref`.
3. **AccountingScope equality:** YES — compare the request to `Activation.static_accounting_scope_ref`.
4. **Run belongs to the same Activation:** YES — `RuntimeAuthorityResolver` returns the Runtime-owned `activation_ref` and `execution_ref`; compare both to the resolved Activation.
5. **Exact accepted RunAttempt authority:** YES — the resolver returns the canonical current Attempt identity plus fencing token/generation and fails closed unless it is the admitted, open, current `CREATED`/`ACTIVE` authority. Compare its `(run_ref, attempt_seq)` to the request.
6. **Definition anchor without caller fiction:** YES — for Task 074's Module execution path, derive it from `Activation.module_instance_revision_ref`, compare the request, and pass the canonical value to `AccountingScopeResolver`. This is consistent with the already-accepted admission binding.
7. **No dynamic provenance required:** YES — no Packet, trigger Edge, PWP, current Workspace/Project pointer, worker/provider identity, or other dynamic provenance participates. This preserves the frozen static-membership rules.
8. **Read-only Runtime validation / Accounting-only budget writes:** YES — Runtime repositories/resolver are read-only in this flow; only `BudgetAuthority` mutates reservation, policy, and exposure state.
