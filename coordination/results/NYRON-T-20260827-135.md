## Executive Conclusion

The frozen D-008 Process boundary is implementable as a bounded future slice on the current Nyron Runtime/Host foundation **without architecture redesign**, but it is not safe to open Process Production yet.

The current Production surface does **not** expose a Process EXEC adapter. `TrustedModuleHost` currently registers only the in-process trusted `builtin_text_concat` implementation, and `RuntimeContext` exposes only the bounded-write effect broker. Repository inspection found no current `subprocess`/`Popen`/`CreateProcess`/Process adapter implementation. Therefore the blocking findings below are **future activation blockers**, not evidence that the accepted current PURE/trusted host already violates process containment.

A future Process slice must not be implemented by simply adding subprocess spawning inside a trusted Module or by treating the root PID as the owned effect. The minimum safe design is a dedicated mediated Process Effect boundary that durably PREPARES the EffectOperation, revalidates live authority at the actual spawn boundary, enters an enforceable OS descendant-containment domain before untrusted child code can run, and only reports `FENCED` after the containment domain itself proves no controlled descendants remain. Any inability to establish or re-observe that proof must fail closed to `UNKNOWN`.

No Lead architecture escalation is required: the frozen D-008 / D-004 model already supplies the correct ownership vocabulary (`CapabilityGrant`, optional `ResourceLease`, `EffectOperation`, Attempt fencing, Recovery). The missing work is bounded implementation/platform machinery and tests.

3. Parent PID alone is insufficient containment or durable identity evidence.
4. A claimed process-isolation profile must capture relevant descendants; indirect children may not escape merely because the original parent exited.
5. Cancellation, timeout, terminate and kill are requests, not terminal proof.
6. `FENCED` requires reliable confirmation that all owned descendants are stopped or an authoritative equivalent fence is installed.

10. `FENCED` proves the old operation cannot continue; it does **not** prove historical non-occurrence or semantic retry safety. A possibly consequential process run may still require independent idempotency/history policy before redispatch.

## Required OS Containment Primitives

### Windows — minimum acceptable containment

A Windows Process adapter claiming descendant containment requires an OS Job Object (or a demonstrably equivalent stronger platform primitive) as the owned containment unit; the root PID is only supplemental evidence.

Minimum requirements:

1. Create a dedicated Job Object per Process EffectOperation or per explicitly modeled managed process resource.
2. Configure `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` before target code is allowed to execute, and keep the Job handle non-inheritable so broker crash/handle loss cannot be defeated by a child retaining the last handle.
3. Do **not** enable `JOB_OBJECT_LIMIT_BREAKAWAY_OK` or `JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK` for a containment profile. `CREATE_BREAKAWAY_FROM_JOB` must not provide an escape path.
4. Ensure assignment is complete before untrusted target code can run. Preferred on supported Windows is process creation with `STARTUPINFOEX` + `PROC_THREAD_ATTRIBUTE_JOB_LIST`; an acceptable bounded fallback is `CREATE_SUSPENDED`, `AssignProcessToJobObject`, verify success, then resume. If assignment fails, terminate before resume and fail closed.
5. Use `TerminateJobObject` (or stronger equivalent) to request termination of the full job tree, not only the root process.
6. Confirm terminal inactivity from the Job, e.g. `JOB_OBJECT_MSG_ACTIVE_PROCESS_ZERO` via completion port and/or authoritative Job accounting/query evidence. The return from `TerminateJobObject` is a kill request result, not by itself the Nyron `FENCED` proof.
7. Preserve enough durable launch/containment identity to interpret crash recovery. `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` is valuable crash fencing only if the Job handle is owned solely by the trusted broker and cannot be inherited/duplicated into the child boundary.
8. Nested-job incompatibility, unsupported platform versions, assignment denial, or inability to establish the no-breakaway invariant must cause Process EXEC to fail closed before target execution.

### Linux — minimum acceptable containment

A Linux Process adapter claiming descendant containment requires a dedicated cgroup v2 domain (or a demonstrably equivalent stronger supervisor/container boundary). A POSIX process group/session alone is **not** sufficient for D-008 hostile descendant containment because daemonization/double-fork/session changes can escape signal-group ownership.

Minimum requirements:

1. Create a dedicated cgroup v2 domain under a broker-owned or correctly delegated subtree.
2. Establish the child in the target cgroup **before target code can run**. Acceptable primitives include `clone3(CLONE_INTO_CGROUP)` on supported kernels or a trusted launcher that is itself already inside the dedicated cgroup and performs the final exec. A create-then-later-write-PID-to-`cgroup.procs` sequence has a child/fork race and is not sufficient for a hostile containment claim unless the child is otherwise held from execution until migration is complete.
3. Ensure the target cannot migrate itself outside the delegated subtree. cgroup delegation/permissions must deny outward migration; exposing the global cgroup hierarchy writable to the child defeats the claim.
4. Descendants inherit cgroup membership on fork; double-fork/daemonization therefore remains inside the cgroup so long as migration escape is prevented.
5. Request full-tree termination using cgroup v2 `cgroup.kill` where available. Kernel documentation specifies that it kills the cgroup and descendants with `SIGKILL` and handles concurrent forks/migrations.
6. Confirm terminal inactivity using `cgroup.events` `populated 0`, whose semantics cover the cgroup and descendants. Reading an empty one-time PID list or observing root PID exit is not equivalent proof.
7. A zombie does not appear in `cgroup.procs`; therefore zombie/reaping status must not be confused with a live descendant. `populated 0` proves no live processes in the subtree, while the trusted launcher/broker must also reap directly owned children so Nyron does not leak zombie process-table entries.
8. Persist the cgroup/launch token identity needed for crash recovery. After broker restart, the adapter must be able to reopen/observe the same cgroup, kill remaining descendants, and classify history. If it cannot prove whether a matching spawn occurred or whether descendants survive, the EffectOperation is `UNKNOWN`.
9. If cgroup v2/delegation/`cgroup.kill` or an equivalent proven containment service is unavailable, the first bounded Process slice must report the platform/profile as unsupported rather than silently degrading to PID-only/process-group-only containment.

Linux authority references:

- Linux Kernel — Control Group v2: https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html
  - child inheritance through fork;
  - delegation containment;
  - `cgroup.kill` full subtree SIGKILL semantics;
  - `cgroup.events populated` recursive liveness signal.
- Linux man-pages — `clone(2)` / `clone3(CLONE_INTO_CGROUP)`: https://man7.org/linux/man-pages/man2/clone.2.html
- Linux man-pages — `cgroups(7)`: https://man7.org/linux/man-pages/man7/cgroups.7.html

## Stdio / Inherited-Handle Boundary Requirements

Process containment is incomplete if the child can inherit unrelated broker authority or if pipe state is misused as lifecycle proof.

Minimum boundary:

- Default-deny inheritance of file descriptors/handles.
- Windows: `bInheritHandles=FALSE` unless inheritance is required; when required, use `STARTUPINFOEX` + `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` to pass only exact stdin/stdout/stderr handles. Job/DB/socket/secret/capability handles must never be inherited.
- POSIX/Linux: use close-on-exec/default-close behavior and an explicit allowlist for the exact stdio descriptors; do not leak StateStore DB fds, sockets, secret handles, workspace directory handles, or cgroup control fds into the target.
- stdin/stdout/stderr are transport streams, not authority/liveness evidence.
- Pipe EOF is not a Process `FENCED` proof: a descendant may inherit a pipe writer and keep it open after the root process exits.
- Cancellation must be able to close/stop stdin delivery and bound output collection without depending on the child cooperating.
- Output draining must be bounded/backpressured so an untrusted child cannot deadlock the broker on full pipes or cause unbounded in-memory capture. Resource-limit details beyond this minimum remain IsolationProfile policy.

## Minimum Future Process EXEC Implementation Boundary

The smallest safe first slice should support only an explicitly declared platform/profile set and reject everything outside it.

### A. Request / authority envelope

A Process request must carry at least:

- stable `operation_ref` / caller intent identity;
- current AttemptAuthority tuple;
- exact `PROCESS_EXEC` CapabilityGrant reference;
- machine-checkable command request identity (prefer executable + argv, not an implicit shell string);
- optional ResourceLease references only when the selected profile actually requires a managed Resource;
- stdio mode declaration;
- selected supported IsolationProfile / platform backend.

The first slice should default to direct executable + argv and `shell=False` semantics. Shell execution can be a later explicitly scoped capability/profile because it materially widens parsing and descendant behavior.

### B. Durable pre-spawn sequence

```text
validate request shape
→ derive stable Process operation_ref
→ commit Process EffectOperation(PREPARED)
→ allocate/record durable containment launch identity
→ revalidate current Attempt + fencing + PROCESS_EXEC Grant + applicable Lease
→ establish OS containment before target code can run
→ spawn/exec target
→ durably record external spawn acknowledgement / process start identity
→ ACTIVE
```

If authority validation or containment setup fails before spawn is provably possible, owner may fence as a proven no-dispatch path. If spawn history is ambiguous, state must be `UNKNOWN`, never guessed back to PREPARED/not-dispatched.

### C. Cancellation / timeout / replacement sequence

```text
cancel / timeout / replacement request
→ EffectOperation(REVOKE_REQUESTED)
→ stop stdin / stop accepting new child work as applicable
→ terminate full containment domain
→ wait/query authoritative containment liveness
   ├─ all controlled live descendants absent → FENCED (active execution stopped)
   └─ cannot prove → UNKNOWN + Recovery handoff
```

Root process exit, successful signal delivery, local pipe close, timeout, socket disconnect, or `TerminateJobObject`/`kill` call success is never sufficient by itself.

### D. Crash recovery sequence

```text
recover PREPARED/ACTIVE/REVOKE_REQUESTED Process EffectOperation
→ reopen/lookup durable containment identity + strongest process-start identity
→ classify external active state from platform evidence
   ├─ matching containment/process still live → ACTIVE/REVOKE_REQUESTED as owner semantics require
   ├─ reliable evidence proves never spawned → safe non-dispatch fence path
   ├─ containment proven empty after revoke → active fence proven
   └─ history/containment cannot be proven → UNKNOWN
→ if UNKNOWN, open/feed Recovery case
```

Historical consequence remains independent: a Process operation that ran before being fenced may have performed irreversible external work. Per the fenced-retry amendment, Process redispatch requires independent idempotency/history policy; active `FENCED` status alone is not replay clearance.

### E. Platform support rule

First implementation may legitimately support only:

- Windows versions where the selected Job Object creation/assignment strategy can be made race-free and no-breakaway;
- Linux deployments with cgroup v2 and the required delegated control/kill/observation primitives.

That is preferable to a portability shim that silently downgrades safety. Unsupported OS/runtime/container environments must return an explicit unsupported-profile failure before target execution.
