## Executive Conclusion

The frozen D-008 Network boundary is implementable without architecture redesign, and several generic Nyron foundations are reusable: exact Attempt/fencing identity, immutable CapabilityType/Grant records, inert RuntimeContext handles, the PREPARED-before-external-mutation pattern, and generic Recovery case/evidence records.

However, the current Kernel/Host implementation is **not sufficient as-is to open a bounded Network production slice**. Three security-critical prerequisites remain blocking:

1. a non-bypassable mediated network path / truthful IsolationProfile;
2. supported boundary-time authority admission for the actual effective destination;
3. a consequential network EffectOperation path that preserves external identity, UNKNOWN history, cancellation evidence, and the EIW-INV-32 distinction between fencing and semantic retry safety.

These are bounded implementation dependencies, not reasons to reinterpret D-008. Track D Network production should remain unopened until they are implemented and independently reviewed.

## Required Effective-Destination Contract

The following is the minimum contract required by the frozen semantics. Component names are illustrative; the responsibilities are normative consequences of D-008, not new architecture.

### 1. Canonical requested destination

Before resolution or dispatch, the trusted adapter must canonicalize the requested destination into an unambiguous tuple at least equivalent to:

```text
scheme/protocol
canonical host identity
normalized effective port
request method / registered operation class
endpoint/path restriction input where the Capability scope uses it
```

Requirements:

- scheme/protocol is parsed, not prefix-matched;
- default ports are normalized before policy matching;
- DNS names are canonicalized label-wise (including IDNA handling) before exact/wildcard policy matching;
- wildcard matching is DNS-label bounded; `*.example.com` must not match `evil-example.com`;
- IP literals are parsed as IP addresses, not compared as arbitrary strings;
- ambiguous/legacy numeric host forms are rejected unless explicitly normalized by the approved parser;
- credentials embedded in a URL never widen destination authority.

### 2. Resolve under adapter control

For a direct connection, the adapter must resolve the authorized hostname through a controlled resolver and obtain concrete A/AAAA candidates before opening the connection.

Every candidate actually eligible for connection must be checked against the Capability scope's effective-address policy. Where policy is public-only, the safe default is to deny any non-globally-routable address unless explicitly authorized, including at minimum:

- IPv4 and IPv6 loopback;
- RFC1918 private ranges and IPv6 ULA;
- link-local ranges;
- unspecified addresses;
- multicast;
- reserved/special-use ranges;
- IPv4-mapped IPv6 representations of otherwise denied IPv4 addresses.

A mixed DNS answer must never be handed to a lower client that is free to choose an unvalidated address. The adapter may use only a specifically validated candidate, or fail closed according to the registered policy.

### 3. Bind authorization to the connection that is actually opened

The adapter must connect to the exact validated IP/port, or use an equivalently trusted mechanism that pins the validated result. Passing the hostname back to a lower networking library that silently re-resolves it reopens the DNS-rebinding gap.

After connection establishment, the adapter must verify the actual peer endpoint (or equivalent transport evidence) against the approved effective destination. For TLS, certificate/hostname verification and SNI remain bound to the authorized logical hostname; connecting by validated IP must not disable hostname authentication.

This yields the required relation:

```text
requested host is in scope
AND chosen resolved IP is in scope
AND actual connected peer is the approved endpoint
```

Authorization of the requested hostname alone is insufficient.

### 4. Redirects are new destination decisions

Every redirect hop is reparsed and reauthorized from the beginning:

```text
new scheme
new canonical host
new effective port
new resolved IP set / chosen peer
new method/operation semantics where redirect rules alter the request
```

The adapter must enforce a bounded redirect count. Cross-origin credential forwarding is denied by default and is permitted only by explicit credential and network policy. Scheme downgrade or port change is a new policy decision, not inherited authority.

### 5. Proxy chains do not collapse destination authority

Ambient `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY`-style behavior must not silently alter the trusted path. Proxy use must be explicit in the adapter/IsolationProfile.

For an explicit proxy there are two distinct questions:

1. is the transport hop to the proxy allowed; and
2. is the ultimate requested/effective destination allowed.

Allowing the proxy address never authorizes arbitrary proxy targets.

If DNS resolution occurs remotely at the proxy (for example a remote-DNS SOCKS/HTTP CONNECT path), the component performing remote resolution must itself be inside the trusted enforcement boundary and apply the same effective-destination restrictions. If Nyron cannot obtain trustworthy final-destination enforcement/evidence from that component, the profile cannot claim D-008 private/link-local/loopback exclusion for that route.

### 6. Connection reuse must not preserve stale authority

Connection pooling is an optimization, not an authority cache.

Before each request dispatch on a reused connection, the adapter must revalidate the current Attempt/fencing tuple and the applicable CapabilityGrant. A connection created by an old/replaced Attempt or revoked/expired Grant is not reusable merely because the socket is still open.

Pool identity/evidence must preserve the exact effective peer and policy binding. HTTP/2 or HTTP/3 origin coalescing must not allow a second hostname to inherit the first hostname's authorization; each logical origin is independently checked before use.

For a new connection, resolution/effective-destination validation runs again. For a still-open reused connection, the already connected peer remains the effective IP, but policy/authority must still be current; any profile requiring DNS freshness must additionally define and enforce its re-resolution/TTL rule.

### 7. Credential possession is downstream of authority

Credentials are acquired/attached only after the network destination and current Attempt/Capability authority pass. A token/API key/cookie is not evidence that a destination is authorized.

Credentials must not be forwarded to a redirect target or proxy outside their explicit credential scope. Credential lookup/possession must never substitute for `NETWORK_ACCESS` validation.

### 8. Consequential request effect boundary

For a request classified as consequential or crash-ambiguous, an EffectOperation must be durably PREPARED before the first external dispatch that can create relevant consequence. The dispatch gate then revalidates current Attempt/fencing and exact network Capability scope at the actual boundary.

The durable operation/evidence binding must preserve, when available:

- Nyron semantic operation identity;
- external request/operation identity;
- idempotency key and its protocol semantics;
- requested destination;
- approved effective destination / dispatch evidence;
- acknowledgement/response evidence;
- cancellation evidence;
- historical outcome classification needed for recovery.

Timeout or disconnect after possible dispatch yields `UNKNOWN`/equivalent historical uncertainty unless authoritative evidence proves a terminal outcome. Local socket close is only a cancellation/transport action, never proof of `FENCED` or remote failure.

If remote evidence proves no further activity can occur, active/concurrency state may become fenced, but historical consequence uncertainty must remain representable independently. `FENCED` alone never authorizes semantic retry.

### Recovery

- `src/nyron_kernel/recovery/repository.py::RecoveryRepository` is generic over `subject_owner_ref` / `subject_ref`, stores evidence separately from interpretation, and its retries are observation attempts rather than effect redispatch.

This is compatible with network reconciliation once Effect Authority can durably expose network operation identity/evidence.

## Missing Primitives / Dependencies

Before a bounded Network production implementation can claim D-008 conformance, the minimum missing surface is:

1. a registered machine-checkable `NETWORK_ACCESS` scope schema and validator covering protocol/host/port plus effective IP/CIDR and redirect/proxy policy;
2. a trusted effective-destination resolver/connector that owns DNS normalization, special-range classification, exact-peer binding, redirect revalidation, and proxy-chain enforcement;
3. a supported boundary-time dispatch-admission path that rechecks exact Attempt/fencing and Capability truth and cannot be replaced by advisory check-then-use;
4. a RuntimeContext/Host broker surface that exposes only request-level operations, never raw sockets/session transports;
5. a truthful IsolationProfile or external egress control that prevents Modules/libraries from bypassing the broker when bounded network authority is claimed;
6. a network-capable Effect Authority path for consequential requests, including durable external/idempotency/effective-destination evidence and orthogonal active/fence versus historical-outcome semantics required by EIW-INV-32;
7. Recovery observation/lookup integration for ambiguous network operations.

No new Kernel primitive named HTTP/Browser/Provider is required by this review. These responsibilities remain adapter-mediated uses/extensions of the frozen generic authority model.

Severity: `HIGH — BLOCKING FOR CONSEQUENTIAL NETWORK OPERATIONS`
Invariant: `EIW-INV-13`, `EIW-INV-14`, `EIW-INV-20`, `EIW-INV-32`
Location:
- `src/nyron_kernel/effect/authority.py::EffectRequest`
- `src/nyron_kernel/effect/authority.py::EffectOperation`
- `src/nyron_kernel/effect/authority.py::EffectAuthority`
- `src/nyron_kernel/store/sqlite_store.py::SQLiteStore.create_effect_schema`
- `src/nyron_kernel/recovery/repository.py::RecoveryRepository`
- `tests/kernel/test_effect_operation_foundation.py`

Evidence:
- The current EffectAuthority is intentionally concrete: one `nyron.kernel.managed-resource-bounded-write@1` effect, string payload, deterministic local file target, and local target evidence.
- The `effect_operations` schema has one state dimension (`PREPARED/ACTIVE/REVOKE_REQUESTED/FENCED/COMPLETED/UNKNOWN`) and no generic durable fields/interface for external request identity, idempotency semantics, effective network destination, or an orthogonal historical-outcome classification.
- EIW-INV-32 requires Nyron to preserve `active_state = FENCED` together with `historical_outcome = UNKNOWN | PARTIAL | KNOWN` or equivalent semantics.

Concrete failure scenario:
- A non-idempotent POST is externally accepted, but the client disconnects before the response.
- Nyron correctly has historical uncertainty.
- A later cancellation/status path proves no further remote activity can occur, clearing active conflict, but cannot prove whether the POST already produced its consequence.
- A single-state `FENCED` representation cannot by itself preserve both facts; if retry logic interprets fencing as historical clearance, the POST can be duplicated.

Why existing tests do not catch it:
- Current tests validate local-file UNKNOWN/FENCED behavior where evidence is derived from a deterministic target path.
- They do not exercise a network operation with durable external request identity, remote cancellation proof, `FENCED + historical UNKNOWN`, provider/server lookup, or idempotency-key-based redispatch safety.

Required Resolution:
- Extend/generalize the Effect Authority-owned operation/evidence contract for the bounded Network slice so PREPARED precedes dispatch, external/idempotency/effective-destination evidence is durable, timeout/disconnect remains historically unknown when appropriate, cancellation proof affects active state without erasing history, and semantic retry is separately justified under EIW-INV-32.
- Reuse RecoveryRepository for bounded observation/reconciliation; Recovery must not itself redispatch the consequence.

Disposition: `BLOCKING BEFORE CONSEQUENTIAL NETWORK PRODUCTION GO`

## Minimum Future Implementation Boundary

A smallest D-008-conformant Network slice should remain narrow:

1. one registered `NETWORK_ACCESS` CapabilityType/version with a strict machine-checkable scope schema;
2. one broker-mediated request API exposed through RuntimeContext, using inert handles only;
3. one trusted direct HTTPS adapter path first — no ambient proxies, no arbitrary proxy chain, no raw socket exposure;
4. controlled A/AAAA resolution, address-class validation, exact peer pinning/verification, strict TLS hostname verification;
5. bounded redirect handling with complete reauthorization per hop;
6. boundary-time Attempt/fencing/Capability revalidation after destination resolution and before dispatch/reuse;
7. one consequential request class integrated with Effect Authority PREPARED/ACTIVE/UNKNOWN/cancel/recovery semantics and EIW-INV-32-safe historical outcome handling;
8. Recovery lookup/observation wiring for ambiguous outcomes;
9. an IsolationProfile/egress control statement that is testable and truthful about whether raw Module network bypass is prevented;
10. the adversarial tests above before any broader proxy, streaming, browser, provider, or remote-worker networking is opened.

Starting with direct HTTPS only is a scope reduction, not a semantic change: proxy chains or broader protocols can remain unsupported until their enforcement points are independently proven.
