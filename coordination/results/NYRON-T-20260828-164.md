## 2. Answers To The Required Questions

1. **What credential authority/ownership is already frozen?** PWP owns the durable non-secret reference slot/identity (`secret_ref` / `secret_refs`, immutably revisioned). D-008 freezes the consumption-boundary *rules* (§13, `EIW-INV-18/19/20/22/23/24`) but explicitly does not freeze secret-store internals or a resolution/injection implementation. No Owner currently owns "resolve a reference into a usable value" — that is the gap this Task is asked to judge.
2. **Can a bounded credential-reference + trusted-value-injection foundation be implemented without architecture amendment?** Yes. Every requirement it must satisfy is already frozen text (§13 items 1–10, the invariants above); nothing needed is undefined at the architecture level.
3. **What may be persisted durably vs never?** Durable: reference identifiers (`secret_ref`/binding refs), binding-class/profile-scope identity, policy refs, evidence refs (which operation/attempt a resolution was used for), redacted/boolean status, timestamps. Never: raw secret value, bearer token, API key, request header carrying a credential, or any object that exposes the value via `repr`/`str`/serialization.
4. **What stable non-secret credential reference identity is required before Provider dispatch admission?** A binding reference that composes (a) the PWP `secret_ref` it points at, (b) the `provider_profile_ref`/`profile_revision_ref` scope it is valid for, and (c) a monotonic revision so rotation produces a new identity rather than mutating one in place — mirroring the existing `ProviderProfileRevision`/`EnvironmentBindingRevision` revision pattern already accepted elsewhere in the codebase.
5. **Where may secret material exist in memory, and who owns resolution/injection?** Only inside the trusted adapter/broker (TCB) at the moment of actual external use, for the duration of one Attempt-scoped operation; never in Module inputs/config, Packet, Continuation, RuntimeContext metadata, canonical history, or any structure that outlives that single use. The trusted broker — not the Module, not generic Runtime plumbing, not the credential-reference model itself — owns resolution/injection, consistent with D-008 §13.2 and Task 140 layer B.
6. **What redaction/non-observability guarantees are mandatory for logs, errors, evidence, replay, Result records and SQLite?** No raw value may appear in any exception message, log line, telemetry payload, `ProviderEvidence`/durable Result record, replay/recovery evidence, or SQLite column. This must hold even on the *failure* path (adapter/provider error text), not only the success path — D-008 §13 item 7 and the `credential_exposure_claim` adversarial checklist item apply to error/telemetry surfaces specifically because that is the usual leak vector.
7. **How must rotation/revocation interact with Attempt, CapabilityGrant, ResourceLease and Provider operation identity?** Rotation creates a new binding revision/reference; it must never rewrite the meaning of a historical `ProviderOperation`/`ProviderEvidence` record already bound to the prior revision (mirrors `EIW-INV-20`/`EIW-INV-22` and the existing immutable-revision pattern). Revocation must make resolution fail closed for that reference going forward; it must not retroactively alter past evidence, and it must not itself be treated as proof of the *external* provider-side effect (that remains Provider/Effect-owned historical-outcome semantics, untouched by this foundation).
8. **Does credential presence ever grant authority?** `NO` — this is a frozen invariant (`EIW-INV-19`), not a design choice this session can weigh. The authority that must still be independently revalidated at actual dispatch time is exactly the set `TrustedUnaryProviderBroker.admit_simulated_dispatch()` already re-checks: current-attempt/fencing state, `CapabilityGrant` (state+run+attempt), `ResourceLease` (state+run+attempt), and Effect/reservation state. A successful credential resolution is orthogonal evidence, not a substitute for any of these.
9. **What happens after crash/restart when only a reference is durable?** The value is never durable, so after restart there is nothing to "recover" for the value itself — only the reference (already durable via PWP) and any binding metadata this foundation adds survive. Any component that needs the value again must call the trusted resolver again; if the resolver/backend is unavailable or misconfigured post-restart, resolution must raise a fail-closed error rather than substitute a stale/cached/default value or proceed without one.
10. **What minimum adversarial/boundary tests are required before acceptance?** (a) no `repr()`/`str()`/logging/serialization path exposes a resolved value; (b) the bounded-slice default resolver always fails closed with no implicit default/backdoor value; (c) a successful resolution alone is proven insufficient for dispatch admission — admission must independently query Attempt/fencing/CapabilityGrant/ResourceLease exactly as the Provider broker does; (d) rotation produces a new distinct reference identity, and a stale reference does not silently resolve under a newer revision; (e) simulated restart: no in-memory value/handle survives a process boundary, and post-restart resolution failure fails closed rather than degrading; (f) redaction holds on the *error* path (simulated resolver/adapter exception carrying a handle in its context must come out redacted); (g) schema-shape test proving every column this foundation persists is an identifier/ref/scope/boolean/timestamp, never free-form value storage.
11. **Can this foundation remain completely network-free and SDK-free?** Yes. Everything above is identity modeling, a resolver *interface* plus a fail-closed default implementation, and redaction helpers — no network call, no provider SDK, no real secret backend is required to satisfy items 1–10.
12. **Which dependencies still block actual Provider consequential dispatch even after this foundation is accepted?**
    - Network Production remains `CLOSED` (Task 136 `PASS_WITH_FINDINGS`) — no non-bypassable mediated network path/effective-destination revalidation exists yet; `TrustedUnaryProviderBroker` is explicitly simulated/admission-only and performs no I/O.
    - A concrete Provider adapter (real SDK/HTTP integration) has never been authorized; Task 137's original findings blocked identity/evidence/reconciliation semantics specifically, which Tasks 160/162/163 have now closed at the foundation level — but no Task has yet authorized or delivered an actual network-calling adapter.
    - A real secret-resolution backend (this Task's foundation only defines the seam/contract and a fail-closed stub — it does not implement or authorize a working secret store).
    - PWP `IngressRoute`/`IngressRouteRevision` (Task 142) and Runtime `ExecutionIngressFact` (Task 143) both have `SUCCESS` deliveries pending independent exact-SHA review — required only for ingress-triggered dispatch paths, not for internally-triggered Provider calls, but still open.
    - Streaming/continuation/retry-redispatch remain explicitly out of scope of every accepted Provider foundation step to date (`EIW-INV-15`, `EIW-INV-32`).

## 3. Minimum Safe Credential Identity/Reference Model (design only — not implemented by this Task)

A new, Track-D-owned, PWP-consuming (not PWP-redefining) value-object family:

- `CredentialBindingRef` — frozen dataclass: `credential_binding_ref` (own stable identity), `workspace_secret_ref` (the PWP `secret_ref` it is bound to, read-only foreign reference), `provider_profile_ref` / `profile_revision_ref` (the exact Provider profile scope it is valid for), `binding_class` (identity-only tag, e.g. `PROVIDER_API_KEY`), `revision_seq` (monotonic; rotation = new ref, never in-place mutation), `created_at`.
- `CredentialResolutionRequest` — binds one resolution attempt to one `credential_binding_ref` plus the exact `operation_ref` / `run_ref` / `attempt_seq` / `capability_grant_ref` / `resource_lease_ref` it is being resolved for, so a resolution can never be silently reused across a different Attempt/Grant/Lease context.
- `ResolvedCredentialHandle` — an explicitly opaque, non-dataclass, in-process-only object with overridden `__repr__`/`__str__` returning a constant redacted marker; never placed in any dataclass field that is persisted, hashed for identity, or compared with `==` in a way that could leak timing/content.
- `CredentialResolutionError` — fail-closed error type carrying only a machine-readable code (`CREDENTIAL_RESOLVER_NOT_CONFIGURED`, `CREDENTIAL_BINDING_UNRESOLVED`, `CREDENTIAL_BINDING_REVOKED`, ...), never the attempted value.

No field of any persisted record ever carries a secret value; the family only ever carries references, scope identity, and monotonic revision — matching the PWP substrate's own shape.

## 4. Memory / Persistence / Redaction Boundary

- **Memory**: a resolved value may exist only inside the trusted resolver/broker call stack, scoped to a single `CredentialResolutionRequest`; it must not be attached to any object that outlives that call (no caching on `RuntimeContext`, no module-level cache, no attachment to `ProviderOperation`/`Packet`/`Continuation`).
- **Persistence**: only `CredentialBindingRef`-shaped identity rows may be durable (mirrors the existing Provider/PWP schema pattern of ref/scope/bool/timestamp columns only, per §1.3).
- **Redaction**: every path capable of reaching a log, exception message, telemetry payload, evidence record, or Result/checkpoint file must pass through a redaction helper (or be structurally incapable of holding a value, via `ResolvedCredentialHandle`'s overridden `__repr__`/`__str__`) before it can be observed outside the trusted boundary. This must be tested on the failure path, not only the success path.

## 5. Rotation / Revocation / Restart Semantics Already Supported By Frozen Authority

- Rotation/revocation as "new immutable revision, old revision's historical meaning preserved" is already the accepted pattern for `EnvironmentBindingRevision`, `WorkspaceConfigRevision`, and `ProviderProfileRevision` — the credential-reference foundation reuses this pattern rather than inventing a new one.
- Restart: because the value is never durable, restart safety reduces to "resolution is re-attempted, and unavailability/misconfiguration fails closed" — no new frozen semantics are required beyond the existing fail-closed posture already used throughout the Provider/Effect foundation (e.g. `ProviderFoundationError` fail-closed codes).
