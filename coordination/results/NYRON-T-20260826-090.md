## What was implemented

`UsageLedger` (`src/nyron_kernel/accounting/usage_ledger.py`) is the sole canonical writer for two new immutable, Accounting-owned fact types:

- **`UsageFact`** — committed via `record_usage(UsageFactRequest)`. Canonical dedupe identity is the frozen candidate's `(source_authority_ref, source_fact_id, fact_kind, dimension_ref)` tuple (§11.1), deterministically hashed into `usage_fact_ref` (same pattern `BudgetAuthority` already uses for `reservation_ref`). Behavior:
  - exact duplicate identity + identical payload → idempotent, returns the existing canonical fact, never double-counts (§11.2 / §22 Case A);
  - same identity + a different `quantity`/`unit`/binding (`accounting_scope_ref`, `reservation_ref`, `operation_ref`, `resource_ref`, `run_ref`, `usage_period`, `external_evidence_ref`, `observed_at`, `caused_by_ref`) → fails closed with `USAGE_FACT_RECONCILIATION_REQUIRED`; the existing fact is left untouched, nothing is overwritten, and no latest-by-time tie-break occurs (§11.3 / §22 Case B);
  - distinct `source_fact_id`s for the same logical operation are independent identities and both persist (§22 Case C) — `operation_ref` alone is never the dedupe key;
  - `quantity` is a required, non-optional, non-negative `int` on `UsageFactRequest` — there is no code path that maps missing/unknown evidence to `quantity = 0` (§6.4 / AR-INV-10); a request literally cannot omit it (`TypeError` from the frozen dataclass) or supply a negative value (`USAGE_FACT_REQUEST_INVALID`);
  - `accounting_scope_ref` must resolve against `accounting_scopes` or the call fails closed with `USAGE_FACT_ACCOUNTING_SCOPE_UNRESOLVED`;
  - a concurrent committer racing the same dedupe identity is resolved by re-reading the row after the `UNIQUE` constraint fires, then applying the same identical-payload check — no double-insert, no lost update.
- **`UsageAdjustmentFact`** — appended via `record_adjustment(UsageAdjustmentFactRequest)`, referencing an existing `UsageFact` by `adjusts_usage_fact_ref` (§6.3 / §21.3). It has its own independent dedupe identity (same 4-tuple shape, scoped to the adjustment's own source correction event) with the same idempotent-duplicate / fail-closed-conflict behavior as `UsageFact`. The original `UsageFact` is never mutated by an adjustment; corrections are strictly append-only. An adjustment targeting an unresolved `usage_fact_ref` fails closed with `USAGE_ADJUSTMENT_TARGET_UNRESOLVED`.

Both row types are additionally protected at the SQLite layer: `create_usage_ledger_schema()` adds `usage_facts` and `usage_adjustment_facts` with `BEFORE UPDATE` triggers that `RAISE(ABORT, ...)` on any update attempt, so immutability holds even against a caller that bypasses the Python API.

`src/nyron_kernel/accounting/__init__.py` exports the new public names (`UsageLedger`, `UsageLedgerError`, `UsageFact`, `UsageFactRequest`, `UsageAdjustmentFact`, `UsageAdjustmentFactRequest`) alongside the existing `BudgetAuthority` exports.

- **No `BudgetReservation` transition, no exposure conversion.** `UsageLedger` never imports `BudgetAuthority`, never opens a `store.transaction()` touching `budget_reservations` / `budget_scope_exposure` / `budget_policy_revisions`, and `budget_authority.py` is untouched (confirmed absent from the diff). `reservation_ref` on `UsageFact` is stored only as an optional, unenforced-by-FK cross-reference for later traceability — recording usage evidence never mutates reservation state.
- **No Recovery Owner `ReconciliationCase`.** The frozen candidate's §11.3 / §22 Case B literally says a conflicting duplicate should "open a ReconciliationCase with both evidence records" and "mark affected reservation settlement RECONCILING when required" — but the Task's Required Semantics and Explicit Non-Goals narrow this for the current slice: surface a machine-readable conflict outcome, do not create/mutate cross-owner Recovery state, and do not invent a new public cross-owner contract to make the conflict path convenient. This implementation follows the Task's narrower instruction: `USAGE_FACT_RECONCILIATION_REQUIRED` / `USAGE_ADJUSTMENT_RECONCILIATION_REQUIRED` are raised as a typed, machine-readable `UsageLedgerError` (code + context) — a purely Accounting-local, in-process signal a caller can act on — with no direct write into any Recovery-owned table and no new cross-owner interface introduced.
- **No `EffectOperation` / `ResourceLease` mutation, no Runtime/Effect/Resource/Capability/Host change.** `operation_ref` / `resource_ref` / `run_ref` on `UsageFact` are optional plain `TEXT` columns with no `FOREIGN KEY` into `effect_operations` / `resources` / `run_attempts`, specifically to avoid coupling this Accounting-local ledger to those Owners' schemas or semantics, consistent with the Task's Explicit Non-Goals.
- **No provider billing / pricing / currency / rolling-window policy.** Out of scope per Task; not implemented.
