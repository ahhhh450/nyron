## What Was Wrong

`publish_policy_revision()` only performed per-revision shape validation (`_validate_revision`) — it never checked a new revision's `supersedes_ref`/`effective_from`/`effective_until` against the rest of the same-scope stored history. `reserve()`'s per-scope "current policy" lookup was:

```sql
SELECT * FROM budget_policy_revisions
WHERE accounting_scope_ref = ? AND effective_from <= ? AND (effective_until IS NULL OR effective_until > ?)
ORDER BY effective_from DESC, budget_policy_revision_ref DESC
LIMIT 1
```

— a lexical/row-order tie-break that could silently pick one revision out of an ambiguous, branched, disconnected, or overlapping same-scope history instead of failing closed, and provided no genesis/successor/linear-chain/strict-ordering enforcement at all.

## Fix

### Publication (`publish_policy_revision`)

Added `_validate_chain_linkage(connection, revision)`, called inside the same transaction as the insert (after existing shape validation and the identical-content idempotency check, both unchanged). Resolves the current validated same-scope chain via a new shared `_resolve_chain(connection, accounting_scope_ref)` and requires exactly one of:

- **Genesis** (chain currently empty): `supersedes_ref` must be absent, else `BUDGET_POLICY_REVISION_GENESIS_SUPERSEDES_FORBIDDEN`.
- **Successor** (chain non-empty): `supersedes_ref` must be present (`BUDGET_POLICY_REVISION_SUPERSEDES_REQUIRED` otherwise); the named target must exist (`_SUPERSESSION_TARGET_UNRESOLVED`), be in the same scope (`_SUPERSESSION_CROSS_SCOPE`), and be the exact unique current tip (`_SUPERSESSION_NOT_TIP` — this single check structurally also rejects self-supersession, branching off a non-tip/already-superseded revision, and any attempt to create a second alternate branch); `effective_from` must strictly exceed the tip's (`_EFFECTIVE_FROM_NOT_INCREASING` — also covers equal-effective rejection); and if the tip has an explicit `effective_until`, it must be `<=` the successor's `effective_from` (`_PREDECESSOR_OVERLAP` otherwise; a gap, `predecessor.effective_until < successor.effective_from`, is explicitly permitted).

Because every successor must name the exact unique tip, cycles/branches/cross-scope histories cannot be created through any valid publication path (Clarification-003 SS2/SS3), and pre-publishing multiple future successors (SS6) falls out of the same rule with no special-casing: each new future revision simply becomes the new tip that the next one must supersede.

### Current Selection (`reserve()`, replacing `_current_policy_revision`)

New `_select_current_policy_revision(connection, accounting_scope_ref, now)`:

1. Resolves the same shared validated chain via `_resolve_chain`. An **empty chain** (no published history at all for that scope) returns `None` — the scope contributes no local rule, but ancestor `HARD` rules remain fully enforced (unchanged cumulative-ancestor loop in `reserve()`).
2. For a **non-empty chain**, computes each revision's half-open `[effective_from, logical_effective_until)` interval — explicit `effective_until` if present, else the direct successor's `effective_from`, else open — and collects every revision applicable at `now`.
3. Exactly one applicable revision is returned and used. **Zero or more than one** applicable revision raises `POLICY_NOT_RESOLVABLE` and fails the *entire* new authorization closed (not just that one scope) — this is the Clarification-003 SS7 distinction between "no history" (silently contributes nothing) and "has history but nothing resolves right now" (hard fail).

`_resolve_chain` itself is the single shared source of "is this stored history a valid unambiguous linear chain" for both publish-time tip lookup and reserve-time selection (Clarification-003 SS8): it fails closed with `POLICY_NOT_RESOLVABLE` on zero/multiple genesis rows, a branch (a revision superseded by more than one row), a cycle, a disconnected row (unreachable from the single genesis by valid links), a non-increasing `effective_from` step, or a predecessor/successor overlap — never repairing or guessing, never tie-breaking on ref/row/arrival order. Since `publish_policy_revision` now enforces these invariants on every insert, a malformed stored chain can in practice only arise from data inserted outside the public API (verified by a dedicated test that does exactly that); `_resolve_chain` still fails closed on it rather than assuming publish-time validation is airtight.

Existing-request replay in `reserve()` is structurally unaffected: it still returns the exact already-stored/pinned reservation via the pre-existing `_load_reservation_by_request_ref` + `_require_identical_replay` early return, before `_select_current_policy_revision` is ever reached, so it never performs a new policy selection (Clarification-003 SS9) and historical `policy_revision_refs` are never rewritten by later publication (verified by both the pre-existing pinning tests and a new multi-hop-chain-growth test).
