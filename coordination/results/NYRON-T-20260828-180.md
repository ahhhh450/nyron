## 3. Product Node Contract Sketch (Analysis A)

**A1 — Product inputs/outputs.** A single text prompt input port and a single text response output port, mirroring the existing `builtin.mock.llm_echo@1` / `product.mock_llm` precedent (`{"prompt": str} -> {"text": str}`).

**A2 — Compiles to which ModuleDefinition/ModuleInstanceRevision?** Exactly the existing pattern: a real `ModuleDefinition` declaring `effect_classes` that include a new non-`PURE` class (see §3, A4/Finding 005) and `required_capability_types=("NETWORK_ACCESS",)`-shaped entry, bound 1:1 by a `ProductNodeDefinition` via `bound_module_ref@bound_module_version` — no new Product-layer type is required; `src/nyron_kernel/product/node_definition.py` already has the exact shape (`ProductNodeDefinition`, frozen, `bound_module_ref`/`bound_module_version` pinned, port bindings alias Module ports by name, `product_config_schema` may only narrow the Module's own `config_schema`).

**A3 — Immutable Product config vs host-owned Provider/Credential authority.** Already enforced today: `ProductNodeRegistry._validate_config_narrowing` (`src/nyron_kernel/product/node_definition.py`) rejects any Product config schema that is not a strict subset of the bound Module's own `config_schema` (`PRODUCT_CONFIG_WIDENS_MODULE_AUTHORITY`). A provider/model identity field placed in Product config is therefore safe **only if** the underlying Module's own `config_schema` already declares that exact field as a non-secret string reference (e.g. `provider_profile_ref`, `model_ref`) — Product can then expose/narrow it, never invent it. Today **no such field exists anywhere** (confirmed: no `provider_ref`/`model_ref`-shaped field in `ProductNodeDefinition` or any registered `ModuleDefinition`).

**A4 — Representing provider/model selection without becoming a CapabilityGrant or credential authority.** Non-secret **binding identity only** (a `profile_ref`/`profile_revision_ref`-shaped string, matching the already-accepted `ProviderProfileRevision` identity model in `src/nyron_kernel/host/provider/models.py`), never a `ResolvedCredentialHandle`, never a live client/session object. This is exactly the separation the accepted Provider and Credential foundations already enforce end-to-end (Provider operations bind a `profile_revision_ref`; credential resolution requests are separately bound to `capability_grant_ref`/`resource_lease_ref`/`attempt_seq` — Product config never needs to carry any of that; it only needs to name the profile).

**A5 — Version/ref pinning for restart/replay/reproducibility.** Reuse the existing pattern exactly: `bound_module_ref@bound_module_version` (Module) + `product_node_type_ref@product_node_version` (Product node) + a new immutable `provider_profile_ref@profile_revision_ref` reference (Provider). All three are already modeled as exact, non-`latest` pinned identities in their respective accepted foundations; `VisualWorkflowRevision`'s existing predecessor/replay/conflict semantics (`src/nyron_kernel/product/workflow.py`) require no change to carry a fourth pinned reference.

## 4. Runtime Execution Seam (Analysis B)

Traced call path: `AttemptExecutor.execute` (`src/nyron_kernel/execution/executor.py`) → `TrustedModuleHost.execute(module_ref_version, inputs, config, runtime_context=None)` (`src/nyron_kernel/host/trusted_host.py`) → direct in-process call into one of 4 hardcoded `_TRUSTED_IMPLEMENTATIONS`, all declaring `effect_classes=("PURE",)`.

**A seam for a Module to request a host-mediated external effect already exists in code**: `RuntimeContext` (frozen dataclass carrying `capability_handles`, `resource_handles`, `effect_broker: BoundedWriteEffectBroker | None`) and `BoundedWriteEffectBroker.dispatch_bounded_write(...)`, which forwards to `EffectAuthority.execute(EffectRequest(...))` (`src/nyron_kernel/effect/authority.py`). Its own ABI comment states Module code never receives the StateStore/SQLite/filesystem/network/capability objects directly — only opaque handles and, if constructed, the broker.

**But it is dead code at the Product base**: the sole production call site, `AttemptExecutor.execute`, **always** passes `runtime_context=None`. No code anywhere constructs a non-`None` `RuntimeContext`. No registered Module declares a non-`PURE` `effect_classes`. The seam is architecturally present and was clearly designed for exactly this purpose, but nothing in the accepted Product base exercises it.

**Additional boundary fact directly relevant to a real Provider-calling Module**: `TrustedModuleHost`'s isolation posture (`TRUSTED_SAME_PROCESS_ISOLATION_PROFILE`, `src/nyron_kernel/host/isolation_profile.py`) self-declares `network_enforcement_claim = BoundaryEnforcementClaim.UNRESTRICTED` and `raw_os_api_access_claim = RawOSAPIAccessClaim.UNRESTRICTED`. In-process trusted Module code today has no OS-level sandboxing preventing it from bypassing any future broker/seam entirely — the entire safety story rests on no Module ever being granted network-capable effect declarations, not on enforced isolation. This is the exact shape of the already-open, already-accepted `NYRON-T-20260827-136-F01` finding (see §6) and is directly load-bearing for whether a real LLM Module can be trusted to only reach the network through the mediated seam.

**Conclusion:** the seam exists but is not wired (`missing bounded implementation`, not an architecture blocker — see §7).

## 6. Credential Boundary (Analysis D)

- **What Product config may reference:** a non-secret `provider_profile_ref`/`profile_revision_ref`-shaped binding identity only (§3, A4) — never a credential binding ref, never a resolved handle.
- **Where `ResolvedCredentialHandle` may legally exist:** exclusively inside `src/nyron_kernel/host/credential/foundation.py`. Construction is gated by a private module-level sentinel (`issuer is _HANDLE_ISSUER`) so only the module-private `_issue_resolved_credential()` factory can create one; consumption is one-shot via `_use_once(consumer, _HANDLE_CONSUMER)`, after which the material is zeroed in a `finally` block. `__slots__` (no `__dict__`), constant-redacted `__repr__`/`__str__`, and a `__reduce__` that raises on any pickle attempt jointly prevent introspection/serialization leakage.
- **Which layer may turn a binding identity into a resolved handle:** only `CredentialResolutionAuthority.use_resolved()`, which itself delegates issuance to an injected `CredentialResolver` and never sees or returns raw material — the production default (`UnconfiguredCredentialResolver`) unconditionally fails closed with `CREDENTIAL_RESOLVER_NOT_CONFIGURED` and has no environment/config/keychain/network fallback.
- **Full-tree reference audit:** every reference to `ResolvedCredentialHandle` at `276432c1...` was enumerated by `git grep`. All real-class references are confined to `host/credential/foundation.py` plus its own `__init__.py`/`host/__init__.py` re-exports. The only reference outside that boundary is a **locally-defined dummy class of the same name** inside `tests/kernel/test_network_foundation.py`, used specifically to prove the Network foundation's `__post_init__` type checks reject a credential-shaped object (`NetworkBoundaryError`) rather than silently accepting it — this is a negative test, not a real leak.
- **Authority orthogonality:** `CredentialRepository` only issues `INSERT`s against its own three tables; it never `UPDATE`s `capability_grants`, `resource_leases`, `run_attempts`, or `effect_operations`. Directly proven by `test_success_does_not_mutate_or_substitute_authority`, which snapshots all five authority tables before/after a successful resolution and asserts byte-identical state, and further shows a later Grant revocation does not retroactively invalidate an already-completed resolution.

**Conclusion: the standing invariant ("`ResolvedCredentialHandle` must never cross into low-trust plugin/module/network-facing code") holds with zero violations found in the current accepted code**, and the credential foundation's own design already gives a real Module-facing seam nothing to leak — no code path anywhere near Module/Product/Network models is even capable of accepting the type.

## 8. Accounting (Analysis F)

`AccountingScope` (`src/nyron_kernel/accounting/scope_resolver.py`) binds to `graph_revision_ref` + `definition_anchor_ref` with a parent-linked, SHA-256-verified ancestry chain; `AttemptAuthority`'s fencing tuple (`execution_ref, activation_ref, run_ref, attempt_seq, fencing_token, fencing_generation`) is independent of it. `UsageFact` (`src/nyron_kernel/accounting/usage_ledger.py`) is a **generic** dimension/quantity/unit ledger entry (`dimension_ref`, `quantity`, `unit`, `fact_kind`, plus dedup key `(source_authority_ref, source_fact_id, fact_kind, dimension_ref)`) with no Provider-specific fields hard-coded.

No new accounting/billing framework is required or justified by current evidence; do not build one speculatively.

## 9. Mandatory Boundary Questions

1. **Can a real LLM Product Node be implemented truthfully today without opening any new Track D Production work?** — **NO.** The Provider/Credential/Network foundations aren't even merged into the Product-usable tree (§1.3); even once merged they are admission/identity-only with zero real dispatch (§5, §7); the Runtime execution seam that would let a Module reach them is unwired dead code (§4); no Module has ever been granted a non-`PURE` effect class; `TrustedModuleHost`'s isolation claim is `UNRESTRICTED` (§4, §7).
2. **Can current Provider code perform real dispatch today?** — **NO.** `TrustedUnaryProviderBroker.admit_simulated_dispatch()` is explicitly simulated (`simulated: bool = True`); zero SDK/HTTP/socket code exists anywhere in the tree (§5).
3. **Is the accepted Network admission broker sufficient by itself to make real network I/O truthful?** — **NO.** It is simulated-only, never checks `effect_class`, reads authority tables directly instead of through the real Capability/Resource/Effect APIs, and Task-136 F01 (raw bypass) and F03 (no network Effect/historical-outcome model) remain OPEN (§7).
4. **Is there already a non-bypassable host dispatch seam immediately before real transport?** — **NO.** No such seam exists yet; the only real invocation chokepoint (`TrustedModuleHost.execute`) has no path to the Network broker, and its isolation profile self-declares `UNRESTRICTED` (§4, §7).
5. **Can Product config safely name a provider/model without owning credentials or capability authority?** — **YES, conditionally.** The existing `PRODUCT_CONFIG_WIDENS_MODULE_AUTHORITY` guard (§3, A3) already makes this safe *in principle*, but only once the underlying Module's own `config_schema` declares a non-secret profile-reference field — that field does not exist yet anywhere in the accepted code and must be added as bounded, non-speculative Module/Product schema work.
6. **Can credential resolution remain entirely host-side?** — **YES.** Zero violations found; `ResolvedCredentialHandle` never crosses out of `host/credential/foundation.py` in the current accepted tree (§6).
7. **Can the first slice remain non-streaming without violating frozen contracts?** — **YES.** `streaming` is an optional boolean capability claim on `ProviderProfileRevision`, never mandatory; Task 171's own precedent already scoped "no streaming semantics" without contradiction.
8. **Can retry remain disabled/absent in the first slice?** — **YES, and must.** No retry/redispatch code exists anywhere; Amendment 001 (`FENCED != retry clearance`, `EIW-INV-32`) and every foundation Task (160/165/168) explicitly forbid inventing retry/redispatch clearance.
9. **Does the first slice require Human, Browser or Filesystem support?** — **NO.** The narrowed slice (single prompt/response, no tool calling, no multimodal, no side effects) needs none of them; the existing `EffectAuthority.EFFECT_CLASS` (filesystem-bounded-write) is irrelevant to a Provider call and does not need to be reused or extended for this purpose.
10. **Does any required gap cross a frozen owner boundary that lacks an accepted contract?** — **NO confirmed instance, with one explicitly flagged open verification item.** Every gap found in this analysis (integration merge, Runtime-seam wiring, Provider-class Effect support, real transport/adapter) is bounded implementation work against **already-accepted** contracts (Effect/Capability/Resource/Attempt/Provider/Credential/Network foundations all already exist and are Director-accepted). The one item this Task could **not** fully verify: whether `EffectAuthority.EFFECT_CLASS` (currently a single hardcoded filesystem-only class constant, not a registry) can accept a second `MODEL_INVOKE`-class Effect without a new Effect-owner frozen-authority amendment — this Task read the Fenced-Retry amendment in full but did not read the complete D-008 baseline text verbatim. Recommend the first bounded Effect/Runtime support task (§10, Task 3) explicitly re-confirm this against frozen authority before writing code — see Finding 005.
