## 2. Answers To The Required Review Questions

1. **Durable requested-destination identity**: scheme/protocol, canonical (IDNA-normalized, label-bounded) host identity, normalized effective port, registered operation class, and any endpoint/path restriction the Capability scope uses — captured as one immutable value object *before* resolution, per Task 136 §1.
2. **Effective-destination identity at connection time**: hostname, the exact resolved IP actually selected (not the full DNS answer set), port, scheme/protocol, proxy hop (if any, explicit only), redirect target (if any, itself a full new requested-destination), and a stable connection/session identity — per Task 136 §2–§4.
3. **Which identities must independently satisfy Capability/Policy scope**: all of them — requested host, the specific selected peer IP, every redirect target, and any proxy endpoint — each independently, per Task 136 §3–§5 and `EIW-INV-11`/`EIW-INV-18`. Authorizing the hostname never authorizes the resolved IP, a redirect target, or a proxy target by inheritance.
4. **Fail-closed range rules**: deny by default unless explicitly scoped — IPv4/IPv6 loopback, RFC1918/IPv6 ULA private ranges, link-local, unspecified, multicast, reserved/special-use ranges, and IPv4-mapped-IPv6 encodings of an otherwise-denied IPv4 address (normalize before classifying, never classify the outer representation alone) — per Task 136 §2 and adversarial cases N01–N06.
5. **DNS re-resolution/rebinding**: the validated candidate must be pinned and used directly for connection; the hostname must never be handed back to a lower client free to re-resolve it. A still-open reused connection keeps its already-verified peer as the effective IP, but authority/policy currency must still be rechecked each use; any profile requiring DNS-answer freshness must define its own explicit TTL/re-resolution rule — per Task 136 §2, §6 and cases N07–N09.
6. **Redirects**: yes — every redirect hop is a brand-new requested-destination decision, fully reparsed and reauthorized from scratch (new scheme/host/port/resolved-IP/peer), with a bounded hop count and default-deny cross-origin credential forwarding — per Task 136 §4 and cases N10–N13.
7. **Proxy behavior**: no implicit environment/system proxy may ever be honored — proxy use must be an explicit adapter/profile declaration. Even then, the proxy-hop authorization and the ultimate effective-destination authorization are two independent questions; allowing the proxy never widens the target's authorization — per Task 136 §5 and cases N14–N16.
8. **Pooled/keepalive reuse**: before each dispatch on a reused connection, current Attempt/fencing and the applicable `CapabilityGrant` must be rechecked exactly as for a new connection; a connection opened under a replaced Attempt or a revoked/expired Grant is not reusable merely because the socket is open; HTTP/2-/3-style origin coalescing must independently authorize each logical origin rather than inheriting the first — per Task 136 §6 and cases N21–N24.
9. **PREPARED before boundary**: any consequential/crash-ambiguous outbound network operation needs a durably `PREPARED` Effect (or equivalent operation-identity record) before the first externally relevant dispatch — mirroring exactly the pattern already accepted for Provider (`ProviderRepository.prepare()` inserts before any `admit_simulated_dispatch()` call) — per Task 136 §8 and `EIW-INV-32`.
10. **Credential resolution stays orthogonal to network authority**: destination/Capability/Attempt/fencing admission must be decided and pass *before* any credential is resolved or attached; a credential must never be used to infer or widen destination authorization (`EIW-INV-19`); and — per the delta in §1.3 above — the future Network broker must call `CredentialResolutionAuthority.use_resolved()` inline at the point of actual use and must never hold, store, log, or pass onward a `ResolvedCredentialHandle`, per the standing `166-F-001` invariant.
11. **Durable evidence after connect/timeout/disconnect**: Nyron semantic operation identity, external request/operation identity, idempotency key + its protocol semantics, requested destination, approved effective destination/dispatch evidence, acknowledgement/response evidence, cancellation evidence, and historical-outcome classification. Timeout/disconnect after a possibly-dispatched request yields `UNKNOWN` unless authoritative evidence proves a terminal outcome; a local socket close is only a cancellation/transport action and is never by itself proof of `FENCED`, non-dispatch, or no-consequence — per Task 136 §8, `EIW-INV-13`/`EIW-INV-14`/`EIW-INV-32`.
12. **Can the next foundation stay socket-free?** Yes, for identity + admission + effective-peer-validation. IP/CIDR classification, hostname canonicalization, redirect-target reparsing, and the boundary-time admission recheck (mirroring Provider's simulated broker) are all pure functions/state-machine logic over caller-supplied strings/records — no live DNS query or socket is needed to prove any of these invariants; tests can supply literal "as-if-resolved" IP strings exactly as Task 136's adversarial matrix (N01–N09) already assumes. A real socket/loopback probe is **not** required for this slice and is explicitly **not** part of the bounded implementation authorized here. A real transport is required only to close `F01` (truthful non-bypassable enforcement) and to run any live consequential dispatch — both remain out of scope.
13. **Remaining dependencies after this foundation**: `F01` (non-bypassable mediated network path / truthful IsolationProfile — requires either real broker-mediated egress or an OS/process isolation mechanism, neither of which this session may design or implement); `F03`'s full consequential-dispatch closure (a real, non-simulated network Effect class integrated with Recovery, exercised against a live or faithfully-emulated transport); a concrete Provider/HTTP adapter (never authorized); a real secret-resolution backend (Credential foundation explicitly ships only `UnconfiguredCredentialResolver`); and PWP `IngressRoute`/Runtime `ExecutionIngressFact` (Tasks 142/143, `SUCCESS` pending independent review) for any ingress-triggered path.
