R1/R2 canonical identity defined as that full tuple; `execution_ref`/`activation_ref`/`run_ref` identical between R1/R2, `attempt_seq`/`fencing_token`/`fencing_generation` are the discriminating fields, with `(run_ref, attempt_seq)` the minimal sufficient pair (new plan section A).
- **B (Gate-4B discovery):** Corrected to `WHERE run_ref = R AND attempt_seq = S1 AND state IN (...)` for both `effect_operations` and `resource_leases`, with an explicit proof it selects only R1, cannot select R2 (different `attempt_seq`), and cannot select another Activation/Run (different `run_ref`) (plan section D). No schema/index change required for the current bounded scale; an additive index is noted as optional future work only, not recommended now.
- **C (Gate-4C barrier):** The `run_ref` predicate is removed entirely. Corrected rule: `resource_ref = R2.resource_ref AND state IN ('PREPARED','ACTIVE','REVOKE_REQUESTED','UNKNOWN') AND operation_ref != R2.operation_ref` (plan section E) — exactly the minimal form the Task suggested, confirmed and proved rather than assumed. `FENCED`/`COMPLETED` remain non-blocking; `FENCED != semantic retry clearance` restated explicitly.
- **D (same-Run/same-Attempt overlap):** Resolved, not deferred. All three cases — stale R1 vs. current R2, another operation within R2's own Attempt, another Run/Activation on the same Resource — resolve uniformly under the corrected barrier with no exemption for any of them, justified from Frozen D-004/Clarification 003's resource/scope-centric (not Attempt-centric) conflict framing, which is definitive enough to answer all three without an Architecture Finding.
- **E (trigger precision):** Restated. Storage triggers can prove monotonicity, paired increment (`current_attempt_seq`/`fencing_generation` change together and by the same delta), legal state transition, and no reactivation/rollback — they cannot prove which Python function issued a write. The plan no longer claims a trigger can guarantee "only `replace_attempt()`" can write.
