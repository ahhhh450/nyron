## Findings

### `NYRON-T-20260828-161-F-001`

- Type: `SECURITY / IMPLEMENTATION`
- Severity: `BLOCKING`
- Location: `src/nyron_kernel/store/sqlite_store.py:1138`; `src/nyron_kernel/host/provider/authority.py:43-64`.
- Evidence: protected-key uniqueness is `(profile_revision_ref, usage_source_namespace, idempotency_key)`. An independent probe prepared operation 1 under `provider-profile:test@1`, registered `provider-profile:test@2` with the same provider/account/endpoint/model scopes and usage namespace, then prepared operation 2 with the same `idem:1`; the candidate accepted it and printed `CROSS_REVISION_KEY_REUSE_ACCEPTED effect:provider/2 idem:1`.
- Impact: rotating or revising a profile silently resets the protected idempotency namespace. A different semantic operation can reuse the same provider-scoped key and collide with or be mistaken for the earlier external consequence, defeating the required cross-operation fail-closed guarantee.
- Required Resolution: bind protected-key uniqueness to the declared provider/account/endpoint/model/idempotency namespace independently of profile revision, while retaining exact profile revision in operation identity. Add cross-revision and same/different-scope adversarial tests.

### `NYRON-T-20260828-161-F-002`

- Type: `CONTRACT / SECURITY`
- Severity: `BLOCKING`
- Location: `src/nyron_kernel/host/provider/authority.py:86-122`.
- Evidence: `record_evidence` accepts caller-selected `evidence_semantics`, `authoritative`, and `historical_outcome`. It only forces `UNKNOWN` for a few negative lookup/cancel cases; an `ACKNOWLEDGEMENT` with arbitrary semantics, `authoritative=True`, and `historical_outcome="KNOWN"` is accepted without a profile claim or evidence-kind/semantics rule proving completion/no-consequence. Independent probe output: `UNSCOPED_AUTHORITATIVE_KNOWN_ACCEPTED KNOWN arbitrary-string`.
- Impact: syntactic authority can incorrectly promote ambiguous history to `KNOWN`. Later code can treat unproved evidence as terminal Provider history, violating `UNKNOWN/PARTIAL -> KNOWN` evidence requirements and creating a false basis for accounting closure or future policy decisions.
- Required Resolution: make historical-outcome derivation owner-local and fail-closed from an explicit profile-bound evidence semantics matrix. Callers must not freely choose `KNOWN`; each accepted terminal outcome must require the exact supported claim and sufficient evidence, preserving prior partial consequence where applicable. Add negative ACK/lookup/cancel semantics probes.

### `NYRON-T-20260828-161-F-003`

- Type: `CONTRACT / ACCOUNTING`
- Severity: `BLOCKING`
- Location: `src/nyron_kernel/accounting/settlement_authority.py:212-234,302`; Provider reconciliation UsageFact binding.
- Evidence: for a `RECONCILING` reservation, settlement verifies only that each UsageFact has the reconciliation's `source_authority_ref` namespace and `operation_ref`. It does not verify that the `source_fact_id` was derived from the Provider operation's stable line-item identity or that the zero fact is authoritative frozen no-usage evidence. An independent probe inserted a caller-chosen zero UsageFact under the namespace and operation, then settlement returned `UNKNOWN_RELEASED_BY_ARBITRARY_ZERO_FACT RELEASED`.
- Impact: `UNKNOWN/PARTIAL` billable exposure can be released as zero using an unattributed or fabricated zero fact. This violates `UNKNOWN != zero`, makes `RECONCILING -> RELEASED` possible without explicit frozen evidence, and allows usage-source mismatch at the line-item/evidence level despite matching the broad namespace.
- Required Resolution: require immutable Provider-generated/validated usage-source binding for every reconciliation fact and a distinct explicit authoritative no-usage/no-charge evidence path before `RELEASED`. Ordinary zero-quantity UsageFact presence must not by itself close ambiguity. Preserve reconciliation exposure until that proof or known actual usage exists; add forged-source, conflicting-line-item, multiple-fact, restart, and explicit-release probes.
