Findings:

- Finding ID: NYRON-T-20260825-038-F-001
  Type: SECURITY
  Severity: NON_BLOCKING
  Location: src/nyron_kernel/resource/manager.py, ResourceManager.recover() PROVISIONING branch (`path.mkdir()` followed by `self._write_exclusive_json(path / self._RESOURCE_MARKER, ...)`)
  Evidence: Between the successful `path.mkdir()` call and the subsequent `open(path/marker, "x")` marker write, there is a real (if extremely narrow) TOCTOU window: a co-resident process with concurrent write access to the exact managed root could `rmdir()` the just-created empty directory and replace it with a symlink to an attacker-chosen target before the marker write executes, causing the marker file (and, once state flips to AVAILABLE, subsequent access via `resource.external_ref`) to resolve into the attacker's directory instead of the isolated managed one. I attempted to empirically reproduce this with a monkeypatch-based race simulation but could not create a real symlink in this Windows review sandbox (`os.symlink` requires elevated privilege there); the finding rests on code-reading analysis of the mkdir/open sequence, which I verified is accurate for POSIX semantics (mkdir fails closed with EEXIST if the target name is already taken by anything, including a symlink placed *before* mkdir runs — that case is safe; the narrow gap is specifically the window *after* our own mkdir succeeds and *before* our own marker write). By contrast, I independently verified (via `inspect.getsource(shutil.rmtree)`) that the DESTROYING/`shutil.rmtree` path is NOT vulnerable to the equivalent race: CPython's `rmtree` explicitly refuses to operate on a top-level symlink ("Cannot call rmtree on a symbolic link", the historical bug #1669 fix), and the code's own `_directory_evidence()` also checks `path.is_symlink()` immediately beforehand — this is correctly hardened.
  Impact: Exploitation requires an attacker who already has concurrent local write access to the Resource-Manager-owned root — a threat model explicitly out of scope for this gate (Module Host hostile-plugin/multi-tenant isolation is deferred to future ARE-GATE-5 per D-004 §15, and Task 037 explicitly excludes "hostile-plugin sandbox" and "Module filesystem read/write APIs"). Even a successful exploit today only plants one fixed-schema, non-overwriting (`"x"` mode) JSON marker file in the attacker's directory — there is currently no code path in this Task that performs Module-driven read/write through `resource.external_ref`, so there is no present confidentiality/integrity consequence. This becomes consequential once a later gate wires real file I/O through the Resource handle.
  Required Resolution: Non-blocking for this Kernel-foundation gate. Recommend hardening the provisioning create path (e.g., `os.open(..., O_NOFOLLOW)` or dir-fd/`openat`-relative operations for both the `mkdir` and the marker write) before ARE-GATE-5 Module Host trust-boundary work or any deployment where the managed root could be concurrently writable by a less-trusted co-resident process.
