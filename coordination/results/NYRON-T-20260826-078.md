## 3. Schema Constraints / Triggers

- `PRAGMA foreign_keys = ON` is set at connection open; all new FKs are enforceable and reference valid PK/UNIQUE targets (`accounting_scopes(accounting_scope_ref)` PK; `run_attempts(run_ref, attempt_seq)` PK; self-referential `supersedes_ref`).
- `budget_policy_revision_immutable` (BEFORE UPDATE) blocks every UPDATE of a revision row. VERIFIED by probe: raw `UPDATE` → `IntegrityError`.
- `budget_reservation_identity_immutable` protects all persisted identity/binding/pinning columns including `graph_revision_ref`, `definition_anchor_ref`, `ancestry_snapshot_json`, `policy_revision_refs_json`. VERIFIED by probe: raw identity UPDATE → `IntegrityError`.
- `budget_reservation_state_transition` matches the design-candidate §7.3 lifecycle exactly (REQUESTED→RESERVED/DENIED; RESERVED→COMMITTED/RELEASED/RECONCILING; RELEASED/COMMITTED→RECONCILING→COMMITTED/RELEASED; same-state no-op) and makes **DENIED terminal** — no out-transition, including no RESERVED→DENIED retroactive path (verified by probe: rejected). Consistent with "DENIED never auto-revives".
- `CHECK (state='DENIED' AND deny_reason_code IS NOT NULL) OR (state!='DENIED' AND deny_reason_code IS NULL)` ties deny state to its reason at DB level.
- `budget_scope_exposure` has `CHECK (reserved_amount >= 0)` / `CHECK (committed_amount >= 0)`.

**Gap (new, NON_BLOCKING):** immutability is enforced for UPDATE only. There is **no DELETE guard** on `budget_policy_revisions` or `budget_reservations` (PROBE-E3: raw DELETE of a non-superseding policy revision succeeds; `supersedes_ref` FK blocks deleting only a revision another revision supersedes, and reservation pins in `policy_revision_refs_json` are plain JSON with no FK protection). No production code path deletes, so no current-version trigger; but historical reservation-basis preservation is not schema-guaranteed against raw/future writers. See finding `078-F-001`.

## 4. Replay Identity Completeness (every persisted immutable request field)

Persisted identity-immutable request-derived columns: `request_ref, activation_ref, run_ref, attempt_seq, accounting_scope_ref, graph_revision_ref, definition_anchor_ref, estimate_ref, requested_dimensions_json, subject_refs_json, caused_by_ref`.

`_require_identical_replay` compares: `activation_ref, run_ref, attempt_seq, accounting_scope_ref, estimate_ref, requested_dimensions, subject_refs, caused_by_ref`.

**`graph_revision_ref` and `definition_anchor_ref` are omitted** — and, at this audited SHA, the `BudgetReservation` dataclass does not even carry those two fields, so the comparison cannot see them. A same-`request_ref` replay that changes only these two static-binding inputs silently returns the existing row instead of `RESERVATION_REQUEST_CONFLICT`.

This is **exactly known finding `NYRON-T-20260826-074-F-001`**, whose Task-076 correction (`6348f5ef`, "Closes NYRON-T-20260826-074-F-001") adds the two fields to the dataclass and to the comparison plus 6 tests. Reported here as independent mechanical confirmation only (see §6), not as a new finding.

**Additional nuance (new, NON_BLOCKING):** replay identity compares `requested_dimensions` as an order-sensitive tuple, while evaluation treats dimensions as an unordered mapping (`dict(request.reserved_dimensions)`). A semantically identical replay with reordered `(dimension, amount)` pairs raises `RESERVATION_REQUEST_CONFLICT` instead of returning the same canonical row. Fail-closed direction (no double-reserve), but inconsistent with §B "identical semantic request → same canonical reservation". See finding `078-F-002`.

## 13. New Findings

### `NYRON-T-20260826-078-F-001`

- Type: `IMPLEMENTATION`
- Severity: `NON_BLOCKING`
- Problem: schema immutability guards cover UPDATE only; no DELETE guard on `budget_policy_revisions`/`budget_reservations`, and reservation policy pins are JSON text with no FK protection. Probe confirmed raw DELETE of a non-superseded policy revision succeeds.
- Impact: historical reservation basis is protected only by code discipline; a raw or future writer could remove pinned revisions or reservation history.
- Suggested disposition: add BEFORE DELETE guards (RAISE) on both tables, or explicit policy; owner-local, no cross-owner impact.

### `NYRON-T-20260826-078-F-002`

- Type: `IMPLEMENTATION`
- Severity: `NON_BLOCKING`
- Problem: replay identity is order-sensitive for `reserved_dimensions` (tuple equality) while evaluation treats dimensions as an unordered map; semantically identical reordered replay raises `RESERVATION_REQUEST_CONFLICT`.
- Impact: fail-closed false conflict (no double-reserve risk); inconsistent with §B idempotency wording for reordered input; callers must keep stable tuple order.
- Suggested disposition: normalize dimension pairs to a canonical sorted order before comparison/persistence, or document order significance explicitly.

### `NYRON-T-20260826-078-F-003`

- Type: `TEST`
- Severity: `NON_BLOCKING`
- Problem: request/policy validation branches implemented but untested: duplicate request dimension rejection, zero-amount pairs, empty `reserved_dimensions`, empty `subject_refs`, policy `limit_amount == 0`.
- Impact: validation behavior is not pinned by tests; future edits could silently relax or break fail-closed checks.
- Suggested disposition: add focused negative tests for each branch (correction Task or later slice).
