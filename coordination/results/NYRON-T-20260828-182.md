## 2. Required Questions — Answered With Exact Frozen-Document Evidence

### Q1 — Is Effect authority defined as a generic effect-class mechanism that already permits multiple independently named effect classes?

**YES.**

- `design/Nyron_Capability_Resource_Effect_Authority_Design_Candidate_v0.1.md` §5 defines `CapabilityTypeDefinition` with a field `compatible_effect_classes[]` (plural/array), and states explicitly:

  > "Initial vocabulary includes MODEL_INVOKE, WORKSPACE_READ, WORKSPACE_WRITE, PROCESS_EXEC, NETWORK_ACCESS, EVENT_SUBSCRIBE, HUMAN_INTERACT and CANONICAL_COMMAND. Future types such as BROWSER_CONTROL, TOOL_INVOKE and REMOTE_EXEC may be registered without Kernel taxonomy changes."

  `MODEL_INVOKE` is named in the **initial** frozen vocabulary, not merely a hypothetical future type.

- §9 ("Mediated Effect Boundary") enumerates the effect-shaped operation categories as peers under one generic mechanism, explicitly including:

  > "model invoke: Capability; provider-session Resource optional; EffectOperation"

  alongside workspace write, process start, non-idempotent network mutation, consequential browser action, etc. — all governed by the same `EffectOperation` canonical model.

- §10 defines `EffectOperation` with `effect_class` as one ordinary field of a generic record shape; no enum/singleton restriction is stated anywhere in the frozen Candidate, either Clarification, or the Frozen Baseline index.

- `design/clarifications/NYRON-D-004_Lead_Integration_Clarification_002.md` line 117 reinforces this directly: D-008 extension vocabulary (`BROWSER_CONTROL`, `TOOL_INVOKE`, `REMOTE_EXEC`) is "permitted extension vocabulary" that does "not need to be hardcoded as Kernel primitives" — confirming the frozen architecture's own stated model is an open, registrable vocabulary, not a fixed single value.

- `design/Nyron_External_Interfaces_Workspace_Boundary_Design_Candidate_v0.1.md` §11 ("Provider / Model Adapter Boundary") independently designs the full `MODEL_INVOKE` CapabilityGrant + optional Provider Session ResourceLease + `EffectOperation` pattern in detail (invocation, streaming, cancellation, timeout ambiguity, retry safety), using exactly the same generic PREPARED/ACTIVE/REVOKE_REQUESTED/FENCED/UNKNOWN vocabulary the Frozen Baseline defines generically for every effect class.

- Existing **accepted Production code**, not merely design text, already encodes this generic multi-class vocabulary at the Module-contract layer: `src/nyron_kernel/definitions/registry.py` defines `EFFECT_CAPABILITY = {"MODEL_CALL": "MODEL_INVOKE", "WORKSPACE_READ": ..., "WORKSPACE_WRITE": ..., "PROCESS_EXEC": ..., "NETWORK_IO": "NETWORK_ACCESS", ...}` and `KNOWN_EFFECT_CLASSES = frozenset({"PURE", *EFFECT_CAPABILITY})`. A `ModuleDefinition` may already declare `effect_classes=("MODEL_CALL",)` today and pass `ModuleRegistry._validate_effects_and_capabilities` without any code change — the Module/Definition layer already accepts `MODEL_CALL`/`MODEL_INVOKE` as a known, valid effect class.

### Q2 — Is the current single `EffectAuthority.EFFECT_CLASS` constant merely a narrow implementation, or is the single-class shape itself authoritative?

**Narrow implementation, not authoritative.**

`src/nyron_kernel/effect/authority.py` defines exactly one class-level constant:

```python
EFFECT_CLASS = "nyron.kernel.managed-resource-bounded-write@1"
```

and `_validate_request` rejects any `EffectRequest.effect_class != cls.EFFECT_CLASS`. This is the **only** place in the frozen bundle or accepted code that hardcodes a single value — and it appears solely inside the one concrete `EffectAuthority` class that happens to implement the one effect use case built so far (a bounded managed-resource/filesystem write): `prepare`/`_admit_dispatch`/`_activate`/`_mutate_and_complete`/`_target_evidence`/`_commit_completed` are all written in terms of a filesystem `target` path, byte payload, `xb` file write, and SHA-256 content-hash completion evidence. Nothing in the frozen D-004/D-008 text ties this filesystem-specific evidence/dispatch mechanics to the *identity* of "Effect Authority" as an owner concept; §10 of the D-004 Candidate defines `EffectOperation` generically (owner enforcement, transaction/fencing primitives, causal/replay foundations) without specifying filesystem semantics as intrinsic to the owner.

Corroborating evidence that the surrounding, adjacent Owner (`CapabilityAuthority`) is **already class-agnostic**: `src/nyron_kernel/capability/authority.py` `_is_effect_dispatch_admissible_with(connection, grant_ref, authority, exact_scope, now)` takes an arbitrary `exact_scope: dict[str, Any]` and does a generic canonical-JSON scope comparison — it is not filesystem- or class-specific in any way; `EffectAuthority._admit_dispatch` already passes `exact_scope = {"effect_class": operation.effect_class, "resource_ref": operation.resource_ref}` generically. The single-class restriction exists only inside `EffectAuthority._validate_request`'s literal equality check — it is a narrow gate in one implementation method, not a frozen architectural constraint repeated anywhere else in the authority chain.

Also directly on point: Task-180's own Finding `NYRON-T-20260828-180-F-005` already characterized this exact fact pattern as unconfirmed ("could not fully verify... whether introducing a second `MODEL_INVOKE`-class Effect is already permitted by frozen authority or requires an architecture amendment") — this Task's full read of the complete bundle (Task 180 read only the Fenced-Retry Amendment in full, not the complete D-004/D-008 Candidate + all Clarifications) resolves that open question: no frozen text anywhere restricts `EffectOperation`/`EffectAuthority` ownership to one effect class; the restriction is local to the current `EffectAuthority._validate_request` implementation only.

### Q3 — Can a future `MODEL_INVOKE` effect be added as bounded implementation work without changing ownership or frozen semantics?

**YES**, subject to the invariants in Q4.

- Ownership is unchanged: Effect Authority remains the sole canonical owner of `EffectOperation` for a `MODEL_INVOKE`-class operation exactly as it is for the existing filesystem class (`ARE-INV-01`; D-004 Candidate §4 owner table: "EffectOperation | Effect Authority"). Nothing in D-008 §11 ("Provider / Model Adapter Boundary") assigns `EffectOperation` ownership to a Provider/adapter; §11.1 states explicitly: "Adapters may hold controlled provider credentials as TCB components but do not own Runtime Attempt, BudgetReservation, CapabilityGrant, ResourceLease or EffectOperation canonical truth."
- No new cross-owner semantics are required: CapabilityGrant/ResourceLease/Attempt/Accounting all remain exactly as owned today (Capability Authority / Resource Manager / Runtime / Accounting respectively); a `MODEL_INVOKE` effect only needs a `MODEL_INVOKE` `CapabilityGrant` (already valid vocabulary, §Q1) and, per D-008 §11.2, an optional Provider Session `ResourceLease` — both fit the existing generic Grant/Lease shapes with no field additions.
- The implementation delta is bounded to: (a) a second concrete effect-class value accepted by `EffectAuthority` (replacing or extending the current single-value equality check with an allow-list, or an equivalent bounded dispatch path scoped to `EffectAuthority`), and (b) new class-specific dispatch/evidence logic appropriate to a provider call (e.g. reliable provider response/idempotency evidence in place of `_target_evidence`'s filesystem hash comparison) — this is exactly "required structural complexity" traceable to D-008 §11's already-frozen model-invoke design, not speculative complexity.
- `design/clarifications/NYRON-D-004_Lead_Integration_Clarification_003.md` line 58 confirms per-class extension is the frozen expectation, not an exception requiring amendment: "Nyron does **not** require one hardcoded global conflict-domain enum. Instead, every EffectClass / CapabilityType contract that can participate in replacement-conflict safety MUST define or deterministically derive a machine-checkable **EffectConflictScope**..." — i.e. adding a new effect class is anticipated frozen-contract work (define its `EffectConflictScope`), not an architecture amendment.

### Q4 — If yes, what exact invariants must the implementation preserve?

All of the following remain unchanged and must be preserved bit-for-bit in shape (not merely "considered"):

- **PREPARED state / ownership** — `ARE-INV-01` (CapabilityGrant, Resource/ResourceLease and EffectOperation each have exactly one authoritative Owner), `ARE-INV-09` (every long/async/non-idempotent/cancellable/crash-ambiguous external effect has durable EffectOperation identity before dispatch; PREPARED does not prove the effect occurred), `ARE-INV-24` (PREPARED is not authority consumption). D-008 §11.3 restates this directly for the provider case: "EffectOperation PREPARED must exist before dispatch if dispatch can become ambiguous across crash."
- **Fencing** — the exact `(execution_ref, activation_ref, run_ref, attempt_seq, fencing_token, fencing_generation)` `AttemptAuthority` tuple must be carried through a `MODEL_INVOKE` `EffectRequest`/`EffectOperation` identically to the filesystem case; stale Attempt cannot obtain new effect/command authority admission (D-004 Candidate §6).
- **Historical outcome / FENCED semantics** — `ARE-INV-20` (PREPARED is conflict-relevant until non-dispatch is proven), `ARE-INV-21` / `EIW-INV-32` (FENCED is not semantic retry clearance — active/concurrency conflict clearance and semantic retry clearance are orthogonal facts), `ARE-INV-22` (active state and historical consequence are orthogonal). D-008 §11.5/§11.6 make the provider-specific instance of this explicit: cancellation confirmation must be *reliable* before FENCED (otherwise UNKNOWN), and client timeout must not be automatically mapped to external failure — if the provider may have accepted/completed the request and no reliable idempotent lookup evidence exists, the operation becomes `UNKNOWN`, exactly like the existing filesystem `_target_evidence` "MISMATCH"/"ABSENT" branches feeding `_mark_unknown`.
- **Authority validation must linearize against revocation** — `ARE-INV-23` / `ARE-INV-25`: real dispatch admission for a `MODEL_INVOKE` effect must re-read current Attempt/Grant/Lease state inside the same dispatch transaction exactly as `EffectAuthority._admit_dispatch` already does for the filesystem case (`self._runtime_authority.is_current_with(...)` + `self._capability_authority._is_effect_dispatch_admissible_with(...)` inside one `self._store.transaction()` block) — no check-then-use, no broker-local cached boolean treated as authority (`NYRON-D-004_Lead_Integration_Clarification_005.md` §9).
- **CapabilityGrant / ResourceLease / Attempt / Accounting distinctness** — `ARE-INV-13` (EffectOperation and BudgetReservation remain orthogonal canonical states/owners/lifecycles); a `MODEL_INVOKE` effect must not fold Provider Accounting/usage facts into EffectOperation canonical state or vice versa (D-004 Candidate line 486: "EffectOperation may be COMPLETED while BudgetReservation remains RECONCILING; EffectOperation may be UNKNOWN while budget remains RESERVED").
- **New per-class conflict scope required, not optional** — Clarification 003 line 58 (quoted in Q3): the `MODEL_INVOKE` class must define its own deterministic, machine-checkable `EffectConflictScope`; it cannot silently reuse the filesystem class's resource-directory-based conflict check as-is without re-deriving what "disjoint" means for a provider operation. `ARE-INV-19` (unproven disjointness fails closed) applies to whatever that new scope definition is.
- **Streaming is not a multi-effect loophole** — D-008 §11.4: one provider request is normally one `EffectOperation` that stays `ACTIVE` while the request is externally active; stream chunks are not separate external-invocation effects by default.
- **No retry/redispatch clearance is created** — External Interfaces Amendment 001 §2/§6 (`EIW-INV-32`) applies without modification: `FENCED` alone never authorizes same-semantic redispatch; safe redispatch (if ever implemented, which is explicitly out of this Task's scope and this Task's constraints forbid inventing it) would require proven non-dispatch, provider idempotency-identity deduplication, an explicitly distinct new operation, or explicit duplicate-acceptance policy.

### Q6 — Does anything in the frozen baseline allow a Provider or Product layer to own or bypass Effect authority?

**NO — proven, not assumed.**

- D-004 Candidate §4 (canonical-state ownership table) assigns `EffectOperation` to `Effect Authority` only; the same table states "Module Host owns none of these canonical truths. It may hold transient execution state and Kernel-issued proxies but cannot become a durable semantic Owner," and "Runtime may request grants, leases, effect creation/revocation... but cannot directly mutate their canonical state."
- D-008 Candidate §11.1 states directly, for the Provider/model case specifically: "Adapters may hold controlled provider credentials as TCB components but do not own Runtime Attempt, BudgetReservation, CapabilityGrant, ResourceLease or EffectOperation canonical truth."
- D-008 Candidate §11.2: "A provider session is not workflow canonical truth. If a provider session disappears, Nyron must still be able to explain committed history" — i.e. Provider-side state is explicitly demoted to non-authoritative even when it exists as a Resource.
- The Frozen Baseline's own "Frozen scope" section (`design/Nyron_Capability_Resource_Effect_Authority_Frozen_Baseline_v0.1.md`) lists as frozen: "Package trust/install/enable is not Capability/Resource/Effect/Runtime authority" and "Capability / Resource / EffectOperation / BudgetReservation remain distinct canonical facts and owners" — the Product layer (Product Node / Module config) is even further removed, and `coordination/STATUS.md`'s own standing "Product Guardrails" section (independently, at the coordination layer) states "Product declaration != execution authority."
- Task-180's own independently-reproduced code trace (§5, §6 of its result) found zero references to `ResolvedCredentialHandle` or any authority-mutating call outside `host/credential/foundation.py`, and zero Provider/Product code path that writes `capability_grants`, `resource_leases`, `run_attempts`, or `effect_operations` tables directly — confirmed again in this Task's own read of `src/nyron_kernel/effect/authority.py` (the `INSERT`/`UPDATE` statements against `effect_operations` exist only inside `EffectAuthority`'s own methods).

No text anywhere in the frozen bundle grants Provider or Product any Effect-authority-owning or -bypassing capability; this is confirmed by direct textual citation and independent code trace, not inferred by absence.
