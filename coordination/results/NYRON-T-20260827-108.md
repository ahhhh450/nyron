## Blocking finding

- Type: `CONTRACT / ARCHITECTURE`
- Severity: `BLOCKING`
- Code: `CROSS_OWNER_RUNTIME_ACCOUNTING_STORAGE_BOUNDARY_UNFROZEN`

The frozen baseline requires Accounting and Runtime to converge without assuming a shared/global transaction. The implemented public `BudgetAuthority` can read Runtime identity through injected `ActivationRepository` and `RuntimeAuthorityResolver`, but its Accounting-owned `budget_reservations` table also has a direct SQLite foreign key to Runtime-owned `run_attempts(run_ref, attempt_seq)`. `SQLiteStore.create_budget_schema()` installs Runtime tables inside the Accounting store to satisfy that foreign key.

Consequently, a concrete Runtime -> Accounting `RequestBudgetReservation` delivery using separate owner-local stores can validate the canonical Runtime binding successfully and then still fail the Accounting commit with `sqlite3.IntegrityError: FOREIGN KEY constraint failed`, because the Runtime canonical row is not duplicated in the Accounting database.

Continuing requires an authority decision among semantics not currently concretely frozen/implemented, for example:

1. declare the shared SQLite Runtime/Accounting canonical database and its cross-owner foreign keys to be the supported owner-local persistence model despite the no-global-transaction invariant; or
2. define an authoritative Runtime identity projection / evidence contract in Accounting and the durable propagation/freshness rules that replace the cross-owner foreign key; or
3. define another explicit cross-owner storage/identity boundary.

Task 108 explicitly forbids inventing a new cross-owner Contract, Owner authority, or concurrency/fencing architecture. No option can therefore be selected by the Executor.
