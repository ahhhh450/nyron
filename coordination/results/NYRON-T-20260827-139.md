## Reusable Surfaces

### 1. Runtime Attempt / fencing identity

Reusable as a required boundary input:

- `AttemptAuthority` identity and current-Attempt checks;
- exact `execution_ref / activation_ref / run_ref / attempt_seq / fencing_token / fencing_generation` binding;
- replacement cleanup pattern that discovers old-Attempt Effects/Leases by exact tuple and delegates lifecycle changes to their canonical Owners;
- Runtime remains the sole authority for whether stale Attempt output may canonical-commit.

Browser and Remote adapters must consume this authority evidence; they must never decide which Attempt is current.

### 2. Capability Authority pattern

The current Effect dispatch path demonstrates the correct owner boundary: capability scope and current Attempt are revalidated at dispatch admission rather than accepted from a prior advisory check. Browser and Remote slices should reuse this owner contract/pattern with their own registered capability types/scopes.

For Browser operations that can navigate, fetch, redirect, upload, or otherwise cross a network destination boundary, browser authority is not sufficient by itself. It must compose with the Network destination authority contract; every effective destination remains subject to the frozen Network revalidation rule.

### 3. Resource / ResourceLease identity model

The canonical `Resource` / `ResourceLease` data model is reusable conceptually:

- Resource identity/lifecycle is separate from workflow truth;
- leases are bound to an exact Attempt and fencing generation;
- resource possession does not imply Capability authority;
- advisory lease validation is not a dispatch permit;
- live Resource/Lease truth must be rechecked at the actual use boundary.

The current `ResourceManager` implementation is specifically a managed-directory/workspace-handle implementation (`nyron.kernel.managed-workspace-handle@1`). It is not a Browser Session or Remote Worker implementation and must not be relabeled as one.

### 4. EffectOperation preparation / ambiguity pattern

Reusable semantics:

```text
intent
-> EffectOperation PREPARED committed
-> actual-boundary Attempt + Capability + ResourceLease revalidation
-> external dispatch
-> external identity / acknowledgement evidence
-> ACTIVE / COMPLETED
   or REVOKE_REQUESTED / FENCED / UNKNOWN as evidence permits
```

The current EffectAuthority correctly demonstrates PREPARED-before-dispatch and fail-closed UNKNOWN handling, but its concrete effect class and evidence model are for one managed-resource bounded filesystem write. Browser/Remote adapters need their own evidence/lookup/cancellation profiles under the same Effect Authority ownership semantics.

### 5. Recovery evidence repository

`RecoveryRepository` is reusable for ambiguous Browser/Remote cases because it stores external evidence without treating that evidence itself as canonical subject truth, and its retry records are observation/reconciliation attempts rather than permission to replay an Effect.

### 6. Host RuntimeContext pattern

The current Host exposes Attempt-bound Capability and Resource handles and returns a distinct UNKNOWN result for ambiguous external history with the explicit semantic note that UNKNOWN gives no retry clearance. That handle/broker pattern is reusable. The existing `BoundedWriteEffectBroker` itself is not reusable as a Browser/Remote implementation because it supports only the current bounded workspace-write Effect class.

## Findings

### NYRON-T-20260827-139-F-001

- Type: `SECURITY`
- Severity: `BLOCKING`
- Location:
  - `design/amendments/External_Interfaces_Amendment_001_Fenced_Retry_Semantics.md`
  - `src/nyron_kernel/effect/authority.py`
  - `src/nyron_kernel/store/sqlite_store.py` — `effect_operations`
- Evidence:
  - The frozen amendment requires preservation of two independent facts: whether old activity is authoritatively stopped (`FENCED`) and what historical consequence already occurred (`UNKNOWN | PARTIAL | KNOWN`, or equivalent).
  - Current `effect_operations` persists a single lifecycle `state` plus completion/fence evidence; there is no separate historical-outcome dimension.
  - Current concrete EffectAuthority only emits `FENCED` on bases that prove dispatch/mutation was prevented before consequential work (`PREPARED_NEVER_ACTIVE`, dispatch rejected before active, or executor stopped before first mutation). That is safe for the current bounded filesystem slice, but it does not provide a representation for the Browser/Remote case `active_state = FENCED` while prior consequence remains `UNKNOWN` or `PARTIAL`.
- Impact:
  - A future Browser/Remote cancellation implementation that maps authoritative stop confirmation directly to the existing single `FENCED` state could erase historical uncertainty and accidentally treat fencing as semantic retry clearance, violating `EIW-INV-32`.
- Required Resolution:
  - Before post-dispatch Browser/Remote fencing is implemented, Effect Authority must expose an owner-local representation/API that preserves active/conflict cessation separately from historical outcome, or another equivalent representation satisfying Amendment 001. Exact schema shape is intentionally not prescribed by this review.
  - Retry admission must independently prove no relevant prior consequence, reliable idempotent deduplication, a new distinct semantic operation, or explicit duplicate-consequence policy. `FENCED` alone is never sufficient.

- Location:
  - `src/nyron_kernel/host/runtime_context.py`
  - `src/nyron_kernel/effect/authority.py`
  - `src/nyron_kernel/resource/manager.py`

- Evidence:

  - Current EffectAuthority is explicitly the bounded managed-resource write adapter; its target/evidence semantics are filesystem-specific.
  - Current ResourceManager owns one managed-directory/workspace-handle resource implementation, not Browser Session or Remote Worker resources.
  - No current Browser/Remote actual-boundary broker exists that can carry exact Attempt authority, validate Browser/Remote capability scope, validate a Browser Session/Remote Worker lease, compose Browser navigation with Network destination scope, and bind PREPARED Effect identity to external action/job evidence.
- Impact:
  - Opening Browser or Remote dispatch by passing raw automation handles, SDK clients, direct remote protocol connections, or prevalidated booleans to Modules would bypass the frozen authority boundary and create stale-Attempt, scope-widening, crash-ambiguity and cancellation/fencing vulnerabilities.
- Required Resolution:
  - The first Browser and Remote slices must introduce bounded adapter/broker entry points that revalidate owner truth at the actual external boundary and report evidence back to canonical Owners. They must not give restricted Modules raw browser automation handles, raw remote-worker protocol access, or canonical-state mutation authority.
  - Browser network composition must depend on the separately implemented Network boundary; this Task does not design or implement that Network layer.

## Minimum Safe Browser Slice

The smallest safe first Browser implementation slice is intentionally narrow:

1. **Browser Session as Resource/Lease**
   - one managed Browser Session/Profile/Context resource type owned through Resource Manager semantics;
   - exact Attempt-bound ResourceLease;
   - cookies/authenticated state/open-page continuity may live in the Resource, but canonical workflow truth may not;
   - session rebinding/restart creates/validates current live binding; historical session identity is not authority.

2. **Typed Browser boundary broker, no raw automation handle**
   - accepts only an exact Attempt-bound RuntimeContext/authority envelope plus registered Browser capability handle and Browser Session lease handle;
   - immediately before each browser boundary operation revalidates current Attempt/fencing, active capability scope, live session/lease compatibility and operation classification;
   - restricted Modules do not receive the underlying browser engine object.

3. **Observation allowlist with adapter-declared semantics**
   - initial untracked observations may include only operations whose adapter profile proves them non-consequential under the Lead clarification, e.g. local DOM/accessibility-tree/title/current-URL/screenshot/element lookup when they are not independently billable, externally stateful, asynchronously active, cancellable or crash-ambiguous;
   - if any of those properties applies, or classification is uncertain, fail closed to the tracked consequential class and require an EffectOperation.

4. **Consequential Browser actions are individual EffectOperations**
   - each independently retryable/cancellable/ambiguous externally meaningful action gets a stable semantic `operation_ref`;
   - PREPARED is committed before the adapter can trigger the action;
   - action intent must identify the semantic operation, not merely coordinates or a UI label;
   - external transaction/request identifiers and strong evidence are bound to the Effect when available;
   - completion is committed only from reliable evidence.

5. **UI/action ambiguity fails closed**
   - a click labelled `View`, a link, navigation, script-driven action, or unknown control is not presumed observational;
   - if the adapter cannot prove the operation class, dispatch is denied or treated as consequential/tracked before the click occurs;
   - module self-declaration cannot weaken adapter classification; at most it may request the stronger class.

6. **Network capability composition**
   - any operation that can initiate network navigation/request/redirect/upload/download must pass Browser authority and the effective-destination Network policy;
   - every redirect/effective destination is revalidated by the Network boundary;
   - the first Browser slice must not substitute origin-page authorization for destination authorization.

7. **Crash / timeout / cancellation semantics**
   - crash after PREPARED but before action may clear only with reliable no-dispatch/no-consequence evidence; otherwise UNKNOWN;
   - crash/disconnect after click/submit is UNKNOWN unless external/application evidence proves a terminal outcome; DOM state alone is insufficient;
   - cancellation request or local page/socket close is not FENCED evidence;
   - post-dispatch FENCED requires reliable proof no further relevant activity can occur, while historical outcome remains independently represented per Finding F-001.

8. **Stale Attempt result handling**
   - a browser action started under R1 may later return after R2 has replaced it; its external Effect evidence remains owner history, but R1 output cannot canonical-commit;
   - the adapter must never reinterpret a late result as authority to mutate Runtime state.

9. **First-slice exclusions**
   - no arbitrary page script execution exposed to restricted Modules;
   - no unrestricted raw browser session handle;
   - no claim of crash-safe semantic retry unless adapter evidence/idempotency supports it;
   - persistent browser download-to-workspace is deferred until the separately tracked Browser Effect + Workspace mutation composition is explicitly implemented and tested.

## Minimum Safe Remote Worker Slice

1. **Remote Worker Session as Resource/Lease**
   - a reusable worker connection/agent/session is a Resource only when it has stateful continuity worth leasing;
   - lease is exact-Attempt bound and does not itself represent job history;
   - live worker availability/compatibility is checked at use time; configuration or prior session identity is not proof of a current worker.

2. **Remote Job is always a distinct consequential EffectOperation**
   - creation/dispatch of a remote job requires an EffectOperation independent from the worker Resource;
   - stable Nyron operation identity is committed PREPARED before the first external send that could create the job;
   - worker/session Resource cannot replace that Effect history.

3. **Actual-boundary authority admission**
   - immediately before send, validate current Attempt/fencing, registered remote-execution Capability scope, Resource/Lease identity/state and remote target/profile constraints;
   - direct remote-worker protocol access from restricted Modules is prohibited.

4. **Durable external identity**
   - the first crash-recoverable backend profile must provide a stable remote job/request ID or reliable idempotency identity;
   - acknowledgement/job identity is durably bound to the Effect evidence as soon as available;
   - semantically different jobs may not reuse the same external idempotency identity.

5. **Lookup is required for crash-safe recovery claims**
   - after disconnect/crash, lookup by durable external identity determines ACTIVE/COMPLETED/stopped evidence;
   - absence of a channel/response is never proof the job did not run;
   - a backend without reliable lookup/idempotency may still be supported only with explicitly weaker semantics: ambiguous dispatch becomes UNKNOWN and the same semantic job is not automatically retried.

6. **Cancellation / fencing**
   - cancellation flow is `ACTIVE -> REVOKE_REQUESTED -> remote cancel request -> authoritative remote lookup/terminal evidence`;
   - confirmed completed job maps to COMPLETED;
   - confirmed cessation may clear active conflict as FENCED only with reliable evidence that no further relevant activity can occur;
   - uncertain or unqueryable state maps to UNKNOWN;
   - worker-channel disconnect or cancel acknowledgement alone is not proof of FENCED.

7. **Retry semantics after cancellation**
   - even when active conflict is FENCED, the same semantic job remains non-retryable if historical consequence is UNKNOWN/PARTIAL unless the same external idempotency identity reliably deduplicates, evidence proves no relevant consequence, duplicate consequences are explicitly accepted, or the next job is explicitly a new semantic operation.

8. **Stale Attempt result handling**
   - returned job data must carry/bind the original operation/job/Attempt identity;
   - Effect Authority may record truthful terminal evidence for old work, but Runtime rejects output commit from a stale Attempt;
   - late R1 result cannot become R2 output by identity substitution.

## Unresolved Assumptions

1. `BROWSER_CONTROL` and `REMOTE_EXEC` are frozen examples, not necessarily standardized initial CapabilityType names. The first implementation Task must bind exact registered capability types/scopes without redefining D-004 vocabulary.
2. The concrete Browser engine/service is intentionally unspecified. Its adapter profile must state which observations are truly untracked-safe and what authoritative action/cancellation/lookup evidence it can provide.
3. The concrete Remote Worker backend is intentionally unspecified. Its profile must define durable job identity, idempotency semantics, lookup guarantees, terminal-state meaning and what `stopped` proves about future activity.
4. Browser operations that can cross a network boundary depend on the separately implemented Network authority/effective-destination contract. This review does not authorize or design that implementation.
5. Finding F-001 may be resolved through any Effect-Owner-local representation that preserves the frozen semantics; this review does not freeze a database column, enum, state machine or migration design.
6. Resource Manager remains the canonical Resource/Lease Owner, but this review does not prescribe whether future Browser Session/Remote Worker resource support is implemented through a generalized manager, separate owner-local adapters, or another contract-compatible internal structure.
7. No crash-safe retry claim is permitted for an adapter profile that lacks the external evidence/idempotency/lookup necessary to justify that claim.
