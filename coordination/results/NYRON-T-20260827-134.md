## Findings

### Finding
ID: NYRON-T-20260827-134-F01
Type: SECURITY
Code: WORKSPACE_READ_HANDLE_CONTINUITY_MISSING
Severity: HIGH
Location: `src/nyron_kernel/resource/manager.py` / future Workspace READ integration boundary
Evidence: Existing descriptor logic pins and verifies the managed resource directory, but `_resolve_effect_directory_with(...)` returns a `Path`. There is no descendant resolver that preserves an already-verified directory handle from containment resolution through the actual observation operation.
Impact: A future adapter that validates containment and then rejoins/reopens by pathname would recreate validation/use TOCTOU, ancestor replacement, intermediate-link swap, and final-target swap windows forbidden by D-008 EIW-INV-03/04 and EIW-G2.
Required Resolution: The first Workspace READ implementation must preserve a verified workspace/root directory handle through descendant resolution and actual read/stat/list/hash use. It must never treat a validated `Path` string as an authority token. The final object must be consumed from the same handle-relative resolution chain, with no path re-resolution between validation and use.

### Finding
ID: NYRON-T-20260827-134-F02
Type: SECURITY
Code: MOUNT_BOUNDARY_NOT_ENFORCED
Severity: HIGH
Location: `src/nyron_kernel/resource/manager.py` / descendant resolution not yet implemented
Evidence: Current provenance checks verify root/resource identities, but there is no explicit descendant mount/bind-mount crossing policy. Device/inode identity of the starting directory alone does not prove that a descendant walk did not cross a nested mount, and bind mounts cannot be safely modeled as simple lexical containment.
Impact: A nested or bind-mounted subtree could widen effective filesystem authority while remaining lexically under the workspace root, violating D-008 EIW-INV-05.
Required Resolution: The first bounded Workspace READ slice must default-deny mount crossing. Strong profiles must use an OS primitive capable of enforcing this during the same handle-relative resolution (for example, a platform resolver with a no-cross-device/no-mount constraint) or fail closed. Explicit external/nested-mount allowlisting is outside this first slice.

### Finding
ID: NYRON-T-20260827-134-F03
Type: SECURITY
Code: DESCENDANT_LINK_REPARSE_POLICY_NOT_IMPLEMENTED
Severity: HIGH
Location: future Workspace READ descendant path walk
Evidence: Current code rejects/rechecks the managed root/resource directory with no-follow/reparse evidence where supported, but it does not walk arbitrary request descendants and therefore does not enforce intermediate/final symlink, Windows junction, reparse-point, or magic-link policy component-by-component.
Impact: A future lexical or partially-resolved walker could escape through an intermediate or final indirection, including races that replace an ancestor after validation.
Required Resolution: Freeze the first Workspace READ slice to `symlink/junction/reparse traversal = forbidden`. Enforce that rule during each handle-relative component resolution and for the final object. If the platform cannot prove the rule race-safely, the strong isolation profile must be unavailable rather than degraded silently.

### Finding
ID: NYRON-T-20260827-134-F04
Type: SECURITY
Code: SPECIAL_FILE_GATE_REQUIRED
Severity: HIGH
Location: future Workspace READ final-object handling
Evidence: No current Workspace READ adapter classifies final filesystem object types. D-008 explicitly excludes consequential special/device-path behavior from ordinary Workspace READ semantics.
Impact: Opening a FIFO, socket, character/block device, pseudo-filesystem endpoint, or other special object as if it were a regular file can block, trigger device semantics, or cross the intended observation-only authority boundary.
Required Resolution: Before content access, classify the already-resolved final handle and permit only regular files for file observation and directories for directory observation in the first slice. Reject symlinks/reparse points, FIFO, socket, block/character/device objects, and other special types without invoking their consequential behavior.

## Minimum Safe Future Workspace READ Implementation Boundary

The Development Director may open a bounded Workspace READ implementation task only if its scope is no broader than the following:

1. **Operation class**
   - Observation-only Workspace READ: bounded file read, stat/metadata, directory list, and optional hash over already-authorized regular files/directories.
   - No Workspace WRITE, Process, Network, Browser, Credential, Secret retrieval, or general raw filesystem access.
   - Ordinary reads remain outside EffectOperation unless an exact operation classification says the requested observation is consequential.

2. **Authority inputs**
   - Current RuntimeContext / Attempt identity.
   - RuntimeContext-issued `WORKSPACE_READ` `CapabilityHandle`.
   - RuntimeContext-issued managed-workspace `ResourceHandle` (Resource + Lease).
   - Exact PWP `workspace_ref`, WorkspaceConfigRevision/root declaration, and EnvironmentBindingRevision/resource-compatibility context required for that root.
   - Structured relative path only; no module-supplied raw host root.

3. **Path input contract**
   - Treat the request as relative path components, not as a host pathname to canonicalize by prefix comparison.
   - Reject `.` / `..`, empty traversal components where semantically ambiguous, NUL, absolute paths, drive-qualified paths, UNC/NT-device namespaces, rooted separator forms, and separator-smuggling/mixed-separator variants before filesystem resolution.
   - Do not perform Unicode/case normalization that can widen a scoped path. If scoped subpaths are later supported, grant-time and use-time canonical-key logic must be identical for each supported filesystem profile.

4. **Race-safe resolution/use**
   - Open and verify the managed workspace/root directory as a handle and keep it alive through the whole operation.
   - Resolve descendants relative to that handle with no-follow semantics at every component.
   - First slice forbids all symlink/junction/reparse/magic-link traversal and all nested/bind-mount crossing.
   - Use a platform-native resolver that enforces `beneath/in-root`, no-link, and no-mount-crossing semantics atomically where available; otherwise the strong profile fails closed.
   - Inspect the final opened handle's type/identity, then perform read/stat/list/hash from that same handle. Do not stringify/reopen the path after validation.

5. **Live-state revalidation / linearization**
   - Capability, Attempt, Resource, Lease, PWP workspace/config/binding compatibility must be current at the actual privileged boundary.
   - If handle acquisition and authority checks cannot be one atomic transaction, perform a final current-state check immediately before the first observation from the pinned final handle. Expired/revoked Lease, stale capability/Attempt, archived/rebound workspace, config pointer mismatch, or resource incompatibility must fail closed.

6. **Broker output**
   - Return bounded bytes and/or normalized metadata/entry names only.
   - Never expose host `Path`, raw file descriptor/OS handle, unrestricted file object, or host exception containing an authority-bearing absolute path to module code.
   - Enforce explicit maximum bytes, maximum directory entries, and metadata bounds.

7. **Isolation claim**
   - Broker correctness is not a hostile-module sandbox. `TrustedModuleHost` remains a trusted execution mode; a strong D-008 isolation claim requires a host profile that prevents ambient direct filesystem access independently of the broker.

## Explicit Unresolved Platform Assumptions

- The frozen baseline intentionally leaves the first supported OS/filesystem security envelope open. No strong cross-platform claim is justified yet.
- Linux/Unix strong support requires a verified native handle-relative resolver that can simultaneously enforce beneath/in-root resolution, no link traversal, and no mount crossing. Existing Python `Path` resolution is not sufficient.
- Windows strong support requires native handle-based component resolution and explicit junction/reparse/mount-point rejection; the current root-level reparse check alone is insufficient.
- Filesystems with nonstandard inode/device stability, network filesystems, FUSE/overlay-like layers, or unusual rename/mount semantics must be excluded from the strong profile until the adversarial matrix passes on the exact claimed profile.
- Case-fold and Unicode normalization behavior is filesystem/platform dependent and must be frozen/tested per supported profile before scoped-subpath authority is claimed.
- `TrustedModuleHost` is not itself hostile-code filesystem isolation. A bounded Workspace READ broker may be correct while the overall host remains a trusted-only profile.

## Director Decision

`PASS_WITH_FINDINGS`: current managed-workspace Resource provenance/lease machinery, RuntimeContext opaque-handle/broker pattern, and accepted PWP root/config surfaces are sufficient foundations to open a **narrow future Workspace READ implementation task**, but they are not by themselves D-008 EIW-G2-complete. Findings F01-F05 are mandatory acceptance constraints for that implementation. The initial task must pin a supported platform/isolation profile and must fail closed wherever handle-continuous no-link/no-mount-crossing resolution cannot be proven.
