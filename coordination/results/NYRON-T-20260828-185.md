## B. RuntimeContext Authority Boundary (Requirements 1–6)

**Code-level trace**, `src/nyron_kernel/execution/executor.py` `AttemptExecutor._runtime_context`:

- PURE Modules (`effect_classes == ("PURE",)`) return `None` unconditionally — the exact prior expression is preserved verbatim; no code path can reach the new grant-resolution logic for a PURE Module (Requirement 1). `ModuleRegistry._validate_effects_and_capabilities` (unchanged, pre-existing) already guarantees `PURE` is only ever a strict singleton, so this equality check is exhaustive, not just the common case.
- For any non-PURE Module, the Module's own **canonical, already-registered** `effect_classes` are mapped through the pre-existing `EFFECT_CAPABILITY` vocabulary (`src/nyron_kernel/definitions/registry.py`, unchanged by this delivery) to capability-type names. If any mapped effect is anything other than `MODEL_INVOKE`, or `capability_authority`/`effect_authority` is not wired, execution fails closed with `RUNTIME_CONTEXT_AUTHORITY_INVALID` **before** `self._host.execute(...)` is called — confirmed both by code (the raise happens inside `_runtime_context`, called before `self._host.execute`) and by Task 184's own added test `test_effect_capable_attempt_without_canonical_grant_fails_before_host`, which asserts `host.calls == 0`. This independently satisfies Requirement 5 ("fails closed before host invocation") for the missing-authority case, and additionally confirms the live wiring is deliberately bounded to exactly the one class this Task was scoped to implement (Requirement is not silently widened to WORKSPACE_WRITE/PROCESS_EXEC/etc., which have no live grant-issuance policy and would previously have silently done nothing — now they fail loudly and closed instead, which is strictly safer than the pre-184 dead-code state).
- `CapabilityAuthority._resolve_active_for_attempt` (new, `src/nyron_kernel/capability/authority.py`) resolves grants matching the **exact** 6-tuple fencing identity (`execution_ref, activation_ref, run_ref, attempt_seq, fencing_token, fencing_generation`) of the current Attempt, `state = 'ACTIVE'`, and current `not_before`/`expires_at` bounds, then requires the **union** of matched grants' `compatible_effect_classes` to fully cover every requested effect class (`covered == requested`) or returns `()`. A partial/incomplete grant set is fail-closed, not fail-open (Requirement 3, 5). Because the fencing tuple must match exactly, a replacement Attempt (new fencing generation, per frozen D-004 §6 "Replacement Attempts receive new Grants; they never inherit the old Attempt's Grant") cannot inherit a stale Attempt's grants — this is Requirement 6 (stale Attempt/fencing) enforced at RuntimeContext **construction** time, independently reproduced in §F below at the real **dispatch** boundary (defense in depth, matching Clarification-005 §9's "not check-then-use" requirement).
- `build_runtime_context` constructs only `CapabilityHandle` (capability_type_ref/version/grant_ref triple — confirmed frozen/no-path shape by Task 184's unchanged, still-passing `test_shapes_are_frozen_and_resource_handle_has_no_path`), optional opaque `ResourceHandle`, and the bounded `BoundedWriteEffectBroker`. Reading the full `RuntimeContext`/`BoundedWriteEffectBroker` class bodies in `src/nyron_kernel/host/runtime_context.py` confirms no field or method anywhere in the object graph exposes `StateStore`, a SQLite connection, a raw `CapabilityGrant`/`ResourceLease` row/object, a credential value, `ResolvedCredentialHandle`, a socket/HTTP/Provider client, or an unrestricted OS/network object (Requirement 4). Independently grepped: `ResolvedCredentialHandle` appears nowhere in the diff or in any file this delivery touches; its only Production references repository-wide remain `src/nyron_kernel/host/credential/__init__.py`'s own re-export (unchanged) — see §D.

## C. MODEL_INVOKE Effect Contract (Requirements 7–17)

- **Sole owner (7):** every `INSERT`/`UPDATE` against the `effect_operations` table in the entire diff occurs inside `EffectAuthority`'s own methods; no Provider/Module/Product code path writes canonical `EffectOperation` state. `SUPPORTED_EFFECT_CLASSES = frozenset({EFFECT_CLASS, MODEL_INVOKE_EFFECT_CLASS})` is a closed, bounded set of exactly two values — not an open registry.
- **PREPARED before dispatch (8):** `prepare()` is unconditionally the first step of `execute()` for both classes; `_admit_dispatch` (dispatch admission) only ever runs on an already-`PREPARED` row. Task 184's `test_model_invoke_prepared_before_local_dispatch_and_completion_evidence` independently instruments a crash hook and asserts the first observed stage is `PREPARED` — reproduced and passing in this Review's own full-suite run (§E).
- **Revalidation before ACTIVE (9):** `_admit_dispatch` calls `self._runtime_authority.is_current_with(connection, authority)` and `self._capability_authority._is_effect_dispatch_admissible_with(...)` inside one `self._store.transaction()` block, identically for both effect classes (this code path itself is *not* branched by class — only the `exact_scope`/conflict-query inputs feeding it are). `_activate` only transitions `PREPARED`+admitted → `ACTIVE`. Independently re-verified by the adversarial scripts in §B.
- **Exact provider/model scope (10):** `_exact_capability_scope` returns `{"effect_class": "MODEL_INVOKE", "provider_ref": ..., "model_ref": ...}` derived from the operation's own immutable payload, checked against the grant's fixed `scope_json` by unchanged pre-existing code. Verified empirically in §B.2.
- **Optional ResourceLease contract (11):** `_validate_request` requires `resource_ref`/`resource_lease_ref` to be **both absent** for `MODEL_INVOKE` (any partial/raw supply raises `EFFECT_REQUEST_INVALID`) and **both present as non-empty strings** for the filesystem class (unchanged). This is the "always-absent" instance of the frozen "optional Provider Session ResourceLease" contract (D-008 §11.2) — correct because this bounded local-simulation class has no real provider session to lease; it does not invent a session type the frozen design left unbuilt. Task 184's `test_model_invoke_conflict_scope_resource_shape_and_sqlite_restart` independently exercises a partial-resource-shape rejection and this Review re-ran it (§E).
- **Class-specific deterministic conflict scope (12):** conflict identity is `sha256(canonical_json({provider_ref, model_ref, conflict_scope_ref}))`, entirely disjoint from the filesystem class's `resource_ref`-keyed conflict check (different `conflict_column` branch in `_admit_dispatch`); proven scope distinctness (different `conflict_scope_ref`) does not conflict, same scope does — both directions exercised by Task 184's own `test_model_invoke_conflict_scope_resource_shape_and_sqlite_restart` (re-run, passing).
- **Replay (13):** identical `(run_ref, attempt_seq, intent_ref)` → identical `operation_ref`, and `_require_identical_replay` (unchanged, shared code) rejects any immutable-field mismatch with `EFFECT_OPERATION_IDENTITY_CONFLICT` without creating a second row. Re-run passing (`test_model_invoke_replay_conflict_and_fabricated_handle_fail_closed`).
- **UNKNOWN on ambiguity (14):** `recover()` for `MODEL_INVOKE` treats `state == "ACTIVE"` **or** `dispatch_admission_ref is not None` as insufficient evidence and marks `UNKNOWN` in both cases — deliberately more conservative than the filesystem class (which can use `_target_evidence` to prove `ABSENT` and safely remain `PREPARED`). This is the correct bias: this class has no independent post-crash evidence channel at all, so treating "admission already happened" as the threshold for "cannot prove non-dispatch" fails closed rather than assuming safety. Independently reproduced by crash-hook injection in §E (this Review's own full-suite run includes Task 184's `AFTER_ACTIVE_COMMIT` crash test asserting recovery to `UNKNOWN`).
- **FENCED only for proven non-dispatch (15):** `request_revoke` for `MODEL_INVOKE` FENCEs only when `state == "PREPARED"` **and** `dispatch_admission_ref is None` (i.e., admission never even started) — every other path (already admitted, or `ACTIVE`→`REVOKE_REQUESTED`) resolves to `UNKNOWN`, never a fabricated `FENCED`. `resolve_revoke` for `MODEL_INVOKE` always resolves `REVOKE_REQUESTED` to `UNKNOWN`, never `FENCED` — correct, since this local-simulation boundary has no reliable external cancellation-confirmation channel (D-008 §11.5's "uncertain → UNKNOWN" branch is the only one this class can truthfully take). No code path anywhere treats `FENCED` as retry/redispatch clearance; no retry/redispatch code exists in the diff at all.
- **Historical outcome orthogonality (16):** `_commit_model_invoke_completed` and `_commit_fenced`/`_mark_unknown` each independently set `historical_outcome`/`historical_outcome_evidence_json` alongside (not instead of) `state`; nothing in the diff couples `EffectOperation` state to `BudgetReservation`/Accounting tables (none of the changed files touch `accounting/`).
- **Filesystem semantics unchanged (17):** every filesystem-class branch (`if operation.effect_class == self.EFFECT_CLASS: ...`) reproduces the pre-184 logic verbatim (confirmed by direct diff reading — the `else` branches are pure additions, the `if` branches are the original code unindented into a new conditional).
