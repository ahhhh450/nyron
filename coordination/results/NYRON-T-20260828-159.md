## Required Provider Identity Before Dispatch

The durable immutable binding must include at minimum:

1. Nyron `operation_ref` and exact semantic request/payload hash;
2. exact Provider adapter/profile identity and revision;
3. exact provider/account/endpoint/model scope used by dedupe and lookup, represented by non-secret stable references;
4. external idempotency key when the profile claims dedupe, committed before dispatch and unique to this semantic operation;
5. dispatch-admission identity/evidence tying the request to the current Attempt, Grant, and any Lease authority;
6. stable Accounting `reservation_ref` for billable dispatch and stable usage-source namespace/binding;
7. set-once external request/operation ID when returned, plus immutable acknowledgement/lookup evidence;
8. for any supported continuation, a continuation identity bound to the same `operation_ref` and external request identity, never a fresh semantic request/key.

Same semantic operation with a different idempotency key, or a different semantic operation reusing the old key, must fail closed.

## Truthful Profile Evidence Requirements

- **Dedupe:** exact protected consequence, key namespace/scope, retention/window, replay response behavior, and proof that duplicate dispatch with the same binding does not duplicate the claimed consequence.
- **Lookup:** lookup key, authoritative source, terminal statuses, and whether `not found` proves absence. Non-authoritative absence preserves `UNKNOWN`.
- **Cancel:** whether cancellation is accepted, whether it stops future work, the terminal confirmation evidence, and how prior partial consequence/usage remains represented. Socket closure or cancel acceptance alone is not fencing evidence.
- **Continuation/resume:** whether reconnect resumes the same external request, stable cursor/request identity, duplicate chunk behavior, and terminal detection. Unsupported resume must be declared unsupported.
- **Streaming:** authenticated append-only chunk/cursor evidence, ordering/deduplication, partial output/usage evidence, restart recovery, late-chunk handling after Attempt replacement, and finalization evidence. Until all exist, streaming must remain disabled.

## UNKNOWN / PARTIAL / KNOWN Rules

Remain `UNKNOWN` when dispatch may have crossed the boundary but provider acceptance/consequence cannot be determined; lookup is inconclusive or non-authoritative; cancel/timeout/disconnect lacks terminal proof; an external ID was not persisted and same-key lookup cannot recover it; or evidence conflicts.

Refine to `PARTIAL` only when immutable accepted evidence proves some consequence or usage but terminal/completeness truth remains unresolved, including confirmed partial tokens/usage followed by an unresolvable disconnect or cancel.

Refine to `KNOWN` only from authoritative evidence sufficient to describe the relevant completed consequence, confirmed no-dispatch/no-consequence, or terminal cancellation together with all prior partial consequence needed by the operation contract. `FENCED` does not perform this refinement by itself.

## Accounting Boundary

Already defined:

- Accounting owns BudgetReservation, UsageFact/UsageAdjustmentFact, settlement, and accounting truth.
- reservation precedes billable dispatch;
- UsageFacts are immutable, source-deduplicated, attributable, and may reference `operation_ref`/`reservation_ref`;
- known actual usage can settle idempotently;
- unknown is not zero;
- uncertain/disputed usage belongs in `RECONCILING`, which grants no spend authority;
- Recovery collects evidence but cannot write Effect or Accounting truth.

Still missing in Production:

- an accepted command/API that moves the exact reservation into `RECONCILING` on Provider `UNKNOWN/PARTIAL` evidence;
- stable mapping from Provider request/line-item/callback identities to UsageFact source identity;
- evidence acceptance rules for Provider lookup/billing facts and adjustments;
- idempotent resolution from `RECONCILING` to `COMMITTED` or `RELEASED` while preserving unknown external history where policy permits accounting exposure closure.

These are bounded implementations of already frozen Accounting semantics, not a missing Owner decision. If implementation discovers that the chosen Provider profile requires a new settlement meaning or authority transfer, it must stop and raise `ESCALATION_REQUIRED` rather than invent it.
