## What Was Wrong

`BudgetAuthority.reserve()` evaluated policy, mutated exposure, and inserted RESERVED/DENIED using only caller-supplied `activation_ref`, `graph_revision_ref`, `accounting_scope_ref`, `definition_anchor_ref`, `run_ref`, and `attempt_seq` — never checked against real Runtime truth. A caller could reserve/deny budget against a fabricated Activation, an unrelated Run, or a graph revision / accounting scope / definition anchor that did not match the real Activation. An existing-request replay returned the old canonical reservation without ever re-validating any of this.

## Fix

Consumed only the existing accepted Runtime read boundaries identified by Task-081 triage (`coordination/results/NYRON-T-20260826-081.md`) — no new cross-owner Contract, per the Task's Accepted Read Boundaries and the Standing Interlock:

- `ActivationRepository.resolve(activation_ref)`
- `RuntimeAuthorityResolver.resolve_current(run_ref)` (instance form of `resolve_current_with`)

Added `BudgetAuthority._prove_runtime_binding(request)`, called at the top of `reserve()` — before `_load_reservation_by_request_ref` (so existing-request replay cannot bypass it), before scope resolution, before any exposure mutation, and before any RESERVED/DENIED insert. It proves, in order:

1. `request.activation_ref` resolves to a real Activation (`ActivationRepository.resolve`); else `RESERVATION_ACTIVATION_UNRESOLVED`.
2. `request.graph_revision_ref == Activation.graph_revision_ref`
3. `request.accounting_scope_ref == Activation.static_accounting_scope_ref`
4. `request.definition_anchor_ref == Activation.module_instance_revision_ref`
   — any mismatch of 2-4 raises `RESERVATION_STATIC_BINDING_MISMATCH`.
5. `request.run_ref` resolves through current Runtime authority (`RuntimeAuthorityResolver.resolve_current`).
6. Runtime authority `activation_ref`/`execution_ref` match the resolved Activation.
7. Runtime authority `run_ref`/`attempt_seq` exactly match the request.
   — any mismatch of 5-7 (including "no current authority at all") raises `RESERVATION_RUNTIME_AUTHORITY_MISMATCH`.

`reserve()`'s scope-resolution call now passes the Activation's own canonical `static_accounting_scope_ref` / `graph_revision_ref` / `module_instance_revision_ref` (not the caller-supplied request fields) into `AccountingScopeResolver.resolve(...)`, so ancestry is always derived from proven Activation truth (requirement 8).

No raw SQL against Runtime-owned tables was introduced; only the two accepted repository/resolver read methods are called.

### Circular-import note (minimal wiring)

`nyron_kernel.execution` (specifically `execution/admission.py`) already imports `nyron_kernel.accounting` at module load time for admission-time scope resolution. A real module-level `from nyron_kernel.execution import ...` inside `budget_authority.py` is therefore circular in both import directions (verified with a fresh interpreter both ways before and after the fix). `BudgetAuthority` never constructs `ActivationRepository`/`RuntimeAuthorityResolver` itself — the caller injects instances and `BudgetAuthority` only calls read methods on them — so no runtime import of `nyron_kernel.execution` is actually needed. The three names (`Activation`, `ActivationRepository`, `RuntimeAuthorityResolver`) are imported under `TYPE_CHECKING` only. Verified all three import orderings (`import nyron_kernel.accounting` first, `import nyron_kernel.execution` first, `import nyron_kernel` top-level) succeed cleanly against the fixed source.
