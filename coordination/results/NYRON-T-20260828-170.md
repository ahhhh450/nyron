## Q1–Q3 — ProductNodeDefinition and Module binding

**Q1.** `ProductNodeDefinition` is a **Product-owned, versioned, immutable-once-published wrapper** around exactly one `module_definition_ref@version`. Its identity is `(product_node_type_ref, product_node_version)`. It requires:
- `product_node_type_ref` (stable identity, e.g. `product.text_input`)
- `product_node_version` (immutable once referenced by any `NodeInstance`)
- `bound_module_ref@version` (exact, no `latest`)
- `product_port_bindings[]` (mapping product-facing ports to the bound Module's declared ports — see Q4)
- `product_config_schema` (may be a strict subset/relabeling of the Module's `config_schema`; MUST NOT loosen or widen the Module's own validation — Product cannot grant itself capability the Module doesn't declare)
- `display_metadata` (label/icon/category/description — non-normative, see Q9)

This mirrors the frozen `ModuleDefinition` identity pattern (`module_ref@version`, Module Report §3) at the Product layer without becoming a second Kernel primitive: `ProductNodeDefinition` is pure presentation/config-surface authority, never execution authority (binding guardrail `Product declaration != execution authority`).

**Q2.** `ProductNodeDefinition` binds an exact `ModuleDefinition@version` by **reference only** (`bound_module_ref@version`), exactly as `ModuleInstanceRevision.module_definition_ref@version` does in the frozen Module contract (Module Report §4). It never copies, shadows, or redeclares Module port/effect/capability contracts — those remain sourced from the Module Registry at resolution time (`ModuleRegistry.resolve`, `registry.py:151`). This avoids duplicating Module identity (binding guardrail `ModuleDefinition != ProductNodeDefinition`).

**Q3.** **Yes** — one exact Module may be exposed by multiple `ProductNodeDefinition`s. Authority: Module Report §33 explicitly states "`DeveloperAgent / ReviewerAgent / Moderator` can be the same `ModuleDefinition`'s different `ModuleInstanceRevision`s" — the same reasoning applies one layer up: `provider.model.invoke@1` may back both a "Chat Node" and a "Summarize Node" `ProductNodeDefinition`, differing only in `product_config_schema` defaults/labels/prompt template metadata, not in Module capability. Minimum stable node-type identity is `product_node_type_ref` (Product-owned, distinct from `module_ref`); two `ProductNodeDefinition`s may share `bound_module_ref@version` but never share `product_node_type_ref`.

## Q4–Q5 — Ports

**Q4.** Minimum `InputPortDefinition` (Product layer, wrapping the Module's frozen port — Module Report §3, §7; Graph Candidate §6):
- `product_port_ref` (stable, Product-owned identity — not the display label)
- `bound_module_port_name` (exact match to a name in the bound Module's `input_port_definitions`)
- `schema` (MUST be schema-identical to the bound Module port's `value_schema`; Product does not invent a second, possibly-divergent schema — Graph Candidate §11: "exact-compatible schema only" until a global Schema/Value Contract exists)
- `activation_mode` (MUST mirror the bound Module port's frozen mode — `TRIGGER | REQUIRED_NEXT | REQUIRED_LATEST | OPTIONAL_LATEST`; Product cannot redefine this, only surface it)
- `connection_policy` (`SINGLE_SOURCE | MULTI_SOURCE`, inherited from the compiled Graph Edge cardinality rule — Graph Candidate §6)
- `default_value_ref?` (Product-only convenience for unconnected optional inputs; resolved to a Packet-equivalent constant at compile time, never a Runtime concept)
- `ordinal` (stable within the owning node type, feeding the frozen `target_port_ordinal` — Clarification C1)

`OutputPortDefinition` is the same shape minus `activation_mode`/`connection_policy` (frozen: output ports declare no activation mode, `schema.py:68`).

**Streaming must be deferred** — nothing in the frozen Module/Graph contracts defines a streaming Packet/Delivery semantic (Module Report explicitly lists "streaming/distributed execution" as out of scope for extensibility without a requirement trace, `AGENTS.md`-class `CLAUDE.md` complexity rule). Any node type needing streaming is out of this slice.

**Q5.** **Confirmed.** Product ports are a presentation/config-binding layer over the Module's declared port contract; the canonical data-flow truth is `Packet -> Delivery` (frozen, Module Report §8-9, Graph Candidate §7/§15). A Product port never carries its own value — it only names which compiled Graph Edge/Port a value flows through. This preserves the guardrail `Product Port != Packet/Delivery canonical truth`.

## Q6–Q7 — NodeInstance and NodeConnection

**Q6.** `NodeInstance` is the **workflow-local placement of one `ProductNodeDefinition`** inside one `VisualWorkflowRevision` (pre-compile). Fields:
- `node_instance_ref` (**definition identity** — logical placement identity that can persist across `VisualWorkflowRevision`s of the same workflow, mirroring Graph's `module_instance_ref`, Graph Candidate §5)
- `node_definition_ref@node_version` (**exact version binding** to `ProductNodeDefinition@version` — no `latest`, mirroring frozen Module pinning, Module Report §4)
- `config_snapshot_ref` (**config snapshot/ref** — immutable, addressable, mirrors `config_ref`/`config_hash` split in `ModuleInstanceRevision`, `revision.py:28-29`: `config_hash` is integrity evidence only, `config_ref` is addressable authority)
- `label?` (**optional label** — non-normative, user-supplied)
- `layout_ref?` (**layout metadata** — pointer to a separate presentation record, see Q9; never inline in workflow truth)

This is a direct product-layer analogue of `ModuleInstanceRevision` (`revision.py:21-48`) — same shape, one layer up, before Graph compilation freezes it.

**Q7.** `NodeConnection` binds **one source `NodeInstance` output `product_port_ref` to one target `NodeInstance` input `product_port_ref`**, within one `VisualWorkflowRevision`. It fails closed on:
- **missing ports/nodes** → `PRODUCT_CONNECTION_UNRESOLVED_ENDPOINT` (mirrors Graph V1 "missing ModuleInstance/Port", Graph Candidate §11)
- **direction mismatch** (input→input, output→output, or output feeding an already-fully-bound `SINGLE_SOURCE` input) → `PRODUCT_CONNECTION_DIRECTION_INVALID`
- **incompatible schema** (source output schema ≠ target input schema, exact-compatible-only per Graph Candidate §6/§11 OQ-01) → `PRODUCT_CONNECTION_SCHEMA_INCOMPATIBLE`
- **duplicate illegal edges** (exact duplicate source-endpoint→target-endpoint pair) → `PRODUCT_CONNECTION_DUPLICATE` (mirrors frozen `G-INV-07`)
- **cardinality overflow** (fan-in into a `SINGLE_SOURCE` port that already has a connection) → `PRODUCT_CONNECTION_CARDINALITY_VIOLATION`

No new cycle semantics are invented: whether a `NodeConnection` topology containing a cycle is legal is entirely delegated to the frozen Graph rule (**every directed cycle must contain an explicit `FEEDBACK` edge**, `G-INV-08`) at compile time — Product only needs to let the author mark a `NodeConnection.role = NORMAL | FEEDBACK` and pass that role through unchanged to the compiled `Edge.role`.

## Q8–Q9 — VisualWorkflowRevision and layout ownership

**Q8.** `VisualWorkflowRevision` is an **immutable snapshot** (mirroring `GraphRevision` immutability, `G-INV-02`) of:
- `workflow_revision_ref` (this revision's identity)
- `workflow_ref` (long-lived logical identity — mirrors `Graph` vs `GraphRevision`, Graph Candidate §4)
- `predecessor_workflow_revision_ref?` (revision lineage, non-branching-authoritative — purely provenance)
- `node_instances[]` (frozen `NodeInstance` set, each pinned to exact `node_definition_ref@version` + `config_snapshot_ref`)
- `node_connections[]` (frozen `NodeConnection` set)
- `entrypoints[]` (which `NodeInstance` input port(s) accept top-level Trigger — see Q11, must resolve to a Graph ingress binding, never a direct Activation, per Clarification D-003/D-005 §1 and D-003/D-010 §1/§2)
- `product_outputs[]` (which `NodeInstance` output port(s) are workflow-level results — purely a Product-facing declaration, carries no Runtime authority by itself)
- `product_metadata` (name/description/tags — non-normative)

Existing revisions are **never mutated**; any semantic change (added/removed/rewired node, changed config, changed entrypoint/output declaration) creates a new `VisualWorkflowRevision` with a new `workflow_revision_ref`, exactly mirroring `G-INV-02`. Conflict on identical `(workflow_ref, predecessor_workflow_revision_ref)` fails closed as `PRODUCT_WORKFLOW_REVISION_CONFLICT` rather than silently branching or overwriting.

**Q9.** Layout/UI metadata (node canvas position, zoom, color, collapsed/expanded state) is owned by a **separate Product presentation record** (`WorkflowLayoutRecord`, keyed by `workflow_revision_ref` + `node_instance_ref`), **not** inside `VisualWorkflowRevision` truth. Authority: this is the simplest safe currently-authorized model, directly required by the binding guardrail `Product layout/UI metadata != Runtime canonical truth` and consistent with Graph's own separation of "Derived, rebuildable state includes ... editor/search indexes, UI layout caches" from canonical definition truth (Graph Candidate §3). Putting layout inside the immutable revision would force a new immutable `VisualWorkflowRevision` (and downstream a *new, semantically-identical* `GraphRevision`) every time a user drags a node on the canvas — real cost with zero correctness benefit, correctly rejected as speculative complexity under `CLAUDE.md` §4's structural-vs-speculative-complexity rule. A layout record keyed by workflow-revision + node-instance can be freely rewritten without touching workflow/graph truth, and is naturally rebuildable/derivable-adjacent state.

## Q10–Q11 — Graph ownership and compile seam

**Q10.** **Confirmed, not rejected.** `GraphRevision` remains the sole owner of executable truth. Authority:
`design/Nyron_Graph_Composite_Frozen_Baseline_v0.1.md` §4: "Runtime pins exact GraphRevision and exact ModuleDefinition versions; no mutable latest/current resolution", and Graph Candidate §15: "Runtime accepts `graph_revision_ref`... Runtime MUST NOT read current draft". `VisualWorkflowRevision != GraphRevision` is preserved exactly as the two are structurally different objects with different owners (Product vs. Graph subsystem) and different mutability triggers (a workflow revision may exist and be inspected/edited-as-draft-successor without ever compiling successfully; a `GraphRevision` only exists once compilation succeeds).

**Q11.** Narrowest compile/projection seam, given what is actually implemented today (`src/nyron_kernel/graph/revision.py`, `GraphRepository.publish`):

```text
VisualWorkflowRevision (Product, immutable, already validated at Product's own V0-level:
                         node/connection referential integrity, port existence,
                         schema/cardinality per Q7)
        │
        ▼
Product Compiler (Product-owned, stateless, deterministic pure function)
        │  for each NodeInstance: resolve ProductNodeDefinition@version
        │    -> exact bound_module_ref@version (Q2) -> exact config_ref
        │  for each NodeConnection: map to (source module_instance_ref,
        │    source_port) -> (target module_instance_ref, target_port)
        │  compute static_composite_path / static_accounting_scope_ref
        │    inputs per existing frozen fields (no new semantics invented)
        ▼
GraphRepository.publish(graph_revision_ref, module_instances[], edges[])
        │  (Graph-owned; MUST be extended — see Finding F-001 — from today's
        │   single-instance signature to accept the full multi-instance +
        │   edge set atomically)
        │  Graph subsystem performs its own frozen V1-V7 validation
        │  (referential integrity, UNRESOLVED_MODULE_REFERENCE, Port/edge
        │  cardinality/schema, topology, execution eligibility)
        ▼
GraphRevision (immutable, executable=true|false, reason_code)
```

Traceability back to the exact `VisualWorkflowRevision`: the compiled `GraphRevision` stores `product_workflow_revision_ref` as **non-authoritative provenance metadata only** (mirrors `static_composite_path` — provenance, not authority, per `Provenance ≠ Authority`, Module Report §24 / §51). Deterministic compile identity: `graph_revision_ref` is derived as a stable hash of `(workflow_revision_ref, ordered node/connection compiled facts)` — same pattern as `Delivery.delivery_ref` being a `sha256` of its uniqueness key (`delivery.py:44-50`) — so recompiling the same immutable `VisualWorkflowRevision` twice yields the same `graph_revision_ref` (idempotent publish, already handled by existing `GraphError("GRAPH_REVISION_IMMUTABLE")` re-publish guard at `revision.py:96-100`, extended to compare full multi-instance contract equality the same way single-instance re-publish already does at `revision.py:129-138`).

Required cross-owner reference: **none new**. The only cross-owner fact needed (which node/port is the workflow's execution ingress) is exactly the "Graph ingress binding" already frozen in Clarification D-003/D-010 §2: "If the Graph ingress binding is unresolved/invalid, execution admission fails closed." Product supplies which compiled Port is the ingress; Graph/Runtime own turning that into a Trigger Packet. **No `ESCALATION_REQUIRED` is triggered** — this seam reuses frozen semantics end-to-end.

## Q13 — Config/version reproducibility

Node config schemas are versioned **per `ProductNodeDefinition@product_node_version`**, itself bound to exactly one `bound_module_ref@version`. A saved `NodeInstance` pins `node_definition_ref@node_version` (not `latest`), exactly mirroring the frozen rule that `ModuleInstanceRevision` pins `module_definition_ref@version` and Runtime "MUST NOT resolve latest/current/compatible latest module/config values" (Graph Candidate §5, Distribution Baseline: "Exact `module_ref@version` resolution is mandatory. No `latest/current/range-compatible` substitution"). Consequence: **a saved workflow remains reproducible when newer Module/ProductNodeDefinition versions are installed**, because compilation always resolves the pinned versions recorded in the already-immutable `VisualWorkflowRevision`/`NodeInstance`, not whatever is newest in the registry at replay time. Upgrade/migration tooling (e.g. "offer to bump all nodes to the newest compatible version") is explicitly **deferred** — it is a separate, later, opt-in authoring action that creates a *new* `VisualWorkflowRevision`, never an implicit mutation of an existing one (Graph Candidate §14: "Import never silently upgrades a version; user-requested upgrade creates a new revision").
