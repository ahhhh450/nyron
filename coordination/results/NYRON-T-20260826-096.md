Finding ID: R-096-01
Type: IMPLEMENTATION
Severity: BLOCKING
Location: src/nyron_kernel/recovery/repository.py:126-132 (`RecoveryRepository.open_case`, the `_active_case` reuse branch), contrasted with lines 385-395 (`_require_open_replay`, used only for the `open_request_ref`-keyed replay branch)
Evidence:
- `open_case` has two idempotency branches. The `open_request_ref`-keyed branch (`_case_by_open_request` at line 126) enforces full-identity equality via `_require_open_replay` and raises `RECONCILIATION_CASE_IDENTITY_CONFLICT` on any mismatch across all constructor fields (reconciliation_case_ref, open_request_ref, subject_owner_ref, subject_ref, reason_code, opened_by_ref, max_attempts, retry_policy_ref, backoff_seconds, deadline, escalation_policy_ref, caused_by_ref).
- The subject-condition-keyed branch (`_active_case(subject_owner_ref, subject_ref, reason_code)` at line 130) performs no such check: if an active case already exists for that (owner, subject, reason) tuple, it is returned as-is regardless of what `max_attempts`, `retry_policy_ref`, `backoff_seconds`, `deadline`, `escalation_policy_ref`, `opened_by_ref`, or `caused_by_ref` the new caller supplied.
- Reproduced directly: opening `("effect-authority", "effect:unknown", "EFFECT_DISPATCH_HISTORY_UNKNOWN")` first with `opened_by_ref="requester:A", max_attempts=3, retry_policy_ref="retry:fixed", backoff_seconds=10, deadline=1000, escalation_policy_ref="escalate:human"`, then again with a different `open_request_ref` and `opened_by_ref="requester:B-DIFFERENT", max_attempts=99, retry_policy_ref="retry:DIFFERENT", backoff_seconds=99999, deadline=99999, escalation_policy_ref="escalate:DIFFERENT"` returns the identical first-case row (`case:1`, `max_attempts=3`, `deadline=1000`, ...) with no error and no signal to the second caller that its supplied parameters were discarded.
- `tests/kernel/test_recovery_reconciliation_foundation.py::test_stable_open_identity_and_conflicting_binding_fail_closed` only exercises the `open_request_ref`-keyed conflict path (it reuses `open_request_ref="open:1"` while changing `subject_ref`); it never exercises a second, distinct `open_request_ref` for the same subject condition with divergent bounds/policy fields, so this gap has no regression coverage.
Impact:
- This directly matches the Task 096 required review question "ReconciliationCase identity/opening is stable and idempotent ... without duplicate active cases or unsafe immutable-binding acceptance." Case creation is correctly deduplicated (no duplicate active case), but a second, distinct open request for the same unresolved condition can carry materially different bounds (e.g. a caller that intends `max_attempts=99`/`deadline=99999`) and have that intent silently discarded in favor of whatever the first opener happened to submit, with zero error surfaced. Given `ReconciliationCase` fields are meant to be immutable once created (enforced by the `reconciliation_case_identity_immutable` DB trigger for UPDATEs), this Python-level path lets a divergent binding request bypass that protection entirely rather than fail closed, which is inconsistent with every other idempotency path in this same file (evidence append, attempt record, resolution record, and the sibling `open_request_ref` branch all fail closed on a content mismatch).
Local implementation fix appears possible without Contract change: YES — extend the same identity-consistency check already implemented in `_require_open_replay` to the `_active_case` reuse branch (i.e., compare the new request's non-key-derived fields against the existing active case and raise `RECONCILIATION_CASE_IDENTITY_CONFLICT` on mismatch, exactly as already done for the `open_request_ref` replay branch). This is a bounded, local change inside the existing `open_case` method and does not require any change to the frozen Accounting/Recovery design.
Required Resolution: Add binding-consistency validation to the `_active_case` reuse path in `open_case` (or explicitly document, with Lead disposition, that only `(subject_owner_ref, subject_ref, reason_code)` is authoritative identity for case reuse and that other fields are intentionally advisory/first-writer-wins), then add a regression test covering a second distinct `open_request_ref` with divergent bounds for the same subject condition.

Finding ID: R-096-02
Type: IMPLEMENTATION
Severity: NON_BLOCKING
Location: src/nyron_kernel/recovery/repository.py:197-253 (`RecoveryRepository.record_retry`)
Evidence:
- `record_retry` computes and durably stores `next_retry_at` (exponential backoff capped by `deadline`), but nothing in `record_retry` checks the caller's current time against the case's own previously stored `next_retry_at` before accepting a new attempt. A caller (or a buggy scheduler) can invoke `record_retry` with a fresh `attempt_ref` immediately after a prior attempt, before `next_retry_at` has elapsed, and the call succeeds, advancing `attempt_count` and potentially reaching `ESCALATED` far faster than the stored backoff schedule implies.
- No test in `tests/kernel/test_recovery_reconciliation_foundation.py` exercises calling `record_retry` before the previously recorded `next_retry_at`.
Impact:
- Backoff is durably recorded (satisfies "committed retry schedule decisions" from design section 16.3) but is not semantically enforced by the repository itself, so "provider observation retry is safe" (AR-GATE-5) is only as strong as whatever external caller/scheduler chooses to respect `next_retry_at`; this repository provides no fail-closed backstop against a caller that ignores it. Design section 16.3 does state backoff is "Recovery scheduling metadata only" and does not itself mandate repository-level enforcement, and Task 092's explicit non-goals exclude any scheduler/worker implementation, so this may be an intentional layering (enforcement belongs to a future caller/scheduler) rather than a defect in this foundation slice. Flagging per Task 096's explicit review question on this point rather than asserting a definite defect.
Local implementation fix appears possible without Contract change: YES — if enforcement is desired at this layer, `record_retry` could reject a call with `now < case.next_retry_at` (a new `RecoveryError` code), without any Contract change.
Required Resolution: Orchestrator/Lead disposition on whether repository-level backoff enforcement is in-scope for this foundation Task or deferred to a later scheduler-owning Task; if in-scope, add the check and a regression test.
