## A. Task-136 F01 — Raw-Network Bypass / Non-Bypassable Dispatch Boundary

**Frozen requirement (primary text, D-008 Candidate §9.1):**

> "Network access must occur through a controlled adapter/proxy or through an IsolationProfile that enforces equivalent destination restrictions. Modules must not receive unrestricted raw sockets by default."

This is a disjunction: a controlled-adapter-only enforcement mechanism is one of the two frozen-compliant paths — full OS-level sandboxing is not the only route.

**Current state:** `TRUSTED_SAME_PROCESS_ISOLATION_PROFILE` (`src/nyron_kernel/host/isolation_profile.py`) declares `network_enforcement_claim=BoundaryEnforcementClaim.UNRESTRICTED` and `module_code_trust_class=ModuleCodeTrustClass.TRUSTED_BUILTIN`, with the explicit, honest `host_escape_assumptions`: "module code is trusted and executes inside the Nyron host process" / "no hostile-code containment boundary is enforced by this profile." `BoundaryEnforcementClaim` is a three-value enum (`MEDIATED`, `OS_RESTRICTED`, `UNRESTRICTED`), not binary — `MEDIATED` already exists as a frozen, defined claim value and is not currently used by any registered profile.

**Threat model actually in force for the first real slice:** only `TRUSTED_BUILTIN`-class Module code will exist (the LLM Product Node's builtin Module + one trusted Provider adapter). Track B (Module Ecosystem) has not enabled third-party/untrusted Module loading — `HOSTILE`-class code is not a live threat for this slice. Task-136 F01's own Required Resolution text is explicit that a trusted-same-process profile may remain acceptable "if... document[ed] it truthfully as not enforcing hostile Module egress; do not advertise the bounded network Capability as a sandbox boundary against that code" — i.e. F01 does not require `OS_RESTRICTED`/process sandboxing for a `TRUSTED_BUILTIN`-only threat model; it requires that the *actual* egress path be truthfully mediated for the code that exists.

**Disposition:** F01 can be closed for the first real slice's actual threat model with a **bounded** change: a new registered `IsolationProfile` (e.g. `TRUSTED_SAME_PROCESS_MEDIATED_NETWORK_ISOLATION_PROFILE`) that changes only `network_enforcement_claim` to `MEDIATED`, backed by a genuinely-true enforcement fact — the real transport library import (whatever HTTP client is chosen) exists in exactly one trusted adapter module, and no Module-reachable API (`RuntimeContext`, `CapabilityHandle`, `ResourceHandle`, the broker's public methods) exposes that import, a raw socket, or an unrestricted OS API to Module code. This is independently source-testable (the same style of `grep`-based negative-import test already used and accepted in Task 173's own review, and already an established pattern in `tests/kernel/test_isolation_profile_trusted_host.py`). `raw_os_api_access_claim` and `filesystem_enforcement_claim` are unaffected and remain exactly as they are — F01 is scoped to network bypass specifically; broadening the claim further is out of scope and not required. `OS_RESTRICTED`/process-level sandboxing remains correctly deferred until untrusted Module loading is actually enabled (a Track B decision, not part of this gate).

## C. Task-136 F03 — Network Effect / Historical Outcome

Task 184 (independently reviewed PASS by this session's own Task 185) generalized `EffectAuthority` to a second bounded effect class (`MODEL_INVOKE`) with the full PREPARED/ACTIVE/UNKNOWN/FENCED/COMPLETED lifecycle, a deterministic per-class conflict scope, and `historical_outcome` tracked orthogonally to `state` — this is real, reusable progress toward F03, not merely the pre-184 single-filesystem-class machinery Task-136 originally reviewed.

**What is not yet sufficient:** the current `_commit_model_invoke_completed` (`src/nyron_kernel/effect/authority.py`, read in full in this session's Task 185 review) unconditionally records `dispatch_boundary: "BOUNDED_LOCAL_SIMULATION"` / `external_consequence: "NONE"` and always transitions straight to `COMPLETED` — this is correct and truthful *only* for the current no-real-I/O simulated path. A real network dispatch cannot reuse this exact method, because a real HTTP call's outcome is not unconditionally known: a timeout or disconnect before a reliable response must resolve to `UNKNOWN` (D-008 §11.6 / `EIW-INV-13`), not fabricated `COMPLETED`.

**Required, bounded extension:** add one new class-scoped completion path (e.g. `_commit_model_invoke_dispatched_with_evidence`) that a real adapter calls with the *actual* observed outcome after attempting real dispatch — truthful `dispatch_boundary`/`external_consequence`/response-identity evidence on success, or simply *not calling it* (leaving the operation `ACTIVE`) on ambiguity, so that Task 184's already-built, already-reviewed `recover()` logic for `MODEL_INVOKE` (which already fails closed to `UNKNOWN` whenever `state == "ACTIVE"` or `dispatch_admission_ref is not None` without independent completion evidence — verified directly by this session's own Task 185 review) correctly and automatically classifies any crash/timeout/ambiguity as `UNKNOWN` with no new recovery logic needed. `FENCED` continues to mean only proven pre-admission non-dispatch (`request_revoke`, unchanged); `EIW-INV-32`/Amendment 001 (`FENCED != retry clearance`) is unaffected since no retry code is added. This is a second, small, class-scoped method sharing the exact existing state machine — not a new Effect ownership model or a new architecture.

## D. Task-180 F-004 — `effect_class` Validation at the Network Boundary

Confirmed by direct re-read of `SimulatedNetworkBoundaryBroker.admit()` at the exact accepted base: the method reads `effect["state"] != "PREPARED"` and checks the full authority tuple, but never reads or compares `effect["effect_class"]` — any `PREPARED` `EffectOperation` of *any* class (including the existing filesystem class) currently satisfies admission, provided its other fields happen to match. **Required closure is a single field + a single equality check**: add an `expected_effect_class: str` field to `NetworkAdmissionRequest` (or equivalently read `effect["effect_class"]` and compare it against a value the calling adapter is required to supply, matching the same pattern already used for `dispatch_admission_ref` matching two lines above it) and raise `NetworkBoundaryError("NETWORK_EFFECT_CLASS_MISMATCH")` on mismatch. For the first real slice the expected class is `EffectAuthority.MODEL_INVOKE_EFFECT_CLASS`; the field should remain caller-supplied (not hardcoded to `MODEL_INVOKE`) so a later, distinct network-driven effect class does not require re-touching this file. No architecture change; no registry.

## E. Task-173 F-001 — Connection-Origin Reuse Evidence

Task 173's own Finding is precise: `EffectiveDestination.connection_origin` is compared only against the same caller-constructed object's own `requested` field — a self-consistency check, not a check against any durably recorded fact about a real connection's actual prior origin. No such durable record exists anywhere in the current schema, and building one (a `connection_ref → first-established-origin` durable table, TTL/freshness rules for a reused peer, HTTP/2-origin-coalescing defenses) is exactly the kind of speculative machinery `AGENTS.md` §4 and `REVIEW_PROTOCOL.md` §5 direct against building ahead of a real, current requirement.

**The first single-turn LLM Product Node slice has no requirement for connection reuse**: one Attempt issues at most one real provider request; there is no multi-turn/streaming/session concept in scope (explicitly excluded by this Task and by the entire dependency chain up to and including LLM Product Node implementation itself, which is scoped non-streaming/single-turn). Per Task 186's own instruction, this Task **explicitly recommends `NO CONNECTION REUSE IN FIRST SLICE`**: the real adapter must open one connection per real dispatch and must always construct `EffectiveDestination(reused_connection=False, connection_origin=requested, ...)` — which trivially and truthfully satisfies `admit()`'s existing self-consistency check with no exploitable gap, because there is no reused connection whose real origin could diverge from what is claimed. `NYRON-T-20260828-173-F-001` remains correctly `OPEN` and deferred (not closed, not silently forgotten — restated, not invented around) until a future Task actually needs connection reuse and builds the durable origin evidence Task 173 specified as the precondition.

## F. Credential Boundary

Independently re-confirmed at the accepted base (already verified in this session's Task 185 review and Task 173's own independent review, both cross-checked again here): `ResolvedCredentialHandle` is constructible only via the module-private `_issue_resolved_credential()` factory gated by an identity sentinel, is one-shot-consumed via `_use_once`, has `__slots__` (no `__dict__`), redacted `__repr__`/`__str__`, and a `__reduce__` that raises on pickling — and no reference to the real class exists anywhere outside `host/credential/foundation.py` in the accepted tree. `CredentialResolutionAuthority.use_resolved()` delegates to an injected `CredentialResolver`; the production default (`UnconfiguredCredentialResolver`) unconditionally fails closed with no environment/config/keychain fallback.

**For the first real slice:** credential resolution must happen entirely inside the same one trusted adapter function that performs the real HTTP call (§B/§A) — the resolved handle is consumed exactly once to attach the secret directly to the outgoing request inside that call, and the raw value goes out of scope immediately after, using the existing one-shot pattern unchanged. **The smallest sufficient concrete `CredentialResolver` implementation is a single environment-variable-backed resolver** (read one operator-configured env var, fail closed if unset/empty) — not a generic multi-backend/vendor secret-store abstraction, which nothing in frozen contract or current requirement justifies for a first single-turn slice with exactly one credential consumer. `ResolvedCredentialHandle`/secret values must never be placed on `RuntimeContext`, a `CapabilityHandle`, a `ResourceHandle`, or any Module-facing broker method signature — confirmed unchanged and unnecessary to change, since the resolved handle is consumed and discarded entirely within trusted host code before any Module-visible object is constructed.
