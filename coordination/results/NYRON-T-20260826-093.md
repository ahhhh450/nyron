## Findings

### F-093-001

- Type: `IMPLEMENTATION`
- Severity: `NON_BLOCKING`
- Location: `src/nyron_kernel/store/sqlite_store.py` — `create_usage_ledger_schema()` (new `usage_facts` / `usage_adjustment_facts` tables)
- Evidence: Both new tables carry `BEFORE UPDATE` immutability triggers, but neither has a `BEFORE DELETE` trigger. A caller that bypasses the Python API (raw SQL through `SQLiteStore.connection`) can still `DELETE` a committed immutable fact. This is mechanically identical to the project's already-accepted open debt `NYRON-T-20260826-078-F-001` ("no explicit DELETE immutability guard for canonical Accounting policy/reservation rows; current production exposes no delete path"), and matches the accepted Gate-6A table pattern (all existing immutability triggers in `sqlite_store.py` are `BEFORE UPDATE`; no `BEFORE DELETE` trigger exists anywhere in the reviewed content). The Task-090 Result claim is scoped accurately ("BEFORE UPDATE triggers ... on any update attempt"); it does not claim DELETE protection.
- Impact: If any future path introduces a raw-SQL DELETE, an immutable Usage/Ledger fact could be removed. No such production path exists today (no DELETE statement in reviewed production content; Python API exposes no delete operation), so there is no current correctness exposure.
- Recommended routing (not a fix implementation): track alongside existing debt `078-F-001` in the Orchestrator's open-debt set; the later Codex exact-SHA semantic review may disposition whether the frozen "Committed UsageFacts are immutable" wording requires DELETE protection for the new tables. Not blocking for A2 routing.
