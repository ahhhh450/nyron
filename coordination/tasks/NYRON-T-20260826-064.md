## Questions the Candidate MUST Resolve

The design must give one concrete, minimal answer to every point below.

### 1. Module-facing delivery model

Choose and specify exactly whether the Module receives:

- a callable broker inside `RuntimeContext`;
- inert identity handles plus one callable broker;
- another equally narrow concrete arrangement.

Do not leave callable-vs-inert ambiguous.

### 2. Concrete Python invocation ABI

Define one concrete Module-side Python call shape for the first bounded live effect.

The ABI must include:

- broker object/type identity;
- method name;
- exact arguments;
- exact return type/value shape;
- exact synchronous error/failure mapping.

Do not create a generalized plugin SDK.

### 3. First bounded effect surface

Use only the already accepted bounded Effect class if it can safely demonstrate mediation:

`nyron.kernel.managed-resource-bounded-write@1`

Do NOT introduce workspace/process/network/model/browser APIs or new effect classes.

The Module must not receive or choose a raw managed-root path.

If the existing bounded effect cannot support a safe minimal broker without changing frozen semantics, state a blocking Architecture Finding rather than inventing another effect surface.

### 4. Handle -> request binding

Specify exactly how Module-visible Capability/Resource identity is converted into the trusted Host-side request passed to Effect Authority.

The design must answer:

- which handle/ref the Module supplies or selects;
- who resolves it;
- how the broker proves the selected handle belongs to the current RuntimeContext;
- who supplies `operation_ref`;
- who supplies AttemptAuthority/current attempt facts;
- who supplies `capability_grant_ref`, `resource_ref`, `resource_lease_ref`;
- who supplies `caused_by_ref` and payload;
- what the Module is forbidden to supply.

No raw Owner object may be passed to Module code.

### 5. Real authority boundary

The Host/broker must NOT treat RuntimeContext handles, cached booleans, or old validation as authority.

Specify that the actual effect request crosses the existing accepted Effect Authority dispatch-admission boundary and therefore revalidates:

- current Attempt/fencing;
- CapabilityGrant;
- ResourceLease;
- Gate-4 same-resource conflict barrier;
- target/resource invariants.

Plain check-then-use remains forbidden.

### 6. Operation identity ownership

Specify who creates/owns `operation_ref` for a Module-requested effect and its replay/idempotency rule.

The Module must not be able to reuse an operation_ref with different payload/meaning or collide with another invocation.

Do not define semantic retry clearance beyond current frozen rules.

### 7. Return / error mapping

Specify the synchronous Module-visible outcome of the broker call for at least:

- accepted + completed bounded effect;
- admission rejected;
- UNKNOWN / ambiguous outcome;
- module/request shape error.

Do not fabricate certainty from FENCED/UNKNOWN.

If the correct design requires `Suspended`, async callbacks, background workers, or new Runtime scheduling semantics, STOP with a blocking prerequisite instead of expanding this clarification.

### 8. RuntimeContext / handle field-level contract

Clarify only the fields needed by the first live broker slice.

State whether the Task-061 candidate shapes are:

- acceptable as-is;
- acceptable with explicit corrections;
- not adopted.

Do not silently canonize Task-061 code.

Capability handle must not embed reusable cached authority truth.
Resource handle must not expose raw Resource lifecycle ownership or managed-root path.

### 9. Trusted-mode threat claim

The clarification must explicitly preserve:

- TRUSTED MODULE MODE only;
- in-process Python is not hostile-plugin isolation;
- no claim that dataclass immutability/type checks sandbox malicious Python;
- hostile third-party support requires real enforceable isolation later.

### 10. Standing interlocks

The candidate must keep:

`NYRON-T-20260825-038-F-001` NOT ACTIVATED:
- no Module filesystem API;
- no raw path/managed-root exposure;
- no less-trusted namespace writer model.

`NYRON-T-20260826-043-F-001` NOT ACTIVATED:
- synchronous only;
- no threads/workers/process execution concurrency;
- no async callbacks;
- no connection pool;
- no changed SQLite linearization model.

## Mandatory Invariants

The candidate must state machine-reviewable invariants equivalent to:

1. Module never receives StateStore/SQLite/Owner objects/raw Resource path authority.
2. Module-visible handles are selectors/opaque identities, not authority decisions.
3. A broker call cannot authorize external mutation without fresh accepted Effect Authority admission.
4. Only handles belonging to the exact current RuntimeContext may be selected.
5. Broker/Host never directly mutates canonical Capability/Resource/Effect/Run state.
6. Module cannot choose current Attempt/fencing facts supplied to Effect Authority.
7. Module cannot choose a raw target path for the bounded write.
8. FENCED/COMPLETED active-conflict semantics are not semantic retry authorization.
9. UNKNOWN remains uncertain and is never converted to success/failure certainty by Host.
10. Trusted Module Mode is not hostile-code isolation.
