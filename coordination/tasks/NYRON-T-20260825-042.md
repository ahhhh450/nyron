### D. Real authority-consumption linearization

This is the first Task allowed to implement actual authority-use admission.

A plain sequence of advisory validation followed by use is forbidden:

`plain check-then-use is forbidden`.

For the exact `operation_ref`, the dispatch boundary MUST establish one serializable/linearizable order against all required current authority dimensions:

- Runtime current Attempt/fencing;
- CapabilityGrant exact identity, ACTIVE/time validity, exact Attempt binding and scope;
- Resource exact identity/state;
- ResourceLease exact identity, ACTIVE/time validity, exact Attempt binding and Resource binding.

The admission must be durably identifiable on the EffectOperation itself or an EffectOperation-owned exact admission record. Do **not** build a generalized reusable authority permit/ticket framework.

If revoke/release/expiry/stale authority wins before admission, no external mutation may begin.

If exact effect admission wins while all authority is current, a later revoke/replacement belongs to later in-flight handling and must not retroactively erase that admission.

Use the narrowest transaction/fencing mechanism that actually proves the ordering. If current SQLite transaction semantics are insufficient, stop with a Finding rather than claiming linearization.

### F. Bounded external evidence and crash windows

For this concrete trusted local-file mutation, use the narrowest evidence protocol needed to recover from:

1. crash/stop after PREPARED but before dispatch admission;
2. crash/stop after dispatch admission but before external mutation;
3. crash/stop after external mutation but before COMPLETED commit.

Requirements:

- PREPARED alone never proves dispatch;
- dispatch-admission evidence alone never proves the file mutation occurred;
- exact externally observable target + payload hash may prove COMPLETED for this concrete effect when exact evidence matches;
- mismatched/ambiguous external state becomes `UNKNOWN`, never guessed COMPLETED;
- recovery must not blindly duplicate an uncertain mutation;
- absence may be treated as non-completion only when this concrete trusted adapter contract can authoritatively establish that conclusion; otherwise UNKNOWN.

Do not generalize this into Recovery/Reconciliation subsystem implementation.
