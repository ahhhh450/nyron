## Objective

Implement a small, deterministic localization/i18n foundation for Nyron that supports **Simplified Chinese and English now** and allows later languages to be added without changing Kernel/Runtime semantics or hard-coding a closed language enum.

Current built-in locales:

- `zh-CN` — Simplified Chinese
- `en-US` — English

The implementation must make future locale addition straightforward through additional catalog data / registration, so languages such as Thai, Japanese, Korean, Spanish, etc. can be added later without redesigning the localization API.

This Task is **localization infrastructure**, not an LLM-based machine-translation system.

## Required Semantics

### 1. Non-Kernel boundary

Localization MUST NOT be implemented under `src/nyron_kernel/` and MUST NOT create or modify canonical Owners, Runtime admission, Packet/Delivery/Activation, Capability, Resource, Effect, Accounting, Recovery, PWP, Human Interaction, Distribution, or external-effect semantics.

Use a separate Product-support package, preferably:

`src/nyron_i18n/`

This preparatory support work does not activate the broader Track E Product/Visual Workflow implementation.

### 2. Open locale model

Do not define a closed enum that limits the system permanently to Chinese/English.

The public API must accept locale identifiers as extensible locale tags/IDs. Built-in support is currently only `zh-CN` and `en-US`, but another locale catalog must be registerable/loadable without changing the core translation lookup algorithm.

A lightweight normalization/validation policy is allowed. Do not implement a full BCP-47 parser unless genuinely required.

### 3. Catalog-driven localization

Localized user-facing strings must be data-driven rather than scattered language conditionals such as:

```python
if language == "zh": ...
elif language == "en": ...
```

Provide a minimal catalog format and loader/registration path.

Preferred simple shape:

```json
{
  "locale": "zh-CN",
  "messages": {
    "common.ok": "确定"
  }
}
```

Equivalent minimal design is acceptable if simpler and equally extensible.

### 4. Deterministic lookup and fallback

Provide a small localization API that can at minimum:

- report available registered locales;
- resolve a message key for a requested locale;
- use a configured/default locale when the requested locale is unavailable or a key is missing;
- fail deterministically when neither requested nor fallback catalog can supply the key;
- support safe named placeholder interpolation for strings that require values.

The default built-in locale should be explicit and configurable by the service/factory; do not hide it in mutable global process state.

### 5. Built-in Chinese / English catalogs

Ship initial `zh-CN` and `en-US` catalogs with a small shared baseline vocabulary sufficient to prove the mechanism, for example common Product-shell terms such as:

- OK / Confirm
- Cancel
- Yes
- No
- Back
- Loading
- Error
- Retry
- language display names

Keep the initial catalog intentionally small. Do not invent a full Product UI before Track E begins.

### 6. Future language extension proof

Tests must prove that a synthetic third locale can be added at runtime or loaded from an additional catalog without modifying the localization core implementation.

The test locale may be a tiny fixture and does not need to become a shipped Product language.

## Constraints

- Keep implementation small and readable.
- Avoid generic framework/factory/registry layers unless directly needed by the required extensibility.
- Do not over-engineer future language support; one simple catalog registration/loading seam is sufficient.
- No module import should perform mutable global registration as a hidden side effect.
- Catalog validation must reject malformed top-level structure, blank locale IDs, non-string keys/values, and duplicate/conflicting registration for the same locale unless semantics are explicitly identical and treated idempotently.
- Placeholder interpolation errors must fail clearly rather than silently producing corrupted text.
- UTF-8 throughout.

## Validation

Add focused tests proving at minimum:

1. built-in `zh-CN` catalog loads and resolves expected Chinese strings;
2. built-in `en-US` catalog loads and resolves expected English strings;
3. requested missing locale falls back to the configured default locale;
4. missing key in requested locale falls back to the default locale when available;
5. missing key in both requested/default catalogs fails deterministically;
6. named placeholder interpolation works in both Chinese and English;
7. missing interpolation values fail clearly;
8. malformed catalog data is rejected;
9. conflicting duplicate locale registration fails closed;
10. identical registration may be idempotent if the implementation chooses to support it;
11. a synthetic third locale is added/loaded without changing core localization code and resolves correctly;
12. existing kernel test suite remains unaffected/green to the extent available in the execution environment.
