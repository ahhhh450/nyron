## Required Conflict Semantics

For the EffectOperation currently being admitted, let:

- `operation_ref = CURRENT`
- `resource_ref = X`

Admission must fail closed if another row exists such that:

```text
resource_ref = X
AND operation_ref != CURRENT
AND state IN (
  PREPARED,
  ACTIVE,
  REVOKE_REQUESTED,
  UNKNOWN
)
```

Minimal current scope is the existing effect class / managed-resource effect family already represented by the current EffectOperation schema. Do not invent a generalized multi-dimensional conflict engine.

### Conflict-relevant states

The following remain blocking:

- `PREPARED`
- `ACTIVE`
- `REVOKE_REQUESTED`
- `UNKNOWN`

Reason: each still carries an unresolved active or historical-consequence ambiguity sufficient to fail closed for the same resource.

### Non-blocking states

The following do **not** block active-conflict admission:

- `FENCED`
- `COMPLETED`

But this means only that the **active conflict barrier** is clear.

It must never mean:

- no historical effect happened;
- semantic retry is safe;
- previous completion/fence evidence authorizes replay;
- replacement/retry authority is granted.

`FENCED != semantic retry clearance` remains load-bearing.

## Exact Identity / Scope Rules

### 1. Stale R1 vs current R2

R1 and R2 share the same `run_ref` but have different `attempt_seq`.

If stale R1 has a conflict-relevant row on resource X and current R2 tries to admit a new operation on X:

**REJECT.**

Never use:

```text
run_ref != R2.run_ref
```

That predicate is forbidden because it would exclude stale R1 from the barrier.

### 2. Same Attempt overlap

If another operation in the same current R2 Attempt already targets X and is conflict-relevant:

**REJECT.**

There is no same-Attempt exemption.

### 3. Cross-Run / Cross-Activation overlap

If an unrelated Run/Activation has a conflict-relevant operation on X:

**REJECT.**

There is no cross-Run exemption.

### 4. Self exclusion

The admission query must exclude only the exact current `operation_ref` itself.

Do not exclude its Run, Attempt, Activation or Execution.

## Mandatory Tests / Adversarial Validation

At minimum:

1. **Stale-R1-vs-R2 exact defect regression**

   - stale R1 has each conflict-relevant state in turn on resource X: `PREPARED`, `ACTIVE`, `REVOKE_REQUESTED`, `UNKNOWN`;
   - R2 attempts a distinct operation on X;
   - admission is rejected in every case.

2. **Same-Attempt overlap**
   - two distinct R2 operation_refs on X;
   - first remains conflict-relevant;
   - second admission rejected.

3. **Cross-Run overlap**
   - unrelated Run/Activation has conflict-relevant operation on X;
   - current operation admission rejected.

4. **Only FENCED / COMPLETED history remains**
   - rows on X are only `FENCED` and/or `COMPLETED`;
   - new current operation may be admitted;
   - its own normal mutation/evidence path is unaffected by historical rows.

5. **UNKNOWN remains blocking**
   - explicit direct regression; UNKNOWN must not be treated as terminal clearance.

6. **Self-exclusion only**
   - the current PREPARED row must not block itself;
   - another operation from same Run/Attempt must still block.

7. **FENCED != retry clearance**
   - prove admission barrier does not inspect or interpret old `fence_evidence` / `completion_evidence` to infer semantic retry safety;
