## Blocking Correction — 067-F-001

Task 067 proved that v0.2's rule "resolve canonical state first, then classify" is insufficient when the *current Module request itself* has a different payload under an already-existing `operation_ref`.

Accepted `EffectAuthority.prepare()` / `_require_identical_replay` raises:

`EFFECT_OPERATION_IDENTITY_CONFLICT`

while leaving the already-existing row unchanged. That row may already be any of:

- `PREPARED`
- `ACTIVE`
- `REVOKE_REQUESTED`
- `FENCED`
- `COMPLETED`
- `UNKNOWN`

The corrected design MUST represent two different truths without conflating them:

1. **Current request truth:** the Module's present request conflicts with the already-bound operation identity and therefore is NOT the request that produced the existing row.
2. **Existing operation truth:** the canonical operation with that identity may itself be completed, ongoing, fenced, or unknown.

The existing row's state MUST NOT be reported as the outcome of the current mismatched request.

### Required precedence rule

The candidate must explicitly define request-identity conflict as a higher-level classification condition than ordinary state-to-result mapping.

At minimum:

- if underlying `EffectError.code == "EFFECT_OPERATION_IDENTITY_CONFLICT"`, the broker MUST NOT return `BoundedWriteDispatched` merely because the existing row is `COMPLETED`;
- it MUST NOT return ordinary `BoundedWriteRejected` while hiding that the existing row is still `ACTIVE` or `REVOKE_REQUESTED`;
- it MUST NOT convert an existing `UNKNOWN` row into ordinary rejection or make the current mismatched request itself appear to be the source of that UNKNOWN;
- canonical row state remains important context, but it is context about the pre-existing operation, not proof about the mismatched request.

### Required public result shape

Define one explicit dedicated identity-conflict result type. Preferred minimal shape:

```text
BoundedWriteIdentityConflict
- operation_ref: str
- existing_state: str
- reason_code: str   # fixed literal EFFECT_OPERATION_IDENTITY_CONFLICT
```

An equivalent equally explicit shape is allowed only if it preserves the same two truths without ambiguity.

`existing_state` must be the exact canonical state returned by `EffectAuthority.resolve(operation_ref)` and may be one of the accepted EffectOperation states. It is informational truth about the pre-existing operation only.

The Module-visible semantics MUST state:

- the current mismatched request was not accepted as an identical replay;
- `existing_state == COMPLETED` means the **prior bound operation** completed, not the current different-payload request;
- `existing_state in {ACTIVE, REVOKE_REQUESTED, PREPARED}` means prior work is still in a nonterminal/ongoing state and must not be hidden behind an ordinary rejection category;
- `existing_state == UNKNOWN` preserves uncertainty about the prior operation while still stating the current request is an identity conflict;
- `existing_state == FENCED` remains only state truth about the existing row and gives no semantic retry clearance.

Do not infer or design new retry authorization from this result.

### Required classification order

The corrected candidate must give an exact decision table / algorithm equivalent to:

1. validate broker-level Module input shape/context membership;
2. derive `operation_ref`;
3. call accepted `EffectAuthority.execute(request)`;
4. if it returns `COMPLETED`, return `BoundedWriteDispatched`;
5. if it raises `EffectError`:
   - if `error.code == EFFECT_OPERATION_IDENTITY_CONFLICT`:
     - resolve exact existing row;
     - return dedicated identity-conflict result carrying exact existing canonical state;
     - never reinterpret that row state as the current request's result;
   - otherwise resolve exact row and apply the already-accepted v0.2 mapping:
     - `COMPLETED` -> `BoundedWriteDispatched` only for the same request identity;
     - `UNKNOWN` -> `BoundedWriteUnknown`;
     - definite non-UNKNOWN non-completed state -> ordinary `BoundedWriteRejected` with truthful error code;
     - broker pre-operation shape rejection remains `BoundedWriteRejected(operation_ref=None, BROKER_*)`.

If an identity-conflict error is observed but `resolve(operation_ref)` unexpectedly returns `None`, define one fail-closed Host-fault behavior. Do not fabricate an `existing_state` and do not report success.
