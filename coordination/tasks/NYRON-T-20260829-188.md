## Why This Task Exists

The accepted Node Foundation v0.1 successfully proved persistence, immutable VisualWorkflowRevision, NodeInstance/NodeConnection, deterministic Product-to-Graph compilation, restart/replay, Graph multi-instance publication and pure/mock end-to-end execution.

However, current Product implementation hard-requires every `ProductNodeDefinition` to bind exactly one `ModuleDefinition@version`, and the compiler resolves every node to a `ModuleInstanceRevision`.

Current Product direction now requires a broader Node System:

```text
Node System
  ├─ Built-in / Pure Node
  ├─ System-backed Node
  ├─ Module-backed Node
  └─ Composite Node
```

Node is the workflow-language abstraction. Module is one optional capability source. They may integrate, but MUST NOT be equivalent.

This Task determines the smallest correct generalization path without discarding accepted work and without inventing unfrozen Runtime authority.

Mandatory principles:

```text
Node System != Module System
NodeDefinition != NodeInstance
VisualWorkflowRevision != GraphRevision
```

## Core Questions

### B. General NodeDefinition Contract

Determine the minimum general `NodeDefinition` / `ProductNodeDefinition` contract that does not require a Module binding.

At minimum answer:

1. Which fields are common to all node kinds?
2. How are stable input/output ports represented independently of Module ports?
3. How is config schema represented?
4. How is execution behavior referenced without hardcoding node type switches in Workflow Core?
5. How are Node definition versions pinned so old workflows remain reproducible?
6. How are ACTIVE / DEPRECATED / DISABLED / UNAVAILABLE states represented without deleting historical identity?

Do not invent execution authority merely for Product convenience.

### C. NodeExecutionBinding

Evaluate whether a tagged execution-binding contract is sufficient, conceptually similar to:

```text
NodeExecutionBinding
  kind = BUILTIN | SYSTEM_CAPABILITY | MODULE | COMPOSITE
  binding_ref / version / contract data
```

For each kind, define the minimum ownership boundary and compilation/execution consequence.

#### MODULE
Must preserve existing exact Module resolution and authority boundaries.

#### BUILTIN / PURE
Must support nodes such as Constant / Transform / Compare / Condition without requiring fake Modules solely to satisfy Product shape.

Determine whether these should compile to existing Graph ModuleInstance semantics via an internal built-in adapter, or whether doing so would merely recreate mandatory Module coupling under another name.

#### SYSTEM_CAPABILITY
Must support future nodes such as State Read, Wait, Create Agent Session, Dispatch Task without exposing SQLite/process/provider-specific implementation.

Determine whether current frozen Runtime already has an authorized extensibility seam. If not, return an Architecture Finding rather than inventing one.

#### COMPOSITE
Determine the smallest valid representation of a sub-workflow packaged as a Node. Do not implement recursion, dynamic graphs or distributed execution here.

### I. Controlled Loop Safety

- explicit Scheduler decision such as `CONTINUE | COMPLETE | BLOCKED | ESCALATE`;
- optional/desired hard guards `max_generated_tasks` and `max_wall_clock_duration`;
- hitting a hard limit routes to Failure Handler / terminal failure rather than silently continuing.

Determine what can be implemented as Product/runtime policy under frozen authority and what requires architecture amendment.
