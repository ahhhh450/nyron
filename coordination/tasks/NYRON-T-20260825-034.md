## Required Semantics

### A. CapabilityType registry

Implement immutable versioned authority vocabulary.

Minimum semantic fields:

- `capability_type_ref`
- `version`
- `scope_schema_ref`
- `operation_schema_ref?`
- `compatible_effect_classes[]`
- metadata / immutable descriptor as needed

Representation may store type ref and version separately. This is an implementation detail and MUST NOT claim to freeze OQ-01 identity syntax.

Rules:

- exact `(capability_type_ref, version)` lookup only;
- exact republish is idempotent;
- conflicting republish fails closed;
- registration never creates a Grant;
- no hardcoded product-node taxonomy.

### B. Runtime current-attempt query boundary

Capability Authority must consume Runtime truth without owning or rewriting Runtime tables.

Provide the narrowest read-only Runtime-owned boundary needed to resolve/validate the exact current `AttemptAuthority`:

- `execution_ref`
- `activation_ref`
- `run_ref`
- `attempt_seq`
- `fencing_token`
- `fencing_generation`

If a small reusable Runtime authority resolver is required, it may be added under `src/nyron_kernel/execution/`.

Capability code MUST NOT directly re-own Run/Attempt lifecycle or fabricate current authority.

### C. Capability policy decision boundary

Do not build a generalized policy framework.

Use the smallest explicit Capability Authority-local evaluation seam sufficient to return one machine-readable decision:

- `GRANTED`
- `DENIED`
- `REQUIRES_APPROVAL`

Policy/PWP/Human inputs are evidence/context only. They MUST NOT directly create a Grant.

Only Capability Authority may commit `CapabilityGrant` canonical truth.

If using an injected policy evaluator, it is an implementation dependency of Capability Authority, not a foreign Grant issuer. Exceptions, malformed results, or non-exact statuses fail closed.

### D. Scope

Scope must be:

- explicit;
- immutable per Grant;
- machine-checkable;
- default deny;
- validated against the exact registered `scope_schema_ref`;
- incapable of caller-controlled hidden expansion.

Use the narrowest schema/scope validation seam; do not invent a broad schema framework.

No in-place scope mutation or widening.

Narrowing, if exposed in this Task, must be represented by revoking the old Grant and issuing a distinct new Grant. It is acceptable to defer a convenience narrowing API as long as the immutable/non-widening invariant is enforced.

### E. CapabilityGrant

Minimum canonical identity/binding semantics must preserve the frozen shape:

- `grant_ref`
- exact CapabilityType ref/version
- `activation_ref`
- `run_ref`
- `attempt_seq`
- `fencing_token`
- immutable validated scope
- `issued_by`
- `policy_decision_ref?`
- `issued_at`
- `not_before?`
- `expires_at?`
- state

Required lifecycle states for this slice:

- `ACTIVE`
- `REVOKED`
- `EXPIRED`

Rules:

- Grant is Activation-bound, Run-bound, Attempt-bound and fencing-bound;
- issue only against exact current Runtime Attempt authority;
- stale/mismatched Attempt or fencing cannot obtain a new Grant;
- Grant is non-transferable;
- same `grant_ref` cannot be rebound to another subject/type/scope;
- exact replay of a committed identical Grant may be idempotent;
- revoked/expired Grant never validates ACTIVE;
- persisted Grant survives reopen exactly.

A small Authority-local clock dependency is allowed for `issued_at/not_before/expires_at` validation. Keep it narrow and testable; Module code must not receive it.

### F. Validation is NOT authority consumption

A `ValidateCapability`-equivalent query may exist in this Task, but it is advisory/non-consumptive only.

It MUST:

- re-check exact current Attempt/fencing;
- check exact Grant identity/state/validity/scope;
- fail closed on stale/expired/revoked/malformed authority.

It MUST NOT be documented or implemented as sufficient authorization to later dispatch an external effect or mutate a foreign canonical Owner from a cached result.

Clarification 004 remains explicit:

`plain check-then-use is forbidden`.

Actual race-safe authority-use admission is deferred until a real EffectOperation or Canonical Command boundary is implemented, where the use can be linearized against replacement/revoke/expire.
