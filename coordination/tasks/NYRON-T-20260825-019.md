## Required Accounting Owner behavior

Implement the smallest direct Accounting-owned persistence/resolution boundary.

### 1. Immutable scope identity

- `accounting_scope_ref` is stable and unique.
- Re-publishing the identical canonical scope may be idempotent if the implementation keeps this simple.
- Reusing the same `accounting_scope_ref` for different canonical identity/ancestry facts must fail closed deterministically.
- Runtime/Graph code must not be the writer of AccountingScope rows.

### 2. Definition-time affiliation

For the leaf scope used by a `ModuleInstanceRevision.static_accounting_scope_ref`, the authoritative resolver must be able to establish:

- exact `accounting_scope_ref` resolution;
- correct pinned `graph_revision_ref` affiliation;
- correct immutable `definition_anchor_ref` for the requested ModuleInstanceRevision/definition placement.

Do not derive membership from Packet provenance, incoming Edge, worker, attempt, caller, mutable Project/Workspace context, or runtime scheduling path.

### 3. Complete static parent ancestry

The Accounting Owner resolver must walk the complete canonical parent chain to a root and fail closed on at least:

- missing parent;
- cycle;
- malformed parent reference;
- structurally inconsistent ancestry;
- any reference that cannot be resolved through the Accounting-owned canonical scope store.

Do not create synthetic rootless/unbounded semantics when ancestry is incomplete.

### 4. ancestry_hash consistency

If the canonical `AccountingScope` stores `ancestry_hash`, the resolver must verify that the stored canonical ancestry identity/hash is consistent with the actual resolved parent chain.

The concrete deterministic encoding/hash algorithm is an implementation-local engineering choice for this slice; keep it simple and documented. Do not claim the algorithm itself is frozen architecture.

A corrupt/mismatched stored ancestry hash must fail closed.

### 5. Authoritative result

Expose one small Accounting-owned resolve/deny result that later `ExecutionAdmission` can consume without re-deriving ancestry.

The successful result must carry enough immutable evidence for the later admission layer to know at minimum:

- requested `accounting_scope_ref`;
- pinned `graph_revision_ref`;
- requested `definition_anchor_ref`;
- resolved canonical ancestry (or an immutable equivalent);
- canonical ancestry identity/hash.

Use direct dataclasses/value objects if helpful. Do not introduce service buses, factories, provider interfaces, plugin systems, generic repository frameworks, or multi-backend abstractions.
