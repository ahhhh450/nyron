## Required Fix Scope

### F-001 — Protected idempotency namespace across profile revisions

Fix protected-key uniqueness so it is bound to the declared provider/account/endpoint/model/idempotency scope independently of `profile_revision_ref`.

Requirements:

- exact profile revision remains part of operation identity;
- rotating/revising the profile must NOT reset the protected idempotency namespace when the effective declared provider/account/endpoint/model scope is the same;
- different semantic operations may not reuse the same protected key within the same declared protected scope;
- different scope may use the same key only when the frozen/current profile semantics truthfully make those scopes independent;
- replay with exact same operation/binding remains idempotent;
- restart preserves conflict behavior;
- add cross-revision same-scope and different-scope adversarial tests.

Do not invent a generic key service or new retry semantics.

### F-002 — Owner-local evidence outcome derivation

Callers must not be able to freely choose `KNOWN`.

Implement a fail-closed, Provider-owner-local evidence semantics mapping such that:

- accepted historical outcome is derived from evidence kind + evidence semantics + profile claims;
- arbitrary `ACKNOWLEDGEMENT` or arbitrary semantics cannot become `KNOWN` merely because `authoritative=True`;
- authoritative `NOT_FOUND` may prove no consequence only when the exact profile explicitly claims that meaning;
- cancel request / accepted cancel without terminal confirmation remains `UNKNOWN`;
- terminal cancellation may become terminal only when profile claims and authoritative evidence are sufficient, while preserving prior partial consequence/usage where applicable;
- unsupported or unknown evidence semantics fail closed or remain `UNKNOWN` according to the already-frozen behavior; they must never silently promote to `KNOWN`;
- evidence replay/conflict behavior remains immutable and restart-safe;
- no retry/redispatch clearance is created.

Do not redesign Effect historical-outcome semantics. This fix is Provider evidence binding only.

### F-003 — Reconciliation release requires explicit authoritative no-usage/no-charge evidence

An arbitrary zero UsageFact must not be sufficient to resolve Provider ambiguity to `RELEASED`.

Requirements:

- every reconciliation UsageFact used for resolution must have an immutable Provider-generated/validated source binding at the line-item/evidence level, not only a broad namespace + operation_ref match;
- `RECONCILING -> RELEASED` requires an explicit authoritative Provider no-usage/no-charge evidence path under current frozen Accounting semantics;
- ordinary zero quantity UsageFact alone must not release unresolved exposure;
- known positive/zero actual usage may resolve only when it is backed by valid authoritative Provider usage evidence/source binding;
- ambiguous or forged zero remains `RECONCILING` and retains exposure;
- duplicate/conflicting usage source identities fail closed;
- restart and replay remain deterministic;
- original ambiguity evidence remains immutable after resolution.

If the existing Accounting API shape can be extended minimally, do so. Do not invent a new settlement meaning or transfer Accounting ownership.
