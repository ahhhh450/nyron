## Frozen Rules That Must Be Preserved

- credential possession is not authority;
- credential resolution success is not dispatch admission;
- PWP owns durable secret-reference slots; Track D consumes those refs and must not redefine PWP ownership;
- raw long-lived credential values must not enter Module inputs/config, Packet, Continuation, RuntimeContext metadata, canonical history, SQLite, logs, Result records, durable evidence, or user-visible error text;
- durable records may store only safe references/binding identities/policy/evidence refs/redacted status/timestamps;
- rotation creates a new binding/reference identity; it must not mutate historical execution meaning;
- revocation affects future resolution only and is not proof of external consequence/non-consequence;
- current Attempt/fencing, CapabilityGrant, ResourceLease and Effect/accounting admission remain independently authoritative at the actual external boundary;
- `FENCED != retry clearance`;
- `UNKNOWN != zero` and `UNKNOWN != no external consequence`.

## Required Implementation Scope

### A. Immutable credential binding identity

Add a bounded Track-D owner-local credential package, preferably under:

`src/nyron_kernel/host/credential/**`

Implement an immutable persisted credential binding revision sufficient to bind at least:

1. stable `credential_binding_ref`;
2. PWP-owned `workspace_secret_ref` / `secret_ref` as an opaque foreign reference;
3. exact Provider `profile_ref` and `profile_revision_ref` scope;
4. non-secret `binding_class` identity (for example a Provider API-key class tag, without embedding a value);
5. monotonic revision identity/sequence such that rotation creates a new binding identity rather than mutating the old one;
6. lifecycle state sufficient to fail closed on future resolution after explicit revocation, without rewriting historical binding identity;
7. creation/revocation evidence refs/timestamps as non-secret metadata only if required by the accepted persistence model.

Required rules:

- no persisted field may carry credential value/token/header material;
- exact replay of the same binding is idempotent;
- changed secret ref/profile scope/class/revision under the same binding identity fails closed;
- rotation must produce a distinct immutable binding identity/revision;
- revoked binding cannot resolve going forward;
- restart preserves binding/revocation semantics;
- raw SQL UPDATE/DELETE against accepted binding history fails closed where required by current persistence conventions.

### B. Resolution request identity

Implement an immutable non-secret resolution request/context binding that includes at minimum:

- `credential_binding_ref`;
- Provider `operation_ref`;
- `run_ref`;
- exact `attempt_seq` or current Attempt identity;
- `capability_grant_ref`;
- applicable `resource_lease_ref` where required by the operation profile;
- exact Provider profile revision identity.

A successful resolution for one Attempt/Grant/Lease/operation context must not be reusable as proof or authority for another context.

### C. Opaque resolved handle

Implement the smallest in-process-only opaque `ResolvedCredentialHandle` or equivalent.

Requirements:

- never persisted;
- never serializable into canonical data structures;
- `repr()` / `str()` must return only a constant redacted marker;
- equality/hash/serialization/debug surfaces must not expose the underlying value;
- no dataclass/asdict/model-dump path may reveal the underlying value;
- no module-level/global cache;
- lifetime limited to the trusted resolver/broker call/use scope;
- do not expose a generic public `.value` attribute to untrusted/module code.

The foundation may use synthetic test-only secret values in memory to verify non-observability, but no real credential may be used.

### D. Trusted resolver / injection seam

Provide a bounded trusted resolver interface and fail-closed default implementation.

Requirements:

- default resolver has no secret backend and always fails closed with a machine-readable code such as `CREDENTIAL_RESOLVER_NOT_CONFIGURED`;
- no environment-variable fallback, implicit default, config-file lookup, OS keychain call, network call, Provider SDK, or hidden test backdoor exists in production code;
- resolution validates exact immutable binding identity and revocation state;
- resolution request context is checked against the exact Provider operation/profile identity;
- credential resolution must never itself mark Attempt/Grant/Lease/Effect admission as valid;
- if a narrow trusted test resolver is needed, keep it test-local or explicitly injected and never Production-default;
- exception/error objects crossing the trusted boundary expose only redacted machine-readable metadata.

### E. Authority separation

The credential foundation must demonstrate that possession/resolution remains orthogonal to authority.

At minimum:

- resolving a credential cannot create/activate a CapabilityGrant;
- cannot create/renew a ResourceLease;
- cannot change Attempt current/fenced state;
- cannot change Effect state/history;
- cannot change BudgetReservation/Accounting state;
- cannot create Provider dispatch admission;
- any later real dispatch must independently use the existing trusted Provider admission checks at the actual boundary.

Do not duplicate or re-own Provider broker admission logic; only ensure credential resolution cannot bypass it.

### F. Redaction / durability / restart

Implement only the minimal helpers/guards necessary to prove:

- raw credential values never enter SQLite columns;
- raw values never enter logs/errors/evidence/result-like durable records;
- resolver/backend exceptions that contain secret-looking material are converted to safe redacted errors before crossing the trusted boundary;
- restart persists references/binding/revocation only, never any resolved handle/value;
- after restart, a new resolution is required; if no resolver/backend is configured, it fails closed rather than reusing stale in-memory state.
