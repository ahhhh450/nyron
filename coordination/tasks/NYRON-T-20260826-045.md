## Required Semantics

### A. Provisioning directory identity / marker binding

For the successful new-directory provisioning path:

1. keep the existing durable `PROVISIONING` canonical state before filesystem creation;
2. after creating the exact expected Resource directory, obtain the strongest available handle/descriptor to that directory without following a final symlink;
3. write the provenance marker relative to that already-open directory handle when the platform supports safe descriptor-relative operations;
4. revalidate that the opened object is the expected directory and that the canonical external path still denotes the same object before transitioning to `AVAILABLE`;
5. any mismatch, unsupported safety property at a point where correctness cannot be proved, malformed marker, replacement, symlink, or ambiguous identity must fail closed to `UNKNOWN`, never silently adopt;
6. never write provenance through a symlink or into an object whose identity cannot be tied to the intended Resource directory.

Use the narrowest Python/OS primitives available (`os.open`, `dir_fd`, `O_DIRECTORY`, `O_NOFOLLOW`, `os.stat`/`os.fstat` identity checks where supported). Do not build a filesystem abstraction layer.

### B. Recovery

Apply the same identity/provenance discipline to `PROVISIONING` recovery:

- absent exact path may be created only under the same bounded rules;
- exact already-proven directory may recover to `AVAILABLE`;
- unproven/pre-existing/substituted/symlinked/mismatched directory becomes `UNKNOWN`;
- no recovery path may manufacture provenance by writing a valid marker into an unrelated directory.

### C. Destruction defense-in-depth

Review the existing `DESTROYING` pre-delete evidence path against the same descriptor/identity model.

A small local hardening is allowed if it directly prevents path substitution before destructive removal. Do not redesign Resource destruction and do not introduce a generalized secure-delete framework.

If stdlib/platform semantics cannot prove safe deletion under the activation-condition attacker, preserve current trusted-root restriction and report the exact residual rather than claiming more than is proven.

### D. Cross-platform behavior

- POSIX: use descriptor-relative/no-follow primitives where actually supported and test them directly.
- Platforms lacking the required primitives: preserve existing correct trusted-root behavior, fail closed where a new check detects ambiguity, and make the residual security assumption explicit in Result evidence.
- Do not assume that Windows symlink creation is always privileged; platform behavior may vary by configuration. Do not use that assumption alone as proof of closure.
- No platform may regress current normal Resource provisioning/reopen/recovery behavior.
