## Required Semantics

### 1. Dispatch boundary / crash classification

Before Module code can run, Runtime must atomically prove and persist that the current Attempt crosses the dispatch boundary:

- exact `Run` exists;
- exact current `RunAttempt` exists;
- full current authority is coherent;
- Attempt state is `CREATED`;
- Run/Activation/Execution identities match;
- transition current Attempt `CREATED -> ACTIVE` in a Runtime transaction;
- if a minimal `AttemptStarted` canonical evidence record is needed, write it in the same transaction.

Only after this transaction commits may Module code be invoked.

A later call that observes the same current Attempt already `ACTIVE` with no terminal outcome MUST fail closed as an ambiguous crossed-boundary Attempt. It MUST NOT silently call `execute()` again.

This Task does not choose retry/replacement policy for that ambiguous Attempt.

### 2. Exact immutable inputs

Inputs passed to Module code must be reconstructed only from the immutable Activation's recorded bindings:

`Activation.input_bindings -> exact Delivery -> exact Packet -> packet.value_ref -> immutable durable value`.

Requirements:

- no mutable latest Graph lookup;
- no readiness re-evaluation;
- no alternate Delivery selection after Activation exists;
- input port names/modes must match the exact pinned ModuleDefinition/ModuleInstance evidence;
- missing/corrupt binding/value fails closed before Module execution if detected before crossing, or produces a machine-readable Runtime failure after ACTIVE if detected after crossing; never substitute defaults.

### 3. Exact immutable config

The current repository has only `config_ref/config_hash` identity evidence and no full Config Owner/value subsystem.

Use the smallest exact boundary compatible with Task 023: an injected narrow loader/callable for the exact `(config_ref, config_hash)` pinned by the immutable ModuleInstanceRevision is acceptable.

The loader must:

- resolve exactly that ref/hash;
- return the immutable config object used for execute;
- fail closed on mismatch/exception;
- never resolve `latest/current`;
- not introduce a Config registry/provider framework.

For frozen `builtin.text.concat@1`, the valid config is the exact empty object required by its schema.

If this cannot be done without redefining Config ownership, stop with a CONTRACT/ARCHITECTURE Finding.

### 4. TRUSTED MODULE MODE execute ABI

Invoke only the accepted host boundary:

`TrustedModuleHost.execute(exact_module_ref@version, immutable_inputs, immutable_config, runtime_context=None)`.

Do not call the builtin implementation directly.

The exact registered ModuleDefinition must remain bound to the hosted implementation as already accepted by Tasks 013/017/018.

No raw store/connection/capability/resource handle may enter Module code.

### 5. Durable values

Frozen §12 requires output value durability before canonical success.

Implement the minimum concrete immutable durable-value persistence needed for this slice if none exists. It may be a small SQLite-backed append-only/content-addressed helper, explicitly an implementation-local storage choice rather than a new frozen Owner or generalized Artifact/blob framework.

Requirements:

- immutable `value_ref`;
- identical re-put is idempotent;
- conflicting reuse fails closed;
- values survive file-backed close/reopen;
- output value(s) exist durably before the success canonical transaction opens;
- orphan durable output values are permitted when the later canonical transaction fails;
- Output Packet must never reference a missing durable value.

The same minimal helper may resolve test/input `Packet.value_ref` values. Do not redesign Packet identity.

### 6. Output validation

For `Completed(outputs)`:

- output names must exactly match allowed output ports for the pinned ModuleDefinition as required by the current contract;
- each output value must satisfy the repository's supported schema subset;
- invalid/missing/extra/wrong-type output fails closed and produces no success Packet/Run-success truth;
- `MODULE_OUTPUT_SCHEMA_MISMATCH` or an equivalent stable machine-readable code must be distinguishable.

Do not generalize JSON Schema execution beyond what this slice actually needs.

### 7. Canonical success transaction

After durable outputs exist, perform **one** Runtime owner-local canonical transaction.

Inside that transaction, in order:

1. re-resolve Run/Attempt/Activation/Execution truth;
2. re-verify the full current-attempt fencing tuple:
   - `execution_ref`
   - `activation_ref`
   - `run_ref`
   - `attempt_seq`
   - `fencing_token`
   - plus current fencing generation as the Runtime's current-authority evidence;
3. require the Attempt is still the exact current `ACTIVE` Attempt;
4. commit Attempt terminal state `SUCCEEDED`;
5. commit Run terminal success separately (do not collapse Attempt and Run facts); add/persist `terminal_attempt_seq` or equivalent frozen terminal association if not already present;
6. create deterministic immutable Output Packet manifest(s) referencing already-durable values;
7. append the minimal canonical terminal event/evidence required by the accepted plan;
8. commit.

All writes above must be atomic. No partial terminal Run/Attempt state may survive without the corresponding Output Packet(s)/terminal event.

Do not run Delivery projection inside this canonical transaction. Projection remains replayable/idempotent after commit.

### 8. Output Packet determinism / idempotency

Output Packet creation must preserve accepted Packet semantics:

- `source_kind = MODULE_OUTPUT`;
- exact `execution_ref`, `graph_revision_ref`, source ModuleInstanceRevision, output port and caused-by Attempt/Run evidence;
- durable `source_packet_seq` allocated under Runtime ordering rules;
- deterministic/replay-stable Packet identity for the same terminal Attempt/output port;
- duplicate terminal delivery/result handling must not create a second Output Packet;
- stale/non-current Attempt must create zero Output Packets.

A narrow in-transaction PacketRepository helper is acceptable if needed. Do not duplicate Packet validation/order logic in a second competing implementation.

### 9. Failed result boundary

`Failed(error)` describes the current Attempt only and MUST NOT decide retry/replacement/skip/abort policy.

Minimum acceptable behavior:

- revalidate current fencing before committing any Attempt-failure fact;
- mark the current Attempt `FAILED` as a distinct Attempt terminal fact if implemented;
- do not fabricate Run success or Output Packet;
- do not create another Attempt;
- leave retry/replacement/execution-level disposition to later Runtime policy work.

Do not broaden this Task merely to implement retry policy.
