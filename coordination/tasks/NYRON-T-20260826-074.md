## D. Atomic Full-Ancestry Hard-Limit Reservation

Within one Accounting Owner transaction:

1. validate request identity;
2. resolve/pin exact static ancestry;
3. resolve/pin applicable BudgetPolicyRevision set;
4. calculate current canonical reserved + committed exposure relevant to each governing HARD rule;
5. evaluate every governing ancestor against the same transaction snapshot;
6. if any hard rule denies: commit canonical `DENIED` with no partial counter increment;
7. if all pass: increment every required ancestor exposure atomically and commit `RESERVED`;
8. persist pinned ancestry/policy refs with the reservation.

No child may remain reserved when any governing ancestor denies.

Use accepted SQLiteStore transaction discipline. Do not introduce threads, workers, connection pools or another writer model.
